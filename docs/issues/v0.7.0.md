# v0.7.0 詳細要件

2026-09-26、v0.7.0はリリース運用の安定化を対象とする。v0.6.0／v0.6.1で発生した静的成果物の不備、検証漏れ、復旧手順の煩雑さを解消し、再現性のある準備・デプロイ・完了処理・切り戻しを実現する。

## 管理・着手条件

- v0.7.0では新しい業務機能を追加せず、リリース運用、検証、復旧手順の改善に集中する。
- 自動化の詳細設計はユーザー素案とレビュー指摘を反映し、[リリース自動化仕様](../operations/release-automation-spec.md)として確定した。本書は事故原因、対応範囲、完了条件を管理する。
- 実装前に既存の`prepare.ps1`、`publish.ps1`、`deploy.sh`、サーバー側ラッパー、ブランチ運用、バージョン管理の責務と重複を整理する。
- スクリプトはWindowsのローカル開発環境と商用・ステージングのLinux環境の境界を明示し、手作業で状態を引き継がない構成とする。

## v0.6.0リリースで発生した問題

### 1. 開発用資産参照が静的成果物へ混入した

ローカルのNuxt開発サーバーが起動したまま静的生成を行ったため、生成HTMLへ`@vite/client`とWindows絶対パスを含む`entry.async.js`参照が混入した。配信先には該当JavaScriptが存在せず、SPAフォールバックのHTMLがHTTP 200で返された。ブラウザはHTMLをJavaScriptモジュールとして読み込めず、商用・ステージングの画面が白くなった。

直接原因：

- 開発サーバーとリリースビルドが同じNuxt生成領域を利用できる状態だった。
- `.output`だけを削除してビルドし、起動中プロセスと`.nuxt`の状態を隔離しなかった。
- ローカル環境で生成した静的成果物を、そのまま正式成果物として扱った。

検出できなかった理由：

- ビルドコマンドの終了成功を成果物の正常性とみなしていた。
- デプロイ後確認が既知のファイルとHTTPステータス中心で、HTML内の全JS/CSS参照を検証していなかった。
- 存在しない資産にもSPAフォールバックが200を返すため、ステータスコードだけでは欠損を検出できなかった。
- Content-Type、HTML本文への開発用URL混入、ブラウザでのJavaScript実行完了を確認していなかった。

### 2. デバッグ計測が本番成果物へ混入した

ビルド端末の`DEBUG=release`をNuxtがデバッグ有効化として解釈し、Hookableのタイマー計測をクライアントバンドルへ含めた。その結果、`[nuxt-app] link:prefetch`の同名タイマーが重複し、ブラウザコンソールへ警告が継続表示された。

直接原因と検出漏れ：

- 本番ビルドでNuxtの`debug`を明示的に無効化していなかった。
- ビルド時に継承してよい環境変数を限定していなかった。
- E2Eとリリース確認でブラウザのconsole warning／errorを失敗条件にしていなかった。

### 3. リリース状態の更新と緊急修正が複雑だった

`version.json`の`current`／`next`とpackageバージョン、正式タグ、`main`の関係がリリース完了後も自動更新されなかった。修正コミットを商用へ適用する際、デプロイ保護が正式タグと`main`の不一致を正しく検出したが、その後のバージョン更新、再生成、PR、タグ発行を手作業で追加する必要があった。

また、候補コミット、`dev`マージコミット、`main`マージコミット、正式タグをそれぞれステージングへ配置する工程が重複し、複数のPR、DBバックアップ、デプロイ、同期、記録更新を個別に操作していた。工程が多いため、実行対象SHAと現在地点の把握が難しくなっていた。

## v0.7.0で確定する対策

### クリーンで再現可能な成果物生成

- リリースビルドは開発サーバーと生成ディレクトリを共有しない。
- ビルド前に、対象ワークスペースのNuxt／Vite開発プロセスが稼働していないことを検査する。稼働中の場合は理由と対象PIDを表示して安全に停止するか、隔離したビルド領域を使用する。
- `.nuxt`、`.output`、リリース専用キャッシュの扱いをスクリプトで統一し、前回ビルドの状態に依存しない。
- 本番ビルドへ渡す環境変数を許可リスト化する。`DEBUG`、`NUXT_DEBUG_PERF`などの診断用変数を継承しない。
- `nuxt.config.ts`では本番時の`debug`を明示的に無効化し、端末環境に依存させない。
- 同一コミットから生成した成果物をステージングで検証し、その同一成果物を商用へ昇格する。環境ごとの再ビルドを行わない。

### 成果物の事前検証

- 全HTMLを走査し、`@vite/client`、ローカル絶対パス、`localhost`、開発専用エントリーが含まれていないことを確認する。
- 全HTMLが参照する同一OriginのJS/CSSを抽出し、成果物内に実ファイルが存在することを確認する。
- 参照URLのパス正規性を検査し、ドライブ文字、バックスラッシュ、`node_modules`などを拒否する。
- Service Workerのプリキャッシュ対象と実ファイルの整合性を確認する。
- 検査失敗時はコミット、push、PR作成、タグ発行、デプロイへ進まない。

### ステージング・商用の配置後検証

- 配信HTMLから全入口JS/CSSを抽出し、各URLのHTTP 200とContent-Typeを検証する。JavaScriptに`text/html`、CSSに`text/html`が返る場合は失敗とする。
- SPAフォールバックによる偽の200を検出するため、Content-Typeに加えてレスポンス本文またはハッシュも確認する。
- 実ブラウザでトップ／ログイン画面を開き、アプリのマウント完了、主要要素の表示、API statusを確認する。
- ブラウザconsoleのerrorを必ず失敗とする。warningは許容リスト方式とし、未知のwarningおよび`console.time`重複を失敗とする。
- Service Worker更新後の再読み込みと、既存キャッシュを保持した利用者の更新経路を確認する。
- 検証失敗時は商用昇格またはリリース後処理へ進まず、失敗地点と復旧方法を表示する。

### バージョン・Git状態の一貫性

- `version.json.current`、`version.json.next`、frontend／backend package、正式タグ、配置SHAの状態遷移を定義する。
- 事前準備、正式リリース、リリース後処理の各段階で期待する状態を機械検証する。
- 正式タグは発行後に移動しない。修正が必要な場合はパッチバージョンを発行する。
- `feature/hotfix → dev → main → dev同期`のどこまでを自動化するかを明文化し、同じマージやデプロイの重複実行を防止する。
- 各工程は再実行可能にし、完了済み工程を安全に検出して継続できるようにする。

## 3スクリプト構成の要求

正式なスクリプト名、引数、責務分担は[リリース自動化仕様](../operations/release-automation-spec.md)に従う。少なくとも次の3段階を単独の手作業へ分解せず実行できる構成とする。

### 1. リリース事前準備

- ブランチ、作業ツリー、依存関係、必要コマンド、バージョン状態、開発プロセス、環境変数を事前検査する。
- Lint、型チェック、単体テスト、E2E、クリーンビルド、成果物検査を実行する。
- 検証済みコミットと成果物を固定し、レビュー可能な差分と結果を出力する。
- 必要なPR作成までを一貫して行い、中断時の再開地点を保存する。

### 2. デプロイ＆リリース

- レビュー・マージ済みの固定コミットだけを対象とする。
- ステージングのプリフライト、DBバックアップ、配置、ブラウザを含むスモークテストを実行する。
- ステージング合格済みの同一成果物を商用へ昇格し、商用でもバックアップ、配置、スモークテストを実行する。
- `main`マージ、正式タグ、GitHub Releaseの順序と失敗時の停止条件を固定する。
- 対象環境、バージョン、SHA、バックアップ、ログを実行前後に明示する。

### 3. リリース後処理

- `main → dev`同期、バージョン状態更新、リリース記録、課題一覧更新、作業ブランチ整理を行う。
- ステージング・商用の配置SHA、タグ、packageバージョン、停止フラグ、ロック、APIリンクを最終確認する。
- 実行結果、検証件数、バックアップのSHA256、デプロイログ、PR、タグ、GitHub Releaseを一つの記録へ出力する。
- リリースが完了状態でない場合は、ブランチ削除や次バージョンへの更新を行わない。

## 切り戻しスクリプトの要求

- 対象環境、現在のバージョン／SHA、戻し先の正式タグ／SHA、対応するDBバックアップを事前表示する。
- デフォルトは確認のみとし、明示的な適用指定がある場合だけ切り戻す。
- アプリだけを戻す場合と、DBを含めて戻す場合を区別する。DB復元は明示指定を必須とする。
- 適用前に現在のDBと配置状態を追加バックアップし、切り戻し自体を戻せるようにする。
- migrationの前後関係を検査し、安全にDBを戻せない場合は自動停止する。
- メンテナンス開始、成果物復元、必要なDB復元、キャッシュ再生成、メンテナンス解除、配置後検証を一連で行う。
- 途中失敗時もロックやメンテナンス状態を放置せず、失敗地点と手動復旧コマンドを出力する。
- 切り戻しの実行記録と検証結果を保存する。

## 次バージョンへ積み残した課題

v0.7.0で扱う積み残しは次のとおり。

1. Nuxt本番ビルドの`debug: false`明示と、`DEBUG`等の環境変数隔離。
2. console error／warningを含む実ブラウザのリリーススモークテスト。
3. 静的HTMLが参照する全JS/CSSの存在・HTTP応答・MIME・本文検査。
4. 開発サーバーとリリースビルドの完全な生成領域分離。
5. `version.json`、package、タグ、配置SHAの状態遷移とリリース後更新。
6. 事前準備、デプロイ＆リリース、リリース後処理の3スクリプトへの統合。
7. アプリのみ／DB込みを選べる切り戻しスクリプト。
8. 中断後の再開、二重実行防止、冪等性、実行記録の標準化。
9. ステージング合格済み成果物を再ビルドせず商用へ昇格する仕組み。
10. 確定した自動化仕様に基づくCLI、GitHub Actions、承認境界、失敗時動作の実装。

## v0.7.0の完了条件

- 合意した3スクリプトと切り戻しスクリプトが実装され、運用文書とコマンド例が整合している。
- 開発サーバー稼働、`DEBUG=release`、欠損資産、HTMLフォールバック、console error／未知のwarningを意図的に発生させた検証で、商用適用前に確実に停止する。
- 正常系で事前準備からステージング、商用、リリース後処理まで完走する。
- 各段階の失敗後に安全に再実行でき、二重タグ、二重PR、不要な再デプロイを発生させない。
- 切り戻しのドライランと、隔離した検証環境での実適用・復旧後確認が成功する。
- v0.6.1のような静的資産不整合をHTTP 200だけで合格させない。
