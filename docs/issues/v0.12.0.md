# v0.12.0 詳細要件 — メール追加・変更・認証、パスワード再設定

2026-10-05、課題24の要件を確定。作業ブランチは `feature/v0.12.0`。

## 目的・範囲

メール任意登録・ログインIDでの利用を維持し、親・子が本人の確認済みメールを使ってパスワードを再設定できるようにする。要件確定・本文書作成後に実装する。

対象外：メール削除、メールなしの子の復旧、親による他者の資格情報変更、ログインID変更、招待メール（課題10）、Resend連携。

## メール追加・変更・確認

- 設定画面に現在のメール・認証状態・確認待ちメールを表示する。家族一覧にはメールを返さない。
- 本人が新メールと現在のパスワードを入力して申請する。親・子で同じ機能を提供する。
- 確認完了まで現在のメールを維持する。確認待ちメールでのログイン・パスワード再設定は不可。
- 現在と同じアドレスでも未認証なら申請できる。既存データ専用の認証・復旧機能は作らず、この通常フローで扱う。
- 再送・申請取消・別アドレスへの再申請が可能。再送・再申請・取消で旧確認リンクを失効する。
- 確認リンクは60分有効・一度だけ使用可能。ログイン不要で別ブラウザでも確認できる。GETや画面表示では更新せず、確認ボタンのPOSTで確定する。
- メールは前後空白を除去し小文字へ正規化する。全ユーザーで一意とし、申請時・確定時に確認する。確認待ちはアドレスを予約せず、先に確認を完了したユーザーが取得する。
- 変更完了時は変更前の確認済みメールに通知する。同じアドレスの初回確認では変更通知は不要。
- 既存メールは自動認証しない。既存のメールログインを維持し、認証完了まではパスワード再設定の対象外とする。

## パスワード再設定

- ログイン画面からメールを入力して申請する。メールでパスワード自体を送らず、再設定リンクから新パスワードを入力する。
- 確認済みメールかつactive所属のユーザーのみ送信対象。不存在・未認証・無効化済みも同じ受付文言と応答を返す。
- リンクは30分有効・一度だけ使用可能。再送、通常のパスワード変更、再設定完了、メール変更完了で旧再設定リンクを失効する。
- 新パスワードは既存同様6文字以上・確認入力あり。再設定成功時はすべてのログイントークンを失効し、自動ログインせず再ログインを案内する。
- 再設定完了を確認済みメールへ通知する。
- 無効化済みメンバーは確認・再設定を確定できない。無効化時に確認待ち申請と再設定リンクを破棄し、復元しても復活させない。
- パスワード変更・再設定時は確認待ちメール申請も破棄し、旧資格情報で作られた申請を残さない。

## メール配送・保護

- Laravelの既存メール機構を利用し、配送設定は環境変数から読み込む。初期SMTPホストは `s140.coreserver.jp`、送信元は `anonymous@ka2.org`、表示名はFamie。
- `MAIL_MAILER`、`MAIL_HOST`、`MAIL_PORT`、`MAIL_SCHEME`、`MAIL_USERNAME`、`MAIL_PASSWORD`、`MAIL_FROM_ADDRESS`、`MAIL_FROM_NAME` を設定可能とする。ポート・暗号化・認証情報は実配送前に運用環境で設定する。
- フロントのリンク生成元URLは環境変数で固定し、リクエストのHostから生成しない。
- 再送間隔60秒、アカウント・宛先・IP単位の制限を設ける。公開APIの応答からアカウントの有無を明かさない。
- 確認トークンはハッシュで保存する。メールリンクの秘密値をアクセスログやブラウザの永続ストレージへ残さない。
- 配送失敗は秘密値を含めず記録する。確認メールの失敗は設定画面へ再試行を案内し、公開再設定申請では対象の有無を明かさない。完了通知の失敗で確定済みの変更を取り消さない。
- ステージングの配送先を許可リストで制限する。実配送検証前に送信設定と許可宛先を設定する。

## 画面・API

- 設定画面のメールカード、ログイン画面の復旧導線、メール確認・再設定申請・再設定入力の公開ページを追加する。
- 送信中の二重操作を防止する。日本語で入力不正・期限切れ・失効・再送待ちを案内する。
- 公開ページはログイン中でも表示可能にする。別アカウントのログイン状態で開いても、リンクが指定する対象だけを操作する。
- `/v1/auth/me/email`：POSTで申請、DELETEで申請取消。`/v1/auth/me/email/resend`：POSTで再送。
- `/v1/auth/email/verify`：POSTで確認。`/v1/auth/password/forgot`：POSTで再設定申請。`/v1/auth/password/reset`：POSTで再設定確定。
- 本人情報に認証日時・確認待ちメール・確認期限を追加し、秘密トークンは返さない。

## 実装・ローカル検証（2026-10-05）

- ユーザーに確認日時・確認待ちメール・ハッシュ化確認トークン・確認期限を追加した。既存メールは変更・自動認証しない。大文字小文字を区別しないメール一意制約を追加し、確定時の競合もDBで拒否する。
- パスワード再設定にはLaravelの既存Password Brokerと `password_reset_tokens` を使用する。家族行・ユーザー行のロック内で状態と秘密値を再確認する。ログインもロック取得後に資格情報を再確認し、再設定前のパスワードで新しいログインを発行しない。
- 再設定申請の対象検索・送信はレスポンス送信後に実行する。SMTP応答時間を公開APIの返答に反映させない。専用キューワーカーは追加せず、プロセス終了等で送信されなかった場合は利用者が再申請する。
- 確認メールは即時送信して失敗を画面に表示する。`log`・`failover`・`roundrobin` transportは秘密リンクのログ出力を避けるため、この機能では拒否する。自動テストは `array` transportとMail fakeを使用した。
- Backend全体：93件合格・441 assertions。PostgreSQL専用21件は通常のSQLite実行ではskip。
- PostgreSQL 14の専用DBで21件合格。同一リンク二重確定、同一メールの別家族同時確定、メール変更と再設定、無効化と確認／再設定、旧パスワードログインと再設定の競合を実際の2プロセスで検証した。既存10件の競合テストも含む。既存DBから分離し、検証用サーバーは終了済み。
- Frontend：変更対象11ファイルのBiomeと `pnpm typecheck` が合格。新規E2EはChromium／iPhone相当WebKitの12件合格（途中の既存通知領域とのセレクター重複を修正して対象を再実行）。既存パスワード・設定カードの8件も合格。新規E2Eの正常送信・確定はAPI応答を差し替えたUI検証であり、APIの実処理はBackendテスト、SMTP配送は今後の実配送検証で担保する。
- リンクの秘密値はフラグメントで受け取り、ページ内メモリへ移した後にURLから除去する。リロード時はメール内リンクの開き直しを案内する。該当ページではフラグメントへの自動スクロールを止め、ルーターの警告へ秘密値が出ないことを確認した。

2. SMTPは `MAIL_PORT=587`、`MAIL_SCHEME=smtp`、`MAIL_AUTO_TLS=true`、`MAIL_REQUIRE_TLS=true` とする（2026-10-07確認済み）。STARTTLSを必須とし、暗号化できない接続は拒否する。`MAIL_USERNAME`、`MAIL_PASSWORD` は環境ごとに設定し、認証情報はGitや本文書へ記載しない。
3. `FAMIE_FRONTEND_URL` を対象環境のフロントURLへ設定する。`MAIL_TIMEOUT` は初期15秒。
4. ステージングも既存配置ガードに合わせて `APP_ENV=production` を維持する。`FAMIE_MAIL_RESTRICT_RECIPIENTS=true`（既定値）と `FAMIE_MAIL_ALLOWED_RECIPIENTS`（カンマ区切りの検証宛先）を設定する。制限有効時に許可リストが空なら全送信を拒否する。配置ガードもステージングの制限解除を拒否する。商用の一般向け配送時のみ `FAMIE_MAIL_RESTRICT_RECIPIENTS=false` とし、許可リストを空にする。
5. 送信制限をHTTPリクエスト間で共有するため、運用環境では永続キャッシュを使用する。IP単位10回／分、宛先・アカウント単位60秒間隔。
6. migration前に既存メールに大文字小文字だけが異なる重複がないことを確認する。重複時は一意制約作成で停止する。`down()` は確認状態と確認待ち申請を削除するため、商用の復旧は前進修正を優先する。

## SMTP配送確認（2026-10-07）

- ユーザー指定の587番ポート・STARTTLS、指定の検証宛先をステージング `.env` へ反映した。ユーザーが設定したSMTP認証情報は表示・変更していない。変更前の `.env` は権限0600で退避済み。
- `MAIL_AUTO_TLS`・`MAIL_REQUIRE_TLS` をメール設定へ追加し、STARTTLS必須を環境変数で指定できるようにした。
- ステージングに導入済みのSymfony Mailerを使い、TLS必須のSMTP transportで指定宛先に「Famie v0.12.0 ステージング SMTP送信テスト」を1通送信し、SMTP受付を確認した。追加の認証接続でSTARTTLSコマンドの使用とTLS必須条件での認証成功を確認した。認証ログ・秘密値は出力していない。
- 最初の検査で `SocketStream::isTLS()` がfalseだったが、この値は接続開始時の暗黙TLS設定であり、STARTTLS後の暗号化状態ではない。実装を確認し、上記のTLS必須接続とSTARTTLSの使用で検証した。
- ユーザーからテストメールの受信確認を受領。SMTP配送経路の検証は合格。新コードの配置、設定キャッシュ反映、アプリ画面からの確認・再設定メールの実配送、実機確認・公開は未実施。
