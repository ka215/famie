## 2. 目的・実装予定範囲

家族の親が活動の目標と報酬内容を設定し、対象者が条件を満たした際に獲得した報酬を記録・確認できるようにする。報酬の実施は家族内の現実の運用に委ねる。

| ID | 機能 | 要件候補・継承方針 |
| --- | --- | --- |
| R1 | 定義管理 | 同一家族のadminが名称・条件・対象者・報酬説明を設定。編集・停止・履歴保持の方式を決定する |
| R2 | 集計・進捗 | 指定期間の活動回数と必要回数。活動は1日1回固定。受信いいね数も選択可、カテゴリは全件または1カテゴリ |
| R3 | 達成判定・獲得 | 条件達成時に履歴を保存。並行処理・再試行でも重複付与しない。期間内に即時判定し、獲得後の減少・条件変更でも取消しない |
| R4 | インベントリ | 現在の条件・進捗・獲得履歴を確認。有効でない定義と他者履歴の表示範囲を決める |
| R5 | 家族・所属整合性 | 定義・対象・活動・獲得履歴を同一家族に閉じ、active所属と役割を毎回確認する |

対象外として継承する事項：送金・決済・決済連携・金銭残高管理・報酬の実際の引き渡し操作。複数所属・招待・家族切替、お知らせ・タスク機能は今回のリワード要件へ追加しない。受渡し済みの記録も初版では設けない。

## 3. 継承する前提

- 定義の所有先はユーザー個人ではなく `groups`。管理権限は家族内のactiveなadmin（画面上の親）。member（子）へ管理権限を与えない。
- 業務APIは `/groups/{group_id}/...` で家族を明示し、所属・権限を毎回検証する。本文や対象IDの差し替えによる別家族への参照・更新を拒否する。
- 初期提供は1ユーザー1家族。対象・履歴はその家族での所属に結び付け、将来別家族の履歴と混ざらない構造にする。
- 所属無効化は物理削除ではない。ユーザー・所属・活動は保持し、活動は通常画面・集計から除外、復元時に再表示する。無効化済み本人はログイン・API利用不可。リワード履歴はD12の承認済み仕様に従い、無効化中は非表示・付与なし、復元時は現在期間のみ再判定する。
- 活動の編集・削除は本人のみ。リワード管理権限を活動の代理編集権限へ拡張しない。
- いいね条件を採用する場合、対象は指定期間の活動が**現在受けているいいね数**。期間は活動の `activity_date` の両端を含み、受信者は投稿者、カテゴリは活動の現在値。いいねした日時や累積押下回数を数えない。
- 投稿者がinactiveならその活動を除外。いいねした人がinactiveならそのいいねを除外し、復元時には再び含める。活動削除・いいね解除で減り、日付・カテゴリ編集で集計先が変わる。

例：10月の活動に11月に付いたいいねは、現在の10月分集計に含む。一方、10月に付いたいいねでも9月の活動なら10月分に含まない。終了後の変化による新規付与は行わない（D06合意済み）。

### 月単位の繰り返しの具体例（D02）

10月開始・3か月サイクルなら、初回は10月1日〜12月31日、次回は翌年1月1日〜3月31日。10月13日に当月開始で作れば、10月1日〜12日の活動も初回へ含む。毎月判定期間をずらす方式ではなく、重ならない3か月ごとの期間を作る仕様（合意済み）。

月初を起点に限定すれば「1月31日から1か月後」のような月末補正が不要になり、初版でも扱える。任意日開始・移動窓・単発との併用を避けることで仕様を抑える。月境界では、終了日の翌日0:00を境に次期間へ切り替える。既定1か月、停止するまで自動反復する（合意済み）。境界のタイムゾーンは親の端末に準拠し、取得不能時はUTC。

### 整合性を保つための具体例・確認事項

#### E1. 締切と、後から実行する集計の違い（D06・D07）

例：10月分の目標がいいね10件。10月31日23:59には9件、11月1日朝に10月の活動へ1件追加され、初回アクセスが同日昼だったとする。昼の現在値だけで集計すると10件だが、締切時点は9件なので10月の報酬を与えてはいけない。逆に締切前は10件でも、翌朝1件解除されれば現在値は9件となり、締切前の達成を見落とす。活動の削除・日付変更でも同じ問題が起きる。

**合意済み：活動・いいね変更時に達成を判定して獲得を即時保存し、期間境界後のアクセス時は期間切替を行う。** 定義有効化時・所属復元時の期間内再判定も既存方針を維持する。前期間の獲得を現在値から作り直さない。

- 家族内activeメンバーがリワード画面を開くまで、家族単位の切替処理を待つ。画面の認証済みAPIアクセスが起点。匿名・他画面のAPIアクセスは起点にしない。
- 3か月サイクルの切替はその3か月境界だけ。アクセスのない期間があっても過去へ新規付与せず現在期間へ進める。
- リワード画面を開く前でも活動・いいねは保存できる。判定は開始月とサイクルから現在期間を識別して即時実行する。例：11月2日に活動を保存し11月5日に画面を開く場合も、2日の達成は11月分へ保存し、5日の切替で消さない。
- 同時アクセスでも家族単位に一度開始する。処理中も即時判定を継続し、切替完了後の再集計で進捗を更新する案。再集計が遅れても期間内の達成保存を欠落させない。
- 合意済み：集計中もリワードを閲覧でき、「集計中」を表示する。定義編集は不可。表示する進捗は更新前の値であることを明示し、未集計を0件と表示しない。失敗時の再試行・処理状態の解除は具体化待ち。停止・再開・削除等の管理更新も完了まで待たせる案。

#### E2. 条件変更で同じ報酬を二度与えない（D08・D09）

例：10月に「活動10日」で既に獲得した後、親が「活動5日」に変更しても、同じ10月分をもう一度獲得しない。変更を次サイクルから適用すれば、10月分は元の条件のまま、11月分から新条件になる。3か月サイクルなら次の3か月期間から適用する。

保存時の重複防止は「定義・期間・対象者」を基準とし、条件の版だけが変わっても獲得回数を増やさない仕様（合意済み）。獲得保存後の条件変更でも履歴を削除しない。別定義として新規作成した場合は別の報酬になるため、削除・再作成による扱いも明示する。

#### E3. 現在の進捗が減っても、獲得済み報酬は残す（D05・D09）

例：「活動10日」で獲得した後に本人が1日分の活動を削除すると、現在の進捗は9/10だがトロフィーは残る。履歴には「獲得時10/10」、条件画面には「現在9/10・獲得済み」と表示すれば矛盾なく説明できる。承認済み方針の画面上の具体化であり、報酬を自動取消ししない。

#### E4. リワードで使っているカテゴリを削除できるか（D01）

例：活動がまだ0件の「勉強」カテゴリに、「勉強を10日」の有効リワードがある。活動が0件だからとカテゴリを削除できると、目標の対象がなくなる。

合意済み：有効な定義・次期間に適用予定の条件で使うカテゴリは削除不可。親には「リワードで使用中」と表示する。停止済み・過去の条件の参照をどう残すかも定め、獲得履歴のカテゴリ名は保存しておく。現在のカテゴリ管理に必要な変更として本版の実装範囲に含める。停止中の参照も再開に必要なため削除を禁止し、削除済み定義・過去版だけの参照なら削除を許す案をE5と合わせて確認する。

#### E5. 停止・再開・削除と枠の管理

**合意済み**：停止・再開で期間を延長・リセットしない。停止すると有効枠が空き、有効な定義はグループ内で最大3件（未来開始を含む）。下書き・停止済みを含め、削除されていない定義は合計6件まで。再開時も3件の上限を再確認する。

合意済み：停止中は進捗の再計算・達成判定をしない。再開した時点で、現在期間の停止中の活動も含めて再計算し、未獲得なら達成判定する。停止中に終了した期間への遡及付与はしない。「停止中の再計算なし」と「再開時に停止中の活動を含む」を両立させる。

**削除仕様（2026-10-15変更承認済み）**：同一家族のactiveな親が、下書きは直接物理削除、停止中は論理削除できる。下書き＝一度も有効化していない定義とし、条件版・対象者設定もトランザクション内で物理削除する。下書きに進捗・期間・獲得レコードまたは期間切替実績がある場合は不整合として409で拒否する。停止中の論理削除は履歴を保持し、復元・再開・編集・新規付与はできなくする。

| 対象 | 削除後の扱い（承認済み） |
| --- | --- |
| 定義一覧・管理 | 通常・停止済み一覧から除外。削除済み一覧や復元UIは設けない |
| 枠 | 有効3件・合計6件の計算から除外し、新しい定義を作成できる |
| 条件・版・対象・期間 | DBで保持し、過去獲得の参照を壊さない。今後の判定対象にはしない |
| 獲得履歴 | 全件保持。本人・同一家族の親はインベントリから閲覧可能。所属無効化の閲覧制限は維持 |
| 表示 | 獲得時の名称・色・報酬・条件・集計値を表示し「削除済みリワード」と併記。現行定義への操作リンクは出さない |
| 未表示の達成通知 | 削除前に獲得済みなら、未表示モーダル通知と既読状態も保持する |
| 再作成 | 同じ名称でも新しいIDの別定義。過去履歴は引き継がず、元の定義の一回制限とは別に判定する |
| カテゴリ | 削除済み定義の参照だけなら削除を妨げない。履歴の名称等を保存し、実参照は安全に解除できる設計とする。活動や別の未削除定義の参照があれば削除不可 |

例：銅の「勉強10日」を獲得後、親が停止→削除した場合、管理一覧からは消え合計6件の枠が1つ空く。本人の履歴には獲得時の銅トロフィーと報酬が残る。後で同名の定義を作っても、過去のトロフィーを書き換えない。

削除・再作成すると同じ期間の同じ活動で別定義を達成できる点には注意が必要。承認済みの扱いは「別定義なので付与可」とし、家族内の親の運用に委ねる。これを禁止するなら名称以外の同一性判定や再作成制限が別途必要となる。

削除確認では「新たな獲得は停止します。獲得履歴は残ります。削除後は元に戻せません」と表示する案。停止／削除と達成保存の同時処理では、先に確定した状態を基準にし、削除後に新たな獲得を作らない。

### タイムゾーンの確定仕様（D02）

ユーザー指定：定義可能な親がアクセスしているブラウザ・PWAに準拠し、JSTなら日本標準時、未定時はUTC。

言語ロケール（日本語等）とタイムゾーンは別情報で、日本語の端末でも海外の時刻設定になり得る。そのため、定義作成時に端末のタイムゾーン識別子を取得し、サーバーで検証して定義へ保存する。日本時間ならAsia/Tokyo、取得不能ならUTCとし、保存前に画面で確認できるようにする。

旅行・別端末・別の親のアクセスで締切が動かないよう、保存済みタイムゾーンは以後固定する（承認済み）。初版は開始後のタイムゾーン変更を提供しない。開始・終了はそのゾーンの月初0:00を基準にし、内部の時刻はUTCへ変換して比較する。終了境界は含まず、次期間開始と一致させる。夏時間があるゾーンでも固定時間数ではなく暦月で計算する。

活動のactivity_dateは記録済みの実施日として扱い、端末タイムゾーン変更で別の日へ変換し直さない。期間内かは実施日の年月日、現在期間の開始・終了判定は定義のタイムゾーンで行う。取得・保存後固定は承認済み。

### グループごとの枠上限・ページング（D13）

最大有効枠・最大管理枠はグループごとに異なる将来の拡張を予定しているため、DB管理を推奨する。案はgroupsに専用の整数属性として有効上限・管理上限を保持し、既存・新規グループの初期値は3・6とする。環境変数は使わず、一般の親・子がAPIから上限を書き換える機能も提供しない。制限解除の操作UIは後続版。

有効上限は管理上限以下とする。将来、有効上限を10へ拡張する際は管理上限も10以上へ更新する必要がある。上限引下げで既存定義を勝手に停止・削除せず、保有数未満への変更を拒否する案。作成・有効化・再開の同時処理でも枠を超えないよう、家族単位で確認する。DB管理を採用し、専用属性・同時更新の制約は本書の設計方針とする。

リワードの一覧・獲得履歴のページサイズは10件で確定。活動・ギャラリー等の既存ページサイズは変更しない。

### 複数端末の達成通知（D14）

合意済み：iPhoneとPCの同時アクセス等では先行した既読リクエストの端末だけにモーダルを表示し、後続には既読として返す。毎サイクルの新たな獲得を対象に、複数未表示は1モーダルへまとめる。他者閲覧では本人の既読を付けない。

通常の一覧取得で両端末へ未読情報を返し、それぞれ表示後に既読を書くだけでは両方にモーダルが出る。実現案は「通知の取得と表示権の取得」をDBで一度に処理し、先行端末だけに通知内容を返す。後続は表示権を取れないためモーダルなし。本人・獲得履歴単位で保持する。

承認済み：表示権取得時に既読とし、通信失敗時にも再通知しない。通知を見逃す可能性はあるが獲得履歴は残る。表示成功後の既読確定を厳密に保証するなら、一時的な表示権と期限・再取得の管理が必要となる。

### 条件変更の適用時期（D08）

有効期間中の変更は次サイクルから適用する合意を維持する。未開始の初回期間と、停止していても既に開始済みの期間を区別する以下の適用表を承認済み。

| ケース | 適用時期（承認済み） | 例 |
| --- | --- | --- |
| 下書き | 直接編集、初回有効化に反映 | 作成途中の必要数変更 |
| 有効だが初回開始前 | 初回開始に変更済みの条件を適用 | 11月開始の定義を10月20日に変更→11月1日から新条件 |
| 有効期間中 | 次サイクルから適用 | 10月の定義を20日に変更→11月から新条件 |
| 停止中で、初回開始前 | 初回開始条件を変更。開始後に再開する場合も初回用条件として扱う | 11月開始を10月に停止・変更→11月再開で新条件 |
| 停止中で、現在期間は開始済み | 再開だけでは新条件へ切り替えず、次サイクルから適用 | 10月10日停止、15日変更、20日再開→10月は旧条件、11月から新条件 |
| 停止中に適用予定の次サイクルへ進んだ後の再開 | その期間に適用予定だった新条件で再計算 | 上記の定義を11月5日に再開→11月分は新条件、10月へ遡及付与しない |

例は1か月周期。3か月周期なら変更の適用境界も次の3か月期間となる。過去の版・獲得は上書きせず保持する。初版では、一度初回期間が開始した定義の開始月・サイクル長・タイムゾーンの変更を不可とする（承認済み）（必要なら停止→削除→新規作成）。期間の重なり・欠落を避け、指標・カテゴリ・必要数・報酬・色・対象者の変更だけを次期予約として扱う。開始前の期間設定変更は当月以降の入力制約を再確認する。

### 追加判断の確定仕様

| ID | 判断事項 | 承認済み仕様・例 |
| --- | --- | --- |
| F1 | 未来開始後、活動等の変更がなくても達成済みの場合の初回判定 | 有効な現在期間を初めて準備するリワード画面アクセスでも未獲得者を判定する。例：11月開始の定義に、10月中に登録済みの11月実施日の活動があり、11月に変更操作がない場合も初回表示時に付与する。既存活動を含むD05に合わせる。初回アクセスが期間終了後なら過去期間へ付与しない |
| F2 | 下書きの削除入口 | 2026-10-15変更承認：下書きから直接物理削除できる。下書き→停止は禁止。有効・停止から下書きへ戻せない。定義期間が始まっても下書きは集計・判定しない |

以下は実装上の設計方針として補完し、追加のユーザー判断を要求しない。

- 次期変更は定義ごとに1つの予約版を持ち、同じ適用期への再編集は予約版の置換とする。現在版・過去獲得は変更しない。対象者の追加・除外も適用期から反映する。
- 集計状態は未処理／処理中／完了／失敗を識別する。失敗時も保存済み獲得・活動は保持し、画面で「集計に失敗しました」と再試行操作を提供する。認証済み同一家族のactiveメンバーが再試行可能。処理の完了・失敗では編集ロックを解除し、途中結果を再利用しても獲得を重複作成しない。
- 集計中は進捗が更新前である旨を表示し、履歴は保存済みのものを閲覧可。定義の作成・編集・有効化・停止・再開・削除は処理完了まで不可。活動・いいねと即時達成保存は継続する。
- 入力は名称1〜50字、報酬説明1〜500字、固定必要数1〜10,000または期間内日数の整数、周期1〜12の整数、対象者1人以上で同一家族active所属のみ。名称・説明は前後空白を除いて検証。名称重複は可。色は金／銀／銅のいずれかを親が選ぶ。開始月は保存済みタイムゾーンで当月以降、開始前に再編集した際も検証する。
- 各一覧は10件、条件は期間終了境界・ID、履歴は獲得日時・IDで安定した並び順を保証。獲得スナップショットは色も保存する。

| 概念 | 必要な情報・整合性 |
| --- | --- |
| 定義 | 家族、名称、管理状態、作成者。家族内adminが管理 |
| 条件版 | 指標、カテゴリ条件、開始月、1〜12か月サイクル、必要数、トロフィー色、報酬説明、適用時点。獲得時の版を特定可能にする |
| 対象 | 条件と同一家族のgroup_member_id。別家族・不存在・inactive指定を拒否する |
| 評価期間 | 具体的な開始日・終了日・タイムゾーン。繰り返しを採用する場合も同じ期間を一意に識別する |
| 獲得履歴 | 定義・版・期間・対象所属、獲得日時、獲得時の集計値・条件・名称・カテゴリ・報酬説明のスナップショット。後の改名・編集に影響されない |

独立した「所持数」テーブルは必要性が決まるまで追加しない。本文の長さ・整数範囲・日付整合性・対象の重複をサーバー側でも検証する。権限や条件値を自由形式のメタ情報だけへ逃がさない。

APIには定義一覧・作成・編集・停止／再開、本人の条件／進捗／獲得履歴、親の対象者別閲覧を想定する。memberの管理操作、他家族ID、inactiveのアクセスを拒否する。ページング・安定した並び順・入力エラー・状態競合の応答は具体仕様で決定する。獲得はクライアントの申告値を信用せずサーバーで判定する。

集計と付与は、活動・いいね・定義変更・所属無効化との競合を考慮する。トランザクションとDB一意制約で再試行・同時達成を安全に扱い、既存のロック取得順を維持する。初期導入で過去全期間へ無条件に報酬を付与せず、D05・D06で合意した範囲だけを評価する。

### API権限表・応答契約

全操作は認証・URLのgroup_idに対するactive所属が必須。以下の「親」は同一家族のactive admin、「本人」はactiveな対象所属の本人を意味する。

| 操作 | 親 | 子 | 契約 |
| --- | --- | --- | --- |
| 管理定義一覧・詳細・予約版取得 | 可 | 不可 | 同一家族の未削除定義のみ。下書きは管理画面専用 |
| 下書き作成・編集、有効定義の変更予約 | 可 | 不可 | 総枠・入力制約・適用期を検証。現在版を書き換えない |
| 有効化・停止・再開・削除 | 可 | 不可 | 下記状態遷移と枠制約に従う。集計中は拒否 |
| 対象者の条件・進捗・獲得一覧 | 家族内active対象者分 | 本人分のみ | 他家族・inactive対象者は取得不可。削除済み定義の獲得履歴は取得可 |
| 期間準備・失敗時再試行 | 可 | 可 | リワード画面操作に限定。家族単位に排他開始。現在期間のみ初回達成判定 |
| 達成通知取得・既読確定 | 本人分のみ | 本人分のみ | 更新APIで原子的に未読を取得・既読化。通常の履歴GETは既読化しない |
| 枠上限変更、手動付与・取消、削除復元 | 不可 | 不可 | 初版に一般利用者向けAPIを提供しない |

一覧は10件のページングとし、同じフィルター条件で安定順を保つ。更新は成功後の状態・現在版／予約版・適用期間を返す。未認証は401、管理権限不足は403、家族外・inactive対象・不存在は既存APIの情報非開示方針に合わせ404、入力不正は422、枠超過・状態遷移不正・集計中の更新・古い版を基にした競合編集は409として理由を返す。上限超過のエラーには上限と現在件数を含める。処理中レスポンスは状態と保存済みデータを返し、空の成功結果で置き換えない。

通知取得はリワード画面で本人が行い、対象獲得の既読確定と通知データ取得を同一トランザクションで行う。後続端末へ未読を返さない。通信失敗時に既読を戻さない。まとめ通知の件数をページング件数で切り捨てず、対象獲得を全て確認できる表示とする。

### 定義・集計の状態遷移

| 現在状態 | 操作 | 遷移・処理 |
| --- | --- | --- |
| 未作成 | 作成 | 下書き。管理枠を1件使用 |
| 下書き | 有効化 | 有効。未来開始も有効枠使用。現在期間が始まっていれば達成判定 |
| 下書き | 削除 | 定義・条件版・対象者設定を物理削除し、管理枠を解放。履歴不整合時は拒否 |
| 有効 | 停止 | 停止。有効枠を解放。獲得・予約版・期間起点を保持 |
| 停止 | 再開 | 入力・active対象・有効枠を再検証して有効へ。現在期間の適用版で停止中活動も再計算 |
| 停止 | 削除 | 削除済み。管理枠を解放。参照・履歴保持、復元不可 |
| 有効 | 期間境界 | 有効を維持。現在期間を進め、予約版を適用。獲得回数は新期間で再び1回まで |
| 削除済み | 更新・再開等 | 全て不可 |

開始前／期間中／期間終了は定義状態とは別の期間属性。「有効」のまま各期間を自動反復し、停止中も暦上の周期は進む。下書きは一度も有効化していない定義であり、期間開始後も通常集計・期間切替・達成判定を実行しない。編集でも再判定しない。下書き→停止と有効・停止→下書きは禁止。初回有効化時に現在期間の過去活動を含めて初めて判定する。開始月が過去の場合は当月以降へ修正してから有効化する。削除済み・停止中の通常集計は実行しない。

集計は未処理または失敗→処理中→完了／失敗。処理中だけ管理更新を禁止する。処理失敗では保留データを未適用のまま残し、再試行が重複付与を作らないようにする。中断による処理中状態の残留は実装で回復可能にし、ロックの有効時間・ログ・回復手順を検証する。

### 保存・並行処理の必須制約

- groupsに有効枠上限・管理枠上限を専用整数属性として保持。既存・新規家族へ3・6を設定し、正数かつ有効上限≤管理上限を保証。通常の親子APIから更新不可。
- 定義・条件版・対象所属・カテゴリ・期間・獲得のgroup_id一致をDB制約と認可で保証する。カテゴリは現在版・予約版・下書き・停止定義の参照中は削除不可。過去版・削除済み定義だけなら履歴の表示情報を保持して参照解除できる。
- 定義×期間開始境界×対象所属で獲得を一意にする。条件版をキーへ加えて同期間に再付与できる構造にしない。期間の境界とタイムゾーンを保存し、版変更・再試行でも同一期間を識別する。
- 活動・いいねの保存と、その操作による期間内の達成保存を整合するトランザクションで扱う。期間終了後の再集計だけに依存して獲得を作らない。対象者の有効性・停止・削除・適用版を付与直前に確認する。
- 枠の作成／有効化／再開、条件変更、達成保存、所属変更、カテゴリ削除は既存の家族単位ロック順に合わせる。並行処理で上限超過・削除後付与・予約版の消失を発生させない。
- 現在期間の開始・終了判定はサーバー時刻と定義保存タイムゾーンで行い、端末の送信時刻・進捗値を信用しない。開始日を含み、次期間開始境界を含まない。

## 10. 期間内日数による必要数（2026-10-15正式採用）
