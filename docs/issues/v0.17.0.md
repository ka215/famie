### 1.3 フェーズ方式での進め方と承認

1. **フェーズ開始時の詳細確認・仕様確定**：前フェーズのステージング実機確認合格後、次フェーズの現行画面・API・データ・例外経路を調査する。本書へ対象／対象外、設計、用語、互換性、受入条件、検証方法を追記する。判断事項は都度ユーザーと連携し、詳細仕様の承認を得てから実装する。
2. **実装・ローカル確認**：承認範囲を実装し、関連する自動検証とユーザーのローカル確認を行う。仕様変更が必要になった場合は先に合意する。
3. **コミット・ステージング配置**：ローカル確認のOK後にコミットし、PRでdevへ取り込む。固定候補からCIが生成した成果物をステージングへ配置し、候補を固定して実機確認する。
4. **フェーズ判定**：NGなら修正とローカル確認から繰り返す。OKなら対象範囲・PR・commit/tree SHA・workflow run・成果物SHA256・実機／PWA結果をGitHub Issueへ記録し、「フェーズ合格／商用未承認」とする。次フェーズへ進むためにコミットをまとめ直す必要はない。
5. **次フェーズへ継続**：同じv0.17.0と作業ブランチで繰り返す。新候補では旧セッションと証跡を保管してセッションを新規作成し、旧候補の合格状態を引き継がない。詳細は[候補更新の運用手順](../operations/runbooks/release-script-notes.md#21-フェーズ単位の確認と候補更新)に従う。
6. **商用リリース承認**：全フェーズ完了後、最終候補で全体回帰・ステージング実機確認を行い、その候補を対象とするユーザーの明示承認後にmain昇格・正式タグ・同一成果物の商用配置へ進む。承認後に変更した場合は再検証・再承認する。

フェーズ開始時の「詳細仕様承認」、実装後の「ローカル確認OK」、ステージング実機確認後の「フェーズ合格」、最後の「商用リリース承認」は別の判断である。全体計画の記載だけで後続フェーズの実装承認とは扱わない。

## 3. 用語・翻訳対象

設定値（`null | ja | en`）と実効言語（`ja | en`）を区別する。`null`は自動判定であり、現在表示中の言語をDBへ書き込む意味ではない。

| 日本語 | 英語 | 適用 |
| --- | --- | --- |
| 自動 | Automatic | 言語設定の自動選択 |
| 日本語 | 日本語 | 日本語選択肢は両言語で自称を維持 |
| English | English | 英語選択肢は両言語で自称を維持 |
| 言語 | Language | 表示設定 |
| 家族 | Family | 所属する家族 |
| 親（管理者） | Parent (admin) | 現行の権限説明 |
| 子供（一般） | Child (member) | 現行の権限説明 |
| タイムライン | Timeline | 共通ナビ |
| リワード | Rewards | 共通ナビ |
| ギャラリー | Gallery | 共通ナビ |
| 設定 | Settings | 共通ナビ |

利用者向けの本文・ボタン・placeholder・説明・確認ダイアログ・トースト・検証エラー・ARIA・画像の代替文言・ページタイトルを対象とする。ライセンス原文・ブランド名Famie・技術ログ・ソースコメント・OSやブラウザ固有UIは翻訳対象外。

活動本文・家族名・人名・ユーザー名・カテゴリ名・リワード名等の利用者データは翻訳しない。初期カテゴリも既存の保存名をそのまま表示し、新規家族作成時の初期カテゴリ名はフェーズ1では変更しない。フェーズ5で新規生成時の言語方針を確定する。言語切替で既存レコードを書き換えない。

日本語の共通ヘッダーは現行どおり敬称設定ONで「さん」を付け、OFFでは付けない。英語ではON/OFFにかかわらず表示名のみとする。敬称設定欄（スイッチと結果通知）は実効表示言語が日本語の場合のみ表示する。言語選択の保存前は現在の実効言語に従う。本人の敬称設定は保持し、日本語へ戻した際に設定欄を再表示して再適用する。対象外の機能固有画面内に残る敬称は後続移行に含める。

## 4. 言語判定とライフサイクル

### 4.1 判定規則

| 状態 | 優先順位 |
| --- | --- |
| 本人取得済み・固定設定あり | 本人DBの`ja`または`en` |
| 本人取得済み・自動 | ブラウザ最優先言語から判定。ゲスト設定を使わない |
| 未ログイン | このブラウザのゲスト選択 → ブラウザ最優先言語 |
| 認証起動中 | ゲスト設定／自動で仮表示し、本人取得後にDBで確定 |
| 判定不能・不正値 | `en` |

ブラウザは`navigator.languages[0]`、取得できなければ`navigator.language`を使用する。正規の言語タグを解釈し、主言語が`ja`なら日本語、それ以外は英語とする。候補一覧を走査して日本語を優先しない。`ja`／`ja-JP`は日本語、`en-US`／`en-JP`／`fr-FR`は英語。不正タグ・空値は英語。IPによる国推測は行わない。

自動設定だけ`languagechange`およびアプリ復帰時に再判定する。固定設定はOS変更で変わらない。別端末での設定変更は次回の本人取得時（再起動・再ログインを含む）に反映する。リアルタイム同期用のポーリングやpushは追加しない。

### 4.2 保存と認証遷移

- ゲスト選択は`localStorage`の専用キー`famie.uiLocale.guest`へ`auto | ja | en`を保存する。`auto`はDBの`null`に相当する。テーマ設定とは別に管理する。
- 本人設定の正本はDB。v0.17.0では本人の言語設定を端末へ永続キャッシュしない。本人未特定時に前ユーザーの言語を仮適用することを避け、本人取得完了時に切り替える。素案の本人別キャッシュによる仮表示は今回採用しない。
- ログイン／登録成功時は応答の本人設定を適用する。ゲスト選択をDBへコピーしない。新規登録・メンバー追加の初期値は`null`。
- ログアウト・401・利用不可による認証解除・ユーザー切替時は本人の言語状態を解除し、ゲスト選択／自動へ戻す。メンテナンス時の現行セッション保持は維持する。
- 本人情報取得の通信失敗で本人設定をDBへ上書きしない。既存の認証制御に従い、再取得可能なエラーを表示する。
- 保存中にユーザーやセッションが変わった場合、古い応答を新ユーザーの状態へ適用しない。トークンをストレージキーやログへ記録しない。
- ブラウザ保存が拒否されたゲスト選択は現在の画面には反映し、再起動後に保持できない旨を実効言語で通知する。本人のDB保存成功とは区別する。

## 5. UIと保存操作

### 5.1 本人設定

設定画面の「表示設定」に「言語／Language」のラジオ選択と保存ボタンを追加する。選択肢は「自動／Automatic」「日本語」「English」。現在の保存値と自動時の実効言語を示し、「本人だけに適用し、他の端末にも反映する」説明を付ける。

選択中は表示言語を変更せず、保存成功後に応答の設定を反映する。成功通知は変更後の言語、失敗通知は変更前の言語で表示し、失敗時は保存済み値へ選択を戻す。保存中は重複送信を防ぎ、本人プロフィール／敬称更新との競合を防ぐ。言語の保存だけでは他の未保存フォームを送信・初期化しない。

固定値から自動への保存成功時は直ちにブラウザで再判定する。言語変更はリロード・再ログイン・ルート変更を必要としない。表示済みのクライアント検証文言も更新し、入力値やフォーカスを維持する。APIが返した過去のエラー本文は切替時にクリアし、古い言語のまま残さない。

### 5.2 ゲスト設定

ログイン・登録・再設定申請・再設定実行・メール確認に共通の言語切替を設ける。各カード右上の44pxアイコンボタン（指定SVGの`translate`）からモーダルを開き、「自動／日本語／English」を選択する。タイトルと主要導線の間には選択欄を置かない。閉じるボタンまたはEscapeで閉じ、操作元へフォーカスを戻す。認証済みでこれらのリンクを開いた場合は本人設定を優先し、ゲスト切替では本人設定を変更しない。本人設定への案内を表示する。

未ログイン時は選択を即時反映・端末保存する。ゲスト選択はログイン後も独立して保持し、ログアウト時に再利用する。ゲストの「自動」は端末判定に戻す操作とする。

## 6. フロント基盤

- 採用は`@nuxtjs/i18n` **10.6.0**。取得可能な版とNode条件`>=20.11.1`を読取確認済み。導入時にlockfileで依存を固定し、既存Nuxt 4.6系・Vue・静的生成との実動確認を行う。互換性検証済みとはまだ扱わず、採用版変更が必要な場合は連携する。
- `strategy: no_prefix`、`defaultLocale: en`、ライブラリによる自動ブラウザ判定は無効とし、4章の判定を単一の状態管理で適用する。独自Cookie判定との二重管理は作らない。
- 辞書は`frontend/i18n/locales/ja.json`・`en.json`、Vue I18n設定は`frontend/i18n/i18n.config.ts`。両辞書を静的importし、今回遅延読込やNitroの翻訳配信APIは使用しない。
- 意味キーを`common`・`navigation`・`auth`・`settings`・`validation`・`errors`・`install`単位で管理する。文単位の翻訳と名前付きパラメータを使い、利用者入力をキーにしない。HTML文言・文字列断片の連結は避ける。
- `html[lang]`は実効言語に追従する。対象ページのタイトルとARIAも同時に更新する。対象外ページの固有タイトルは後続移行対象。
- 対象内の件数・容量・日時は実効言語に応じて`Intl`で整形する。日時のタイムゾーン、APIのISO形式・数値型・並び順は維持する。週開始日・リワード期間・日付境界を表示言語から決めない。対象外カレンダーのロケール処理は今回変更しない。
- フォールバックは英語。未翻訳やキー露出は受入不可とし、フォールバック動作だけで合格にしない。
- 既存Zodルール・共有ユーティリティを再利用し、検証文言を翻訳可能な方式へ変更する。日英で入力条件を変えない。表示後の言語変更でも再評価できる構成とする。

## 7. DB・本人API契約

### 7.1 DB

`users.ui_locale`をnullableの文字列（長さ35、default `null`）として追加する。将来の地域・スクリプト付き言語コードを妨げない長さとし、現在の許可値は`null | ja | en`に限定する。既存ユーザーは全員`null`、登録・家族メンバー作成も`null`。所属・家族テーブルには追加しない。本人情報以外の一覧へ設定値を追加しない。

追加migrationのdownは当該カラムだけを削除する。ロールバックで言語選択が失われることをリリース手順に記載し、既存データ復元を自動実施しない。

### 7.2 入出力

既存APIのbase path・認証・HTTPコード・応答構造を維持し、本人情報の`user.ui_locale`を必須プロパティとして追加する。ログイン・登録・本人取得・本人更新・パスワード警告停止など、共通の本人payloadを返す全経路で統一する。

`PATCH /auth/me`の追加契約：

| 入力 | 結果 |
| --- | --- |
| `{ "ui_locale": "ja" }` | 本人を日本語固定へ変更 |
| `{ "ui_locale": "en" }` | 本人を英語固定へ変更 |
| `{ "ui_locale": null }` | 本人を自動へ変更 |
| `ui_locale`省略 | 既存値を保持。他の既存項目は従来どおり部分更新 |
| `"auto"`・`"ja-JP"`・`""`・大文字・数値・配列等 | 422、保存しない |
| 空body／未知の項目 | 現行どおり422 |

Laravelの空文字→null変換より前に`ui_locale: ""`を不正値として扱うことを保証する。nullと省略を区別し、混在更新のいずれかが不正なら全体を保存しない。

親・子とも本人のみに適用する。家族メンバー作成／編集APIに`ui_locale`を渡した場合は422で拒否し、親から子の設定を変更させない。登録APIでも同項目は受け付けず、ゲスト選択を暗黙保存しない。

OpenAPI・フロントの`User`型・Factory・API Featureテストを同じ実装で更新する。旧クライアントによる本人更新は追加項目を省略でき、既存の設定を消さない。

## 8. API言語とエラー

`useApi`は各リクエスト開始時の実効言語を`Accept-Language: ja`または`en`で送る。バックは認証済みの本人固定設定を優先し、自動・未認証はヘッダーで決める。ゲストのログイン失敗時に照合候補ユーザーの固定言語を使わず、ユーザーの存在や設定を漏らさない。

一般APIクライアントのヘッダーはq値順・同率は記載順で最優先の有効な言語タグを採用し、主言語がjaなら日本語、それ以外は英語とする。q=0は除外。未指定・不正・wildcardのみは英語。対応言語だけを拾って下位のjaを優先しない。

本人設定を変更するPATCHの応答本文／`Content-Language`はリクエスト開始時の言語、フロントの切替は成功payloadの新設定による。成功ログインは本人確定後の固定設定を適用できる。本人未特定の認証エラーや早期制限はヘッダーを基準とする。

Laravel標準のリクエスト単位localeと`backend/lang/ja/`・`en/`のPHP辞書を使用する。`auth`・`settings`・`validation`・`errors`等へ整理し、処理間でlocaleを持ち越さない。認証前の制限・例外にも対応し、認証後に本人固定設定を適用する。早期メンテナンス例外はDB参照せずヘッダー判定とする。

対象APIは、`/auth/*`の既存全経路、家族取得／更新、メンバー一覧・追加・編集・利用状態・パスワード再設定、カテゴリCRUD、セキュリティ通知の取得／既読。これらから使う独自検証ルール・共通認可・例外応答も含む。活動・画像・いいね・リワードの固有業務メッセージは後続フェーズ。ただし共通例外処理を経由する応答は全APIで日英化される。

`message`・`errors`本文を処理分岐に使わない。既存の`maintenance`等のcodeは保持し、対象内で本文依存が見つかった分岐には安定したcodeを追加し、OpenAPIに列挙する。HTTPステータスと検証フィールドで判断できる箇所に不要な独自codeを増やさない。業務ID・JSONキー・権限・レート制限・Retry-Afterは変更しない。

動的な対象応答は`Content-Language: ja | en`を返す。既存の`Vary`を保持したまま`Accept-Language`を追加し、本人設定がヘッダーより優先される認証応答は共有キャッシュ禁止とする。ヘッダーによるキャッシュ分離だけで本人情報を共有可能とは扱わない。

## 10. 辞書品質・管理

### 言語追加への備え

対応言語のコード・自称・Intl表示ロケール・翻訳基盤用ロケールは各基盤の言語定義へ集約し、選択肢・許可値・自動判定はそこから導出する。画面ごとの`ja / en`二択分岐や、日本語以外を無条件に英語辞書へ固定する処理を散在させない。未対応言語の既定フォールバックは英語のまま維持する。

将来の追加手順は、言語定義の追加、同じキー・パラメータを持つ辞書の追加、API契約の許可値更新、整合検査・表示レビューとする。フロント／バックの配布構成を維持して定義を管理し、検査で両者の対応言語不一致を検出する。日英のキー比較に固定せず、登録された全言語を検査する。静的併記の対象言語は日英として別に明示し、第三言語の追加だけで静的画面が過密にならないようにする。

右から左への表示や第三言語の翻訳自体は今回の受入範囲外とし、追加時に必要なUIレビューを行う。

フロントとバックは別辞書とし、共通用語と意味を揃える。全体の共通カタログ／adapterは後続版。今回の新規キーには日英を同時追加する。

CIで次を検査する：日英のキー集合一致、空文字なし、名前付きパラメータ集合一致、参照キーの存在、静的資産の生成差分なし。バック固有の`:name`とVueの`{name}`を同じ構文として検査しない。複数形は各基盤の規則で確認し、英語の単数・複数を検証する。

対象ファイルの日本語直書き・英語直書きを棚卸しし、利用者データ・ブランド・ログ等の除外理由をレビューする。機械検査だけで文脈・翻訳漏れの合格を判断しない。対象外画面から共通部品への引数として渡される固有文言は後続移行対象として区別する。

## 16. 言語追加の手順

1. `frontend/shared/utils/locale.ts`の`uiLocales`と`backend/config/i18n.php`へ同じ対応言語を追加する。外部の言語コードとLaravel辞書ディレクトリ名が異なる場合は`translation`で対応付ける。未知の言語のfallbackは英語を維持する。
2. `frontend/i18n/locales/<code>.json`を追加し、`frontend/i18n/i18n.config.ts`へ静的importと`messages`の登録を追加する。登録漏れは`UiLocale`に対する型検査で検出する。`backend/lang/<translation>/`へ同じ意味キー・パラメータのPHP辞書を追加する。登録言語のバック辞書自体が存在しない場合も整合検査で拒否する。既存の日本語本文や他言語の文言をキーにしない。
3. OpenAPIの`ui_locale`許可値を更新する。フロントの型・選択肢・自動判定とバックの許可値は言語定義から導出されるため、各画面やControllerへ個別の言語分岐を追加する必要はない。
4. `pnpm i18n:check`・Lint・型チェック・対象テスト・静的ビルドを実行し、語順・複数形・ARIA・長文・必要な書字方向をレビューする。追加言語を登録した状態でのAPI判定・保存は、地域付きコードのテストでも検査する。
