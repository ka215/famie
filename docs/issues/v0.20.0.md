## 2. 現行実装と調査の境界

- `frontend/app/pages/register.vue`は家族名・親のアカウント情報を送信し、同意欄を持たない。`useAuth.ts`から`POST /auth/register`を呼ぶ。
- `AuthController::register`は家族・ユーザー・所属・初期カテゴリをトランザクションで作成する。同意検証・履歴保存はない。発行トークンの有効期限は30日。
- `useAuth.ts`は`auth_token` Cookieを30日・Path `/`・SameSite Lax・本番Secureで保存する。JavaScriptから扱う現行認証方式であり、HttpOnlyとは記載しない。
- `auth.global.ts`の公開パスはログイン・登録・メール認証等に限定される。ポリシー閲覧は新たな公開例外が必要。現状は公開ページでもAPI状態確認が走る。
- 言語は`famie.uiLocale.guest`、テーマは`famie-theme`をlocalStorageに保存する。`theme.js`は初期表示時にも値を保存するため、「設定操作後だけ保存」とは断定できない。
- `nuxt.config.ts`はSPA・静的生成、PWA自動更新、静的資産のプリキャッシュ、API GETのNetworkOnlyを設定している。通常のAPI応答をオフライン保存する設計ではない。
- v0.19.0以降のアプリログ14日・監視履歴30日は既存方針。scheduler診断、提供元アクセスログ、DB・画像backup、通知メールは別途区分する。

上記はリポジトリ確認結果であり、商用環境の全Cookie・全送信先の実測完了を意味しない。先行調査の確定資料は今回の検索では特定できていないため、本文を推測で補わない。

## 4. R01：文書の管理・公開

### 4.1 本文の必須項目

| 文書 | 記載内容 |
| --- | --- |
| 利用規約 | 運営主体、対象者・保護者の責任、家族と権限、アカウント管理、禁止事項、投稿・画像の権利、停止・終了、変更・通知、責任範囲、問い合わせ、準拠法等 |
| プライバシー | 取得項目・目的、任意／必須、家族内の閲覧範囲、委託・第三者提供・国外取扱い、ログ・監視・メール、保存・削除・backup、開示等の窓口、子どもの情報、変更通知 |
| Cookie等 | Cookie・localStorage・Service Worker／Cache Storageの一覧、目的・期間・送信先、必須／選択、設定・拒否・撤回・削除の方法、削除に伴う再ログイン等 |

活動本文・画像・メールアドレス等の収集を正確に記載し、監視ログに本文を残さない方針と区別する。現行仕様にない輸出・完全即時削除・常時監視などを約束しない。削除操作とbackupからの消滅時期、運用点検の既知制約を混同しない。

### 4.2 ソースと文書識別

- 提案配置は`frontend/content/legal/{document}/{version}/{locale}.md`。documentは`terms`・`privacy`・`cookies`、localeは`ja`・`en`。アプリ版と独立した不変の文書版を付ける。
- メタデータに文書ID・版・言語・施行日・公開日・再同意要否・本文SHA256を持たせる。施行日は本文確定後に設定し、本書作成日を自動採用しない。
- 同じ版の日英本文を対応付け、片言語不足・版重複・不正リンク・メタデータ不足はビルドを失敗させる。公開済みの版は上書きせず、意味を変えない修正でも新しい版を作る。
- MarkdownからHTMLへビルド時に変換し、本文HTMLとマニフェストを生成する。raw HTML・実行コード・危険なURLを許可しない。実行時に外部サイトから本文を取得しない。
- 現行にMarkdown処理の直接依存は確認できないため、導入が必要なら保守状況・ライセンス・監査を確認して最小限に追加する。既存build／generateへ前処理を組み込み、独立手順の実行忘れを防ぐ。

### 4.3 画面・導線

- 通常ページで表示し、iframeは採用しない。提案URLは`/legal/terms`・`/legal/privacy`・`/legal/cookies`、版・言語を固定した旧版URLも生成する。直リンク・リロード・末尾スラッシュに対応する。
- ログイン・登録画面と、親／一般メンバー共通の設定画面から3文書へ到達できる。公開ページはトークンの有無・期限切れ・同意状態・API停止で閲覧を妨げない。
- `auth.global.ts`に明示した法務ページだけを公開し、この範囲ではAPIのstatus／me確認を必須にしない。任意パス全体を公開しない。
- 日英切替、タイトル、版、施行日、見出し、戻る操作を設ける。320px・ライト／ダーク・キーボード・スクリーンリーダーに対応する。
- 登録途中の閲覧で入力を消さない。別タブ等の導線は挙動を明示し、パスワードをlocalStorageへ保存しない。
- 閲覧と同意は別操作。最下部へのスクロールやリンクを開いたことを同意の証拠にしない。

## 5. 保存・送信の棚卸し

R01で次の表を実測に基づき完成させ、本文とR04の判断根拠にする。秘密値や実利用者データは記録しない。

| 対象 | 現時点の把握 | 追加確認 |
| --- | --- | --- |
| 認証Cookie | `auth_token`、最大30日、同一originのAPI認証 | 実際のDomain・属性・失効／ログアウト時削除、他のSet-Cookie |
| 言語・テーマ | localStorage、明示TTLなし | 自動保存と利用者選択の区別、同意要否、削除時の既定値 |
| PWA | 静的資産のプリキャッシュ・旧キャッシュ整理 | 保存対象・更新時削除・ブラウザ保持、同意要否、本文旧版の扱い |
| DB・画像 | アカウント・家族・活動・いいね・リワード・認証関連 | 保存場所、アクセス者、画像メタデータ、無効化と削除の違い |
| ログ・監視 | アプリ14日・監視30日、scheduler診断は別区分 | IP等の実項目、提供元ログの期間、閲覧権限、削除の実行結果 |
| backup・削除待ち | DB／画像backupと日次画像削除あり | 世代・期限・復元時の削除再適用、提供元backupの制御範囲 |
| メール | 認証・セキュリティ・運用通知 | SMTP提供元・送信項目・保管地域・メールボックスと配送ログの期間 |
| 外部通信 | リポジトリ検索だけでは全送信先を確定できない | 未ログイン／登録／設定／画像／PWA更新のNetwork、CDN・フォント・解析・埋込・提供元機能 |

商用とステージングを区別し、同意前・拒否後・撤回後・ストレージ利用不可・新規タブ／再訪で確認する。計測ツール自体の送信をアプリの送信と混同しない。新しい未分類処理を追加した場合も再棚卸しする。

## 6. R02：登録同意とサーバー契約案

### 6.1 公開マニフェスト

`GET /api/v1/legal/documents`を未認証で取得可能にし、施行中の文書ID・版・日英文書URL・ハッシュ・施行日・必要な操作を返す案とする。本文生成物とAPI設定は同じマニフェストから生成し、別々の手編集による版ずれを防ぐ。

画面が取得できない場合は登録送信を止め、再試行を案内する。文書の閲覧自体はビルド済みページで継続できる。APIに未公開／未施行の本文版を先行して要求させない。

### 6.2 登録ペイロード

既存`POST /api/v1/auth/register`の項目に以下を追加する案とする。例の版は仮値。

```json
{
  "legal": {
    "terms": { "version": "2026-11-example", "locale": "ja", "accepted": true },
    "privacy": { "version": "2026-11-example", "locale": "ja", "acknowledged": true }
  }
}
```

- 規約同意・プライバシー確認を別のラベルで表示し、チェックは初期false。Cookieの任意処理同意を登録必須項目へ混ぜない。
- サーバーで厳密なboolean、対応言語、必要文書と施行中版を検証する。欠落・false・型不正・未知文書は422。クライアント指定の日時・ユーザーID・代理者ID・本文ハッシュは採用しない。
- 正しい形式でも現行版が変わった場合は409と機械判定用`legal_version_changed`・最新メタデータを返す。再読込と再確認を求め、勝手に新版へ同意させない。入力保持を行い、変更した文書のチェックを解除する。
- 同意検証失敗ではユーザー・家族・所属・カテゴリ・トークン・履歴を作らない。家族等の作成と履歴保存を同一トランザクションに含め、保存失敗時は全体をロールバックする。
- 既存の登録レート制限・禁止名・パスワード・家族作成ルールを維持する。追加したlegal構造以外の権限指定を受け付けない。

### 6.3 記録モデル案

`legal_acceptances`を新設し、規約同意とプライバシー確認をイベントとして記録する。

| 項目 | 内容 |
| --- | --- |
| `id` | 履歴ID |
| `actor_user_id` | 実際に操作した認証ユーザー。登録では作成した親本人 |
| `subject_user_id` | 対象者。本人／代理を区別する |
| `group_id` | 代理確認の所属文脈。本人の契約同意のキーにはしない |
| `document_id`, `document_version`, `document_sha256` | サーバーが照合した文書・不変の本文識別子 |
| `locale`, `action`, `source` | 閲覧言語、`accept`／`acknowledge`、登録／既存確認／メンバー作成等 |
| `recorded_at` | サーバーのUTC日時。表示時に変換 |

同一actor・subject・文書・版・操作の重複を一意制約で防ぎ、再送は既存結果を返す。IP・User-Agentは同意履歴の必須保存項目にしない。代理履歴を本人同意へ読み替えず、認証ユーザーと所属・権限からactor／subjectを決定する。

既存ユーザーへ過去日時の履歴を一括投入しない。通常APIから履歴を更新・削除できないようにし、本人には自分の状態だけ返す。他者・他家族の履歴一覧を追加しない。アカウント削除時の保持／匿名化／削除はP05で期限と根拠を確定し、無期限保持や外部キーの自動cascadeを先に決めない。

## 7. R03：既存利用者・メンバー・改定

### 7.1 状態とAPI

- `GET /auth/me`等の共通ユーザー型に`legal_status`を追加し、`current`・`required`・`guardian_required`と対象文書版を返す案とする。古いアプリでも既存フィールドを壊さない追加とする。
- `POST /api/v1/auth/legal-acceptances`を認証必須で追加。登録と同じ検証・409／422契約で履歴を保存する。対象ユーザーIDを自由入力させない。
- 本人の同意はユーザー単位で保持し、家族切替だけで再同意させない。代理確認は所属文脈を分ける。ログアウト・アカウント切替時は状態を破棄し、遅い応答で別ユーザーへ反映しない。

### 7.2 提示と利用制限の案

- 既存の親には次回ログイン／利用再開時に対象文書と変更概要を提示する。移行の猶予期間、猶予中に許可する操作はP04・P07で確定する。
- 施行後に同意が必要な対象者には確認画面へ誘導し、対応する保護APIでも検証する。フロントだけのリダイレクトで強制を完了しない。
- 制限対象のAPIは403と`legal_acceptance_required`を返す案。文書閲覧・同意登録・本人状態取得・ログアウト・問い合わせ／削除相談導線は利用可能とし、リダイレクトループを防ぐ。
- この制御は対象者と対象処理に限定する。Cookie拒否だけでログインを禁じる、全利用者を一律に停止するミドルウェアは設けない。
- 同意しない選択では記録を作らず、ログアウトと問い合わせを案内する。拒否を退会・投稿削除として扱わない。

### 7.3 親によるメンバー作成・子どもの利用

- メンバー作成画面に文書リンクと、作成者の説明・権限に関する確認を設ける案。作成APIでも確認し、メンバー作成と代理確認履歴を同一トランザクションにする。
- 成人本人の同意が必要なケースは初回利用時に本人から取得する。親による作成事実やfamilyのadmin属性を、本人の同意・法的親権の証拠として保存しない。
- 子どもには理解しやすい利用説明を提供し、保護者対応が必要な場合は`guardian_required`として案内する。保護者未確認時の利用範囲はP02・P04で決め、子どもへ成人用チェックを強制しない。
- 既存一般メンバーは年齢不明であり、一律に成人・子どもへ分類しない。分類・保護者確認をどの操作で取得するかを実装前に確定する。

### 7.4 改定・古いPWA

- 文書版と再同意の必要版を分け、非重要改定だけで毎回ブロックしない。重要改定は告知・施行日・再同意対象を運営が指定する。
- 旧PWAが古い本文・契約を送ってもAPIで検出し、更新・再確認を案内する。古い版への確認を施行中版への同意として補完しない。
- 固定した旧版URLは後から同じ内容を参照できる。オフライン閲覧時はビルド収録版であることを示し、最新確認・同意送信には通信を必要とする。未送信を同意済みにしない。

## 8. R04：Cookie・端末内保存の制御

### 8.1 必要性の判断

棚卸しとP01・P06の判断で、各処理を必須・利用者が求める設定・非必須へ分類する。認証に必要な保存と解析等の任意処理を分ける。Cookie以外のlocalStorage・キャッシュ・第三者への通信も調査対象とする。

必須処理のみと確認できた場合は、共通の説明導線とCookieポリシーを提供し、意味のない「すべて同意」を要求しない。この分岐も1-4の対応結果として判断理由と実測を記録する。将来の非必須SDK用の空のCMPは作らない。

### 8.2 非必須処理に同意が必要な場合

- ログインに依存しない共通UIを用意し、未選択のまま対象処理を開始しない。初回起動・ログイン前・PWA・ページ再訪でも適用する。
- 「許可」「拒否」「設定」を同程度の操作で選べるようにし、目的単位で選択できる。閉じる・スクロール・無操作を許可とみなさない。
- Cookieページと設定からいつでも変更・撤回できる。撤回時は次回読込を待たず新しい送信を止め、管理可能な対象保存を削除する。過去に送信済みのデータを端末操作だけで削除できるとは案内しない。
- 保存には選択内容・選択日時・ポリシー版・期限を含める。キー・有効期間は対象分類と合わせてR04で確定する。ログインをまたいでも端末の拒否を上書きしない。
- 不正値・期限切れ・版の非互換・保存不可では未選択へ戻し、非必須処理を停止する。別タブでの撤回にも追随する。
- テーマ・言語が事前同意の対象となる場合は初期自動書込も止め、未許可時はメモリ内／ブラウザ既定値で動作させる。表示後のバナーだけで対応済みとしない。
- 任意処理を止めても登録・ログイン・文書閲覧・家族の基本機能を利用できる。必須認証Cookieを消す操作はログアウトとして別途説明する。

- vaultの上書き・不正パス・リンクを拒否し、失敗時の証跡保全、ledgerの確定後再試行、保全ホールド、cleanupの進捗・スナップショット消去を補強した。DB変更を伴う検証はユーザー承認済みの隔離先で実施した。
- モーダルを閉じたときの準備操作取消APIを追加した。同じ実行者の未確定操作は安全条件を満たす場合だけ再準備でき、他者の操作・保全・処理証跡がある場合は拒否する。確認期限は15分であり、閉じた後に一律15分待たせる動作を解消した。
- 無効化済みメンバーの空表示、開閉、役割バッジ、復元／代表者専用削除ボタンを整理した。確定時エラーをパスワード欄と実行ボタンの間へ移し、表示位置へスクロールする。状況確認はログイン画面から再表示でき、受付番号と確認コードで確定から30日間照会できる。戻るリンク・区切り線・言語切り替えの調整もユーザー確認済み。
- 隔離SQLite重点試験36件・317 assertions、専用PostgreSQL試験19件・239 assertions、実API E2E4件が合格。最終UI版はDBを使用しないChromium／iPhone WebKitの画面試験16件、Lint・型チェックに合格した。先行して日英539メッセージ、OpenAPI53操作、Pintも検証済み。自動ブラウザ試験を実機Safari／PWA受入とは区別する。

次はコミット・dev向けPR・CIを行い、固定候補のステージング受入を準備する。ステージングDBの移行は対象とバックアップ・保全手順を明示して承認を得てから実行する。F03および商用公開は未完了。事故後の空schema、保全dump、ローカルSQLite試験生成物はこの工程では削除しない。
