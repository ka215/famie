## 3. 画面修正の詳細仕様案

### R01：閲覧専用欄の配色

- ダーク／ライト双方でカテゴリ・実施日・時刻・活動内容・補足メモを判読可能にする。空欄、複数行、長文も対象とする。
- 入力可能／閲覧専用それぞれの背景色・文字色・枠線を明示する。ダークの閲覧専用欄には暗色背景と明色文字を組み合わせる。
- WebKit固有のdisabled文字色・不透明度も確認する。単にdisabledを外す修正は行わない。
- 他者の記録には更新・削除・画像変更UIを表示せず、APIの所有者制約も維持する。本人の編集・保存機能を維持する。
- 影響範囲はまず活動詳細に限定し、全画面のdisabled部品の配色を一括変更しない。

### R02・R04：戻り先と復帰条件

必須要件は、ギャラリー経由では「← ギャラリーへ」、タイムライン経由では「← タイムラインへ」を表示し、元の一覧条件を維持すること。固定フッター経由では規定値への初期化を許容する。

以下はD01・D02承認済みの確定仕様。

| 操作 | 移動先・復元内容 |
| --- | --- |
| ギャラリーの「アクティビティを見る」→詳細の上部リンク | ギャラリー。期間・投稿者・カテゴリ・読込済み範囲・元画像カード位置を復元 |
| タイムラインの編集アイコン→詳細の上部リンク | タイムライン。期間・投稿者・カテゴリ・ページ・月／選択日・位置を復元 |
| 詳細で更新成功 | 入ってきた一覧へ同じ条件で戻る。最新データを取得する |
| 詳細で削除成功 | 入ってきた一覧へ同じ条件で戻る。削除カード位置に近い位置へ復元 |
| 詳細で更新・削除失敗 | 詳細に留まり、入力・復帰情報を維持してエラーを表示 |
| 詳細でブラウザの戻る／端末の戻る操作 | 対応する一覧の履歴があれば同じ条件・位置へ復元 |
| 詳細から固定フッターのタイムライン／ギャラリー | 移動先の規定値で新規表示。過去の復帰情報を適用しない |
| 詳細URLへの直接アクセス／復帰情報欠損 | 上部リンクは「← タイムラインへ」。タイムラインの規定値へ移動 |

規定値は現行と同じ：タイムラインは今週・当日・本人・全カテゴリ、ギャラリーは当週・全員・全カテゴリ。端末のロケールによる週開始日など、既存の期間計算は変更しない。

#### 状態の保持方式と復元手順

1. 一覧から詳細へ進む直前に、一覧種別とその表示状態を保存する。詳細へ渡す遷移元は`timeline`／`gallery`の許可値のみとし、任意URLへの戻り先指定は受け付けない。
2. 保存単位はログインユーザー・家族・ブラウザタブ・一覧履歴。タイムラインとギャラリーは別管理とし、別ユーザー・家族や別タブへ持ち越さない。
3. タイムラインは期間種別、開始・終了日、表示月、選択日、月カレンダー／日別の別、投稿者、カテゴリ、ページを保存する。ギャラリーは期間種別、基準日、開始・終了日、投稿者、カテゴリ、読込ページを保存する。
4. 位置は元カードのID、スクロール領域内の相対位置、補助的なscrollTopを保存する。カードが消えた場合は近い位置へ、該当なしなら一覧先頭へ戻す。
5. 復帰時は条件を先に復元してAPIを再取得する。画像Blob、認証トークン、活動本文は復帰用ストレージに保存しない。
6. ギャラリーは元カードまでのページを必要な分だけ順番に再取得する。復元処理中のIntersectionObserverによる重複要求を防ぐ。画像サイズを確保し、DOM反映後に`.app-scroll-area`の位置を復元する。
7. 変更により元の投稿がフィルター対象外になった場合も条件は維持する。ページが末尾を超えた場合は有効な最終ページへ補正する。無効になった投稿者・カテゴリは利用可能な規定選択へ補正し、他者のデータを復帰キャッシュから表示しない。
8. 再取得失敗時はエラーと再試行を表示し、復帰条件を保持する。認証失敗・ログアウト・家族変更時は保存情報を破棄する。

保持はSPA内の一時状態を基本とし、履歴entryと復帰情報を結び付ける。ページ全体のKeepAliveによる無期限保持やlocalStorageへの永続保存は初版では行わない。リロード・新規タブ・ブラウザ再起動後の復元は保証しない。復帰不能でも画面の閲覧・規定値での移動は可能とする。

### R03：タイムラインカードの操作領域

- `.edit-link::after`によるカード全面のリンク領域を除去し、編集アイコンの44px以上の操作領域だけで詳細編集へ遷移する。
- 本人・他者とも、カード背景、本文、メモ、日時、カテゴリ、投稿者名をクリックしても画面遷移しない。不要なリンク風hover表現も整理する。
- 添付画像は既存の`ActivityImageView`で拡大する。拡大・閉じる時に編集へ遷移せず、条件・ページ・スクロール位置を維持する。
- 他者の編集アイコンは引き続き非表示。いいね操作は独立した操作として維持する。
- キーボードでは編集リンク・画像ボタン・いいねボタンへ個別に到達でき、画像モーダルを閉じると元の画像ボタンへフォーカスが戻る。

- `docs/api/openapi.yaml`：OpenAPI 3.1.1による現行API契約の正本。まず単一ファイルで管理する。
- `docs/api/README.md`：対象版、公開パス、検証コマンド、実装との照合方法、更新責任を記載する。
- `docs/README.md`に入口を追加し、旧`docs/reference/backend/`の実装例と区別する。正式要件との関係は、現行APIの具体的IFを補完する文書とする。
- 契約は実際のルート・Controller／Request／Resource・Service・Featureテスト・フロントエンド型から整理する。草案や古いコード例をそのまま契約へ転記しない。
- OAS版3.1.1を採用するが「最新版」とする意味ではない。機械検証可能なスキーマと既存ツールとの互換性を優先する。[公式仕様](https://spec.openapis.org/oas/v3.1.1.html)を基準とする。

### 必須記載事項

| 分類 | 記載内容 |

| 認証 | Bearer認証、認証不要操作、active所属・admin・本人制約、家族境界。Cookie認証方式として誤記しない |
| 認証・アカウント | status、ログイン・ログアウト・登録・ID空き確認、本人情報・パスワード変更、メール登録／再送／取消／確認、パスワード再設定 |
| 家族・メンバー | 家族情報取得／変更、メンバー作成・編集・無効化・復元、無効一覧、人数制限 |
| カテゴリ | 一覧・作成・変更・削除、参照中カテゴリの削除禁止 |
| 活動・画像 | 一覧・件数・詳細・作成・更新・削除、ギャラリー、認証付き画像バイナリ取得 |
| いいね | 本文なしのPUT／DELETE、冪等な付与・解除、件数・本人状態・操作可否の出力、再試行と競合の扱い |
| リワード | 管理一覧・条件／進捗・作成／更新／状態変更／削除・期間準備・獲得履歴・通知取得と既読確定 |
| データ型 | 必須／nullable、enum、ID、日付・時刻・タイムゾーン、文字数・値域、配列上限、画像寸法・容量、revision |
| 入出力 | query／path／header／body、JSON／multipart、画像付き更新のPOST＋`_method=PUT`、画像レスポンスのMIME |
| 応答 | 実際の成功status、dataラップ有無、ページング形式、共通エラーと機能固有エラー、Retry-After等 |
| 横断制御 | 401／403／404／409／422／429／503等の適用条件、IP制限、メンテナンス、レート制限、通知取得の副作用 |

すべての操作に任意の成功・エラーコードを一律列挙するのではなく、実装が返すものを記載する。仕様と実装の不一致は一覧化し、この文書化のためだけにAPIの挙動を変更しない。実データ、トークン、秘密情報は例に含めない。

### 保守と検証

- API変更時は実装・Featureテスト・OpenAPIを同じPRで更新する。
- YAMLとしての構文検査に加え、OpenAPI検証器による`$ref`・型・operationId等の検査と、ルートのmethod/path網羅の照合を行う。YAML操作には`yq`を利用する。
- Laravel側の`/v1`と公開側の`/api/v1`を正規化して照合する。HEADなど自動派生methodと`_method`による公開形を区別する。
- 構文検査だけではレスポンス一致は保証されない。代表的な成功／入力不正／認証・権限／競合／バイナリ応答を既存Featureテストと照合する。
- 開発用検証器・追加依存・CI検査の追加はD03で承認済み。具体的なツールと接続方法は既存スクリプトと利用可能ツールを確認して決める。Swagger UIの公開、SDK生成、実行時入力検証の置換は含めない。

## 5. R06：専用ドメイン移管の設計要件

### 今回の成果物

`docs/operations/runbooks/domain-migration-plan.md`（仮）へ、現状構成、採用構成、事前確認、設定差分、切替手順、確認表、切り戻し、旧ドメインの保持方針をまとめる。運用索引にリンクを追加する。v0.15.1では設計のみとし、ドメイン接続や環境設定・スクリプトの切替は実施しない。

### 採用構成（D04承認済み）

- 新しい正規URLは`https://famie.co/`。同一CoreServer V1、既存`~/famie/backend`、DB・DB user・schema `ka2_famie`、storage、APP_KEYを継続使用する。
- ステージングは`stg-famie.ka2.org`と`ka2_famiestg`を維持する。IP制限・メール送信先制限も変更しない。
- 採用方針は、新ドメインのサイトを既存公開ディレクトリ`~/public_html/famie.ka2.org`へ割り当て、ファイル移動を避ける方式。ただし現契約・管理画面でのカスタム公開先指定可否、旧Hostだけの転送、SSL更新、API symlinkを事前に確認する必要がある。現状では利用可能と断定しない。
- この方式が利用できない場合は`~/public_html/famie.co`を公開先にし、フロント資材とAPI参照だけを移す代替案を設計する。バックエンド・DB・画像実体の複製は行わない。公開ディレクトリのsymlink利用もホスト制約を確認してから採否を決める。
- 配置スクリプトではURLと物理公開先を分離して扱う。新旧双方へ同時に書き込む二重運用を避ける。

### 移管時に必要な変更の棚卸し

| 領域 | 設計・確認内容 |
| --- | --- |
| DNS・TLS | 新ドメインの管理先、A／AAAAの現状、CoreServerのサイト割当、無料SSL発行／更新、旧ドメインの証明書維持。IP値は調査時に確定する |
| Web公開 | 正規Host、HTTP→HTTPS、旧Host→新Host、`api` symlink、SPA fallback、MIME、maintenance、`.htaccess`のHost条件 |
| Laravel | `APP_URL`、`FAMIE_FRONTEND_URL`、`CORS_ALLOWED_ORIGINS`、必要に応じCookie／Sanctum設定、config cacheと生成URL。Bearer方式を前提に不要な設定追加をしない |
| フロント | `/api/v1`の同一origin相対参照、manifest・SW・画像取得、絶対URLの残存、テーマ等の端末保存情報 |
| 配置・復旧 | `deploy.sh`、`server/deploy-artifact.sh`、環境ガード、配置先テスト、workflowの公開URL、スモーク検査、バックアップ・rollbackが参照する旧URL／公開先 |
| メール | 認証・再設定リンクの新URL、切替前に発行済みのリンク、送信元ドメインを変更するか、変更する場合のSPF／DKIM／DMARCと実配送 |
| 利用者 | 新ドメインでの再ログイン、PWAの新規ホーム追加、テーマ等の再設定、旧PWAからの移行案内 |
| ドキュメント | 現行運用手順・OpenAPIのservers・サービス案内を更新。過去のリリース記録にある旧URLは履歴として維持 |

新旧は異なるorigin／ドメインなので、Cookie、ブラウザ保存情報、Service Workerの状態を自動で引き継ぐ前提にしない。新側の再ログイン・PWA再追加を基本とし、認証トークンをURLで受け渡す移行方式は採用しない。[Cookieの適用範囲](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)と[Service Workerのorigin制約](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)を踏まえた承認済み方針。

### 切替手順の設計骨子

1. 本番のactiveグループ集合がID 1・2の2件のみであるか読取専用で確認し、結果・確認日時を記録する。この条件が成立する場合はユーザー家族のみの利用として、外部顧客向けの移行条件・告知待機期間を追加せず移管できる。別のactiveグループが存在する場合はこの前提を適用せず、利用状況をユーザーへ連携する。続いて現行構成・設定・証明書・DNS・SWの記録を取り、バックアップと復旧点を用意する。DNSや秘密の設定値を公開文書へ転載しない。
2. 新ドメインのDNS、サイト設定、TLSを準備する。CoreServer公式では無料SSLに適切なAレコードと名前解決が必要とされるため、DNSと証明書の順序を確認する。[公式手順](https://help.coreserver.jp/manual/v1/security-free-ssl/)
3. 正規URL、物理公開先、配置・復旧先の対応を確定し、後続版の変更としてテストする。ステージングの設定が変わらないことも確認する。
4. 切替前は新側を制限し、一般利用者が新旧両方で操作しない状態で検証する。同一DBを使う新側の操作テストも本番データへの更新となるため、専用の確認用アカウント・記録で行う。
5. 切替時に必要な短時間のメンテナンス、正規URL設定反映、公開先有効化、旧側の転送または案内を順序化する。
6. HTTP・API・画像・認証・メールリンク・PWA・リワードを確認する。旧側SWがキャッシュを返す場合、サーバー転送だけで新側へ移行できないケースも確認し、旧PWA用の移行案内を設計する。
7. 初期はキャッシュされにくい一時転送を検討し、安定後にGET／HEADの恒久転送へ進む。旧APIへのPOST／PUT／DELETE等を新ドメインへ無条件転送せず、旧クライアントの書込み停止・案内応答を定義する。具体的なHTTPコードは後続版で確定する。
8. 旧メールリンクのpath・query・fragmentが維持されることを実ブラウザで確認する。fragmentを含む認証リンクはサーバー側のpath転送検査だけで合格にしない。
9. 不合格時は新側の受付を止め、URL設定・Host転送・公開先・配置先の対応を旧側へ戻す。ドメイン切替だけならDB復元は行わず、切替後の投稿・画像・獲得履歴を保持する。恒久転送キャッシュや旧SWにより復帰が遅れる場合も手順に含める。

本番DNSや管理画面の現状、旧ドメインからのアクセス実態、旧PWAのキャッシュ挙動は未調査。サーバーの実変更前に、後続版で具体的な切替日時・構成・利用者案内を合意する。

### 移管に関する追加合意と確認範囲

- ユーザーより「本番のactiveグループがID 1・2の2件であれば、自分の家族以外の利用者はいないため、顧客条件等の考慮は不要で移管してよい」との指示を受領した。

- 新ドメインのDNS管理サービス・CoreServerへの登録状況、具体的な切替日時・設定手順は移管計画で整理する。現在、詳細仕様Fixに必要な追加判断項目はない。
