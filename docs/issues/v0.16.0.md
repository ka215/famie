# v0.16.0 詳細仕様 — famie.coへの商用環境移管

作成日：2026-10-17。作業ブランチ：`feature/v0.16.0`。

状態：**現行0.15.2でfamie.coへの実切替・商用自動検査完了／ユーザー実機確認合格／0.16.0通常リリースは未実施**。本書を移管の詳細仕様・手順・検証状況の管理先とする。[v0.15.1の準備内容](v0.15.1.md)と[移管計画](../operations/runbooks/domain-migration-plan.md)を引き継ぎ、今回のユーザー指示による変更は本書を優先する。

## 1. 確定方針

- 正規URLは `https://famie.co`（wwwなし）。DNS・サイト・メールの初期設定とHTTPS公開はユーザー実施済み。実切替前に実応答を確認する。
- CoreServer V1では既存公開先への変更ができないため、新ドキュメントルート `~/public_html/famie.co` にフロントを配置する。このディレクトリ自体を旧公開先へのシンボリックリンクにはしない。
- `~/public_html/famie.ka2.org` の公開物は切り戻し用に保持する。移管完了後も旧URL・TLSを当面維持する。
- backend・storage・DBは既存のものを共有する。新側の `api` リンクだけを `~/famie/backend/public` に向ける構成とし、CoreServer上の動作を確認する。
- 商用・ステージングとも家族が管理・利用する2グループだけであることをユーザーが確認済み。外部顧客向けの条件確認・告知待機期間は不要。従来の「ID集合の再確認を移管の前提とする」条件を置き換える。
- **移管のためのメンテナンスは実施しない**。`artisan down`・公開側 `.maintenance` の作成を移管工程に含めない。家族内で切替時の操作を避けるよう連携し、旧APIの受付停止と新側の確認を順序立てる。
- 新側では再ログイン・PWA再追加を行う。Cookie・トークン・端末設定をドメイン間で自動移送しない。メール送信元は当初 `noreply@famie.ka2.org` を維持する。

## 4. 旧URLの動作仕様

- 旧Hostの `/api` と配下は全メソッドで移管案内JSON・HTTP 410、`Cache-Control: no-store` を返す。新ドメインへAPIリクエストや認証情報を転送しない。
- 旧Hostの画面GET/HEADは、新URLの同じpath/queryへ302で転送する。キャッシュを抑制し、恒久転送の導入は安定確認後に別途判断する。
- API以外の更新メソッドも自動転送せず410とする。新Hostでは旧側ルールが動作しないよう配置を分離する。
- 設定の適用順はAPI停止ルールを画面転送より優先する。旧側の既存APIリンクを残す場合も、Laravelへ到達せず410となることを実測する。
- 旧メールリンクのpath/query/fragmentが新側へ届くことをブラウザで確認する。fragmentはサーバーに送信されないため、HTTPヘッダー検査だけで合格にしない。実トークンは記録しない。
- 旧PWAはSWのキャッシュから旧画面を表示し得る。家族には通常ブラウザで新URLを開き、ログイン後にホーム追加し、旧アイコンを削除する手順を案内する。

上記は実装目標。CoreServer上のApache設定・APIリンクの処理順を確認し、適用可能な設定ファイルと実行コマンドを確定する。

## 5. 移管手順

1. **事前棚卸し**：新docrootの既存ファイル・`.htaccess`・apiリンク、旧側設定、PHP実行方式、権限、証明書、現行アプリ版、配布済み成果物のSHAを記録する。秘密値は記録しない。
2. **復旧準備**：新旧docrootの既存内容、旧側`.htaccess`、本番`.env`と設定キャッシュを非公開領域に保存する。既存手順でDBバックアップも確保するが、ドメイン切り戻しでは復元しない。バックアップのパスと取得日時を記録する。
3. **新側準備**：確認済みの同一成果物のフロントを新docrootへ配置し、既存backendへのapiリンクを作成する。サーバー固有設定を無断で上書きしない。準備中の書込み検証は家族の確認用データに限定する。
4. **切替前検査**：新側のTLS、直接URL、JS/CSSのMIME、SW・manifest、API到達性を確認する。正規URL変更前のため未合格となるメールリンク等は切替後に検証し、全項目合格と誤記しない。
5. **切替**：家族内へ操作切替を連携。旧APIに410応答を適用し、旧画面の302転送を有効化。本番APP_URL・FAMIE_FRONTEND_URL・CORSを新側へ変更し、設定キャッシュを再生成する。共有backendをdownにしない。設定更新に失敗した場合は直ちに旧側制御を戻す。
6. **切替後検査**：以下の受入表を実施。新側ログイン・既存データ・画像を先に確認し、その後に識別可能な確認用データで書込み・実配送を確認する。
7. **利用開始・記録**：家族の新PWA利用を確認する。実行日時、担当、成果物SHA、設定差分、確認結果、バックアップ場所を `docs/operations/change-log/` に記録する。旧公開物・URL・TLSを保持する。

移管コマンドの正確なパス・配置対象・設定差分は、CoreServerの現状共有後に追記する。上記を現状未確認のまま一括実行する手順とは扱わない。

## 6. 切り戻し

ログイン不能、API・画像の障害、参照DB不整合、転送ループ、設定更新失敗を切り戻し条件とする。

1. 新側APIの受付を停止する設定を適用し、新旧双方からの更新が重ならないようにする。メンテナンスページや `artisan down` は使わない。
2. 保存済みの旧URL・フロントURL・CORS設定へ戻し、設定キャッシュを再生成する。DB・storage・APP_KEYは維持する。
3. 旧側の410・302設定を解除し、保持した旧公開物とAPIリンクでログイン・画像・既存履歴を確認する。
4. 新側は旧URLへの一時案内／転送に切り替え、家族へ旧URLでの再ログインを連携する。新PWAは自動復帰しないためブラウザ利用を案内する。
5. 切替後に追加した投稿・画像・獲得履歴が残ることを確認し、実施結果を記録する。

成果物のアプリ版を戻す既存rollbackは、ドメイン切り戻しとは別操作。DB互換性ガードを維持し、旧成果物の復旧先も新商用docrootとなることを検証する。
