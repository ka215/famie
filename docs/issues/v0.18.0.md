## 4. R01 — 未確認ログイン警告

### 4.1 表示対象・操作

- 設定画面の家族メンバー一覧で、親本人宛てに未確認警告が残るメンバーの表示名の右横へ警告アイコンを表示する。
- `.tools/ka2_svg-icon-list.md`の`key-alert-outline`と同じpath／viewBoxを使用する。色は既存の警告系amberに合わせ、ライト／ダークの双方で識別できるようにする。
- アイコンは見た目約20px、操作領域は最小44px。SVG自体は装飾扱いとし、ボタンに「{表示名}の未確認ログイン警告を表示／Show unreviewed login alerts for {name}」相当の日英操作名を付ける。色だけで意味を伝えず、フォーカス表示を設ける。
- 親のみ表示し、一般メンバーにはアイコン・件数・通知取得操作を提供しない。親本人の行も他の対象者と同じ条件で扱う。
- 無効化済みメンバーの行を展開した場合も、未確認通知があれば表示する。無効化・名前変更・パスワード再設定を確認済み操作の代わりにはしない。
- アイコン押下で、そのメンバーの未確認通知のみを既存の警告モーダルに表示する。メンバー管理・パスワード再設定モーダルは同時に開かない。
- モーダル内は発生日時・通知時点の表示名／ログインID・個別の「確認済みにする」を維持する。現在のメンバー名と通知時点の名前が異なっても別人扱いしない。

### 4.2 閉じる・確認済み・更新

| 操作・状態 | 挙動 |
| --- | --- |
| 閉じる／Escape | モーダルを閉じるだけ。未確認・アイコンを維持 |
| 個別確認が成功 | その通知だけを除き、件数を再取得。同じ人に残件があればアイコンを残す |
| 該当者の全件確認済み | アイコンを消し、手動モーダルを閉じる。行が残っていれば元の操作位置付近へフォーカスを戻す |
| 他の親が確認 | 現在の親本人宛ての通知には影響しない |
| 同じ親の別端末で確認 | 次回の再取得で追従する。即時同期用のWebSocket等は追加しない |
| 新しい警告の到着 | 既存の自動通知方針を維持。手動表示中は別モーダルを重ねず状態を更新 |
| 手動モーダルを閉じた直後 | 同じ未確認内容を次の通常再取得だけで自動再表示しない。新しい通知は従来の自動通知対象 |
| アカウント・家族・役割変更／ログアウト | 状態・対象・エラー・遅延応答を破棄し、別利用者へ通知を引き継がない |

- 自動通知と手動再表示は同じ確認状態を使う。通知取得の定期タイマーを設定画面側で重複起動しない。
- 起動・画面遷移・focus・60秒周期の現行更新を基本とし、非表示タブで不要な周期取得をしない。手動表示時と確認成功後は再取得する。
- 取得中・確認処理中の二重操作を防ぐ。既に確認済み・対象変更等が起きている場合は再取得結果へ合わせる。
- 取得失敗を「未確認なし」と扱わない。同じ親・家族の直前の取得結果は保持し、設定画面や手動操作では再取得に失敗した旨と再試行を表示する。自動取得失敗で通常操作を妨げない。
- 確認API失敗時は通知・アイコンを維持する。古い取得応答で確認済み通知が復活したり、件数が別アカウントへ反映されたりしない。
- 401・403・メンテナンスは既存の認証／メンテナンス制御に従い、アクセス不能な通知を表示し続けない。

### 4.3 API仕様（P01・承認済み）

既存`GET /v1/groups/{group}/security-alerts`を拡張する。新しい別エンドポイントやDB列を増やすことは前提としない。

| 項目 | 契約案 |
| --- | --- |
| 認証・認可 | 現行どおり親本人宛て・同一家族のみ。一般メンバーは403、別家族は既存の404方針 |
| 絞り込み | 任意の`membership_id`（正の整数）。指定時は同一家族内の該当メンバーだけを取得。無効化済みの所属も対象。別家族・存在しない所属は404、不正形式は422 |
| data | 現行の通知項目・形式を維持。絞り込み後の未確認を新しい順に最大20件 |
| meta.unread_total | 絞り込み後の全未確認件数。未指定なら親本人宛ての家族全体の件数 |
| meta.unread_by_member | 絞り込みの有無によらず、親本人宛て・当該家族の全未確認を`membership_id`単位に集計した`{membership_id, count}`の配列。0件の所属は省略 |
| meta.limit／has_more | limitは20、has_moreは絞り込み後の全件数が返却件数より多い場合true |

- 集計はdataの20件から計算せず、対象となる全未確認通知をDBで集計する。家族をまたぐ件数・他の親宛て件数は含めない。
- 複数通知があるメンバーもアイコンは1個とし、残件の有無で消去を判断する。初版で件数バッジは追加しない。
- 20件超の場合はモーダルに「未確認N件のうち最新20件を表示」相当を出す。確認成功後に再取得し、古い未確認を補充する。確認せず古い通知へ任意移動するページングUIは今回追加しない。
- `membership_id`未指定の既存dataは互換を維持し、集計情報を追加する。OpenAPI・共有型・応答契約テストも実装時に更新する。
- `PUT .../security-alerts/{alert}/read`は本文なし・本人宛てのみの現行契約を維持し、一括確認は追加しない。
- 通知発生条件（24時間内の反復制限・重複抑止等）と親ごとの通知作成を変更しない。DBインデックス追加が必要になる場合は計測根拠と影響を別途連携する。

## 5. R02 — 活動詳細カードと編集

### 5.1 画面と遷移

既存の`/logs/{id}`を利用し、既定を閲覧カードとする。編集は`mode=edit`相当の明示モードで表し、新しい動的URL階層は増やさない。最終のクエリ名は実装時に既存規約と整合させる。

| 入口・操作 | 遷移先・結果 |
| --- | --- |
| ギャラリー「アクティビティを見る」 | 当該活動の詳細カード1件 |
| `/logs/{id}`の直リンク・旧ブックマーク | 詳細カード1件。本人でも自動でフォームにしない |
| タイムラインの本人用編集アイコン | 本人の編集フォームへ直接遷移 |
| 詳細カードの本人用編集ボタン | 同じ活動の編集フォーム |
| 編集の保存成功 | 最新の内容を再取得し、同じ活動の詳細カードへ戻る |
| 編集の取消・編集フォーム上部の戻る | 編集内容と未保存の画像操作を破棄し、詳細カードへ戻る。API更新は送らない |
| 削除成功 | 呼出元の一覧へ復帰。呼出元不明ならタイムライン |
| 詳細カードの「一覧へ戻る」 | 元のギャラリー／タイムラインの条件・ページ・位置へ復帰 |
| 他者の活動への編集モード直リンク | フォームを出さず詳細カードを表示し、URLを閲覧モードに正規化 |

- 詳細／編集モードの切替は同じ履歴項目を置き換える案とする。カード→編集→保存だけで履歴を増やさず、通常のブラウザ戻るは呼出元一覧へ戻る。直リンク時は通常のブラウザ履歴に従う。
- `back`キーはモード切替・保存・取消でも保持する。再読み込みや別タブでアプリ内の復帰情報を失った場合は、現在と同じくタイムラインを既定の戻り先にする。
- 一覧への明示的な戻りリンクと編集取消は別の操作として表示する。編集取消後に自動的にギャラリーへ飛ばさない。
- 戻る操作の矢印文字は指定SVGへ置き換える。閲覧カードから一覧へ戻る場合と、編集から詳細へ戻る場合は`chevron-left`、編集から一覧へ直接戻る場合は`chevron-double-left`を使う。履歴の件数ではなく表示モードで論理的な階層を判定する。日英ラベルから矢印文字を除き、装飾SVGは読み上げ対象外にする（2026-10-24追加指示）。
- 無効な表示モードは閲覧扱いとし、URLの値で編集権限を付与しない。既存の削除確認は維持し、新しい未保存離脱確認は追加しない。

### 5.2 詳細カードの表示

- タイムラインと同じカテゴリ・投稿者・実施日時・活動内容・メモ・画像・いいね・本人の編集操作を、共通カードで1件表示する。
- 一覧フィルター・ページング・登録ボタン等は詳細カードに付けない。読み込み中・取得失敗時に空のカードを実データのように表示しない。
- カテゴリ色と文字色、日英の日時・数値、本文／メモの改行・長文折返し、メモSVG・視覚非表示ラベルを維持する。活動内容やメンバー名等の利用者データを自動翻訳しない。
- 画像は既存ActivityImageViewの取得・拡大・閉じる・失敗表示を再利用する。画像のない活動、画像添付が現在無効でも既存画像がある活動を現行権限に沿って表示する。
- 他者の活動には編集不能な入力欄を並べず、カードのテキストとして表示する。「閲覧のみ」の末尾注記をスクロールしないと判別できない構成を解消する。
- 親でも他者の活動を編集・削除できない。一般メンバーも自分の活動だけ編集・削除できる。最終認可はサーバー側で継続する。

### 5.3 いいねと失敗時処理

- 他者のいいね可能な活動は、詳細カードでいいね付与・解除できる。自分の活動は受信数表示のみとし、自分へのいいねを許可しない。
- いいねの意味・API・リワード反映は変更しない。既存の楽観表示、処理中、未確定時の同じ操作への再試行、429とRetry-After、エラー表示を再利用する。
- 詳細から戻った一覧で、古い件数・選択状態に巻き戻らないよう、共有操作状態と一覧再取得の整合を維持する。
- 閲覧取得にも既存のread revisionとの整合を適用し、遅れて完了した古い取得応答で確定後のいいねを上書きしない。
- 同一操作の二重送信・アカウント切替後の応答混入を防ぐ。権限喪失や404は操作不能として扱い、別家族の存在を示す情報は追加しない。

### 5.4 編集・削除と一覧復帰

- 編集フォームの入力検証・画像選択／キャンセル・差し替え／削除・revisionによる409競合は維持する。エラー時は入力と選択画像を保持し、勝手に保存・再取得で上書きしない。
- 保存成功後の詳細カードには保存済みデータを表示する。再取得だけ失敗した場合は「保存失敗」と誤表示せず、更新後の表示取得失敗として再試行できるようにする。
- メンバー無効化・所属変更・削除等で活動が取得不能なら、既存の401／403／404・メンテナンス制御に従い、古いカードから更新操作を継続させない。
- 一覧へ戻るときは元の条件・ページ・カードの位置を復元する。削除・絞り込み対象外への変更で元カードが消えた場合は、残る一覧と有効なページ・スクロール範囲へ安全に復帰する。
- フッターナビからの新規一覧表示による条件初期化、新規タブ・修飾キー付きリンク等のブラウザ標準動作を維持する。

## 6. R03 — リワード獲得演出

### 6.1 見た目・時間

- 対象は新しい獲得通知モーダルのみ。条件の編集・停止・削除確認、獲得履歴の閲覧には演出を付けない。
- 重なりは「ページ → 既存の暗転＋4pxブラー → 白い集中線 → 鮮明なモーダル本文」とする。集中線がモーダル本文や閉じるボタンに重ならないようにする。
- 集中線は白のみで、複数の透過度を使う。中心はモーダル付近とし、色付き線・星・紙吹雪・音・振動は追加しない。
- 一定方向へ等速で1周12秒、2周（24秒）回転したら静止し、閉じるまで集中線を残す（2026-10-24のユーザー指定を反映）。拡大縮小・往復は行わない。高速な明滅やモーダル自体の点滅は行わない。
- 複数の獲得を1モーダルにまとめて表示する既存挙動を維持し、演出もモーダル全体で1つだけとする。
- 言語・テーマ変更、モーダル内部のスクロール、再描画で演出を再スタートしない。次の別の獲得通知モーダルを開く場合にだけ再実行する。

### 6.2 実装・アクセシビリティ

- CSSのconic-gradient等による軽量な表現を第一候補とし、外部のアニメーションライブラリや画像生成は導入しない。
- ネイティブdialogのtop layer・backdropと両立させる。SettingsDialogを拡張する場合も、演出を明示指定した獲得通知だけに適用する。
- 集中線は装飾で、aria-hidden・pointer-eventsなし。フォーカス可能な要素を増やさず、閉じる／Escape・フォーカス・背景操作遮断を維持する。
- prefers-reduced-motionでは最初から静止する。設定が表示中に切り替わった場合も直ちに停止し、解除時に再生し直さない。
- 非表示タブでは不要な動作を継続せず、戻った際も演出を最初から再開しない。モーダル破棄・画面遷移時にタイマー等を解放する。
- 未対応環境では静止表現または集中線なしで獲得内容を表示できるようにする。演出を通知表示の前提にしない。
- Windows版Playwright WebKitだけでぼかしや描画負荷を実機合格扱いにしない。iPhone Safari／PWAで重なり・読みやすさ・動作を必須確認する。

### ローカル確認で発見した500エラーの修正（2026-10-24）

- 症状：警告一覧GETが500となり、設定のメンバー欄でも取得失敗を表示。再試行しても解消しない。
- 原因：Laravelの`notifications()`関連に付く既定の`ORDER BY created_at DESC`がメンバー別の`GROUP BY`集計へ残り、PostgreSQLで`SQLSTATE[42803]`が発生した。SQLiteだけの初回検証では検出できなかった。
- 修正：集計用に複製したクエリへ`reorder()`を追加。明細一覧の新しい順・表示上限・認可は維持する。
- 回帰：未確認0件の親に空のdata・0件のmetaを返すAPIテストを追加。既存CIのAuthentication PostgreSQL acceptanceはLoginSecurityAlertTestを既に含むため、CI構成の変更は不要。
- 検証：独立したPostgreSQL 14テストDBでLoginSecurityAlertTest／LoginSecurityTest／GroupIsolationTestの19件・204 assertionsが合格。SQLiteのLoginSecurityAlertTestは10件・130 assertions、Pint・差分空白チェックも合格。
- 通常ローカルDBのデータ・スキーマ・設定は変更なし。今回の検証用PostgreSQLは完了後に停止。画面の再読み込みでローカル再確認を依頼する。

### 次の確認

親アカウントで「設定 → 家族メンバー」を開き、未確認警告のあるメンバーについて以下を確認する。
