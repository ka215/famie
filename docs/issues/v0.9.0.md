## 0.9-A. アクティビティ登録モーダルの重なり修正（最優先）

### 現状と方針

`LogCreateModal.vue` はスクロール領域内に配置され、`fixed` / `z-50` を指定している。共通レイアウトはv0.8.0で導入したアプリシェルと内部スクロールを使用し、ヘッダー・フッターに `z-10` がある。数値上の大小だけでは原因を断定せず、実機で重なり・切り取り・表示領域を確認して修正する。

モーダルをスクロール領域や祖先の重なり順の影響から切り離し、画面全体のオーバーレイとして扱う方針とする。配置方法は実装時に決め、v0.8.0のキーボード開閉後のフッター位置対策を維持する。

### 受入条件

- 週表示・月表示・指定期間表示の各導線からモーダルを開ける。
- モーダルと背景オーバーレイがヘッダー・フッターより前面に表示され、フッターが保存ボタンや入力欄を覆わない。
- モーダル表示中、背景のメニューや一覧へクリック・タップ・キーボード操作が抜けない。背景スクロールも抑止する。
- 画面高が不足する場合はモーダル内をスクロールでき、最後の入力欄と「記録を保存する」まで到達できる。保存ボタンを常時固定表示することは必須としない。
- iPhoneのセーフエリアとソフトウェアキーボードを考慮し、入力中・キーボードを閉じた後とも保存・閉じる操作が可能である。
- 開いた際のフォーカスをモーダル内へ移し、閉じた後は起動元へ戻す。ダイアログ名とモーダル状態を支援技術から識別できる。
- 閉じた後、通常画面のスクロール・フッター操作が復旧し、表示位置のずれや下部の隙間が残らない。
- 選択日の初期値、日付・時刻の重なり対策、Zod検証、APIエラー、二重送信防止、保存後の一覧更新を維持する。
- メンテナンス状態に切り替わった際、モーダルがメンテナンス表示より前面に残ったり、操作可能なままになったりしない。

### 主な影響箇所

`frontend/app/components/LogCreateModal.vue`、`frontend/app/layouts/default.vue`、必要に応じて `app.vue`・共通CSS・起動元ページ。既存の登録・モバイルUI・メンテナンスE2Eを利用する。

## 0.9-B. 商用環境のIP制限解除

### 環境別の要件

| 環境 | 画面・静的資産 | API | 認証済みデータへのアクセス |
| --- | --- | --- | --- |
| 商用 | 接続元IPによる制限なし | 接続元IPによる制限なし | 既存の認証・権限制御を継続 |
| ステージング | 現在の許可IPだけ | 現在の許可IPだけ | 既存の認証・権限制御を継続 |
| ローカル・テスト | 既存の開発・テスト設定を維持 | 制限有効・無効の両条件を検証可能 | 既存動作を維持 |

制限解除はログイン画面へアクセスできるネットワークを広げる変更であり、匿名で活動履歴を閲覧・更新できるようにするものではない。既存の単一家族運用を継続し、一般利用者向けの新規登録画面・APIは追加しない。

### 実装・設定要件

- ApacheとLaravelの二層を対象とする。商用のドキュメントルート、API側、上位設定に有効なIP制限がないか適用前に確認する。
- Laravelの現状は `ALLOWED_IPS` が空でも全拒否となるため、空文字による解除にはしない。環境ごとの明示的な有効・無効設定を設ける。
- 新しい設定が未指定の場合は従来どおり制限を有効にする。有効時の許可リスト空欄は引き続き全拒否とする。
- 商用のみ明示的に無効化し、ステージングでは有効を維持する。両環境で `APP_ENV=production` を使う現行配置検査に合わせ、`APP_ENV` だけで解除を判断しない。
- Apacheでは商用のIP制限に関係する設定だけを調整し、API転送、SPAルーティング、HTTPS、メンテナンス503、キャッシュ制御、ファイルアクセス保護を維持する。
- `.htaccess` は現行の配置処理で保持されるため、コード配置だけで解除済みとみなさない。商用の設定変更とLaravel設定キャッシュの反映を配置手順に含める。
- 同一成果物をステージングから商用へ昇格する方針を維持し、環境差分はサーバー側設定で管理する。
- 配置検査・関連テストがIP制限を前提にしている箇所を点検し、必要な箇所だけ環境別の期待値に更新する。
- 商用設定変更前の状態を退避し、Apache・Laravel双方で制限を戻す手順を記載する。旧版への切り戻し時は、新しい無効化設定が旧版に存在しないことも考慮する。

### 受入条件

- 従来の許可リストに含まれない回線から、商用のログイン画面・静的資産を取得し、既存アカウントでログイン、一覧取得、記録の登録、ログアウトができる。
- 未認証の保護APIは401、権限不足の操作は既存仕様の拒否結果となり、IP制限解除による認証迂回がない。
- ステージングは許可IPから利用でき、許可外IPでは画面・APIとも403になる。
- 制限有効時の空許可リストは全拒否、無効時はIPリストの内容によらず認証処理へ進むことをテストする。
- メンテナンス中、商用は既存の503表示・API応答となる。ステージングの許可外IPは従来どおり先に拒否される。
- 再配置しても、商用解除・ステージング制限維持の設定が保たれる。
- 設定差分、適用日時、検証回線、結果、復旧手順を公開記録に残す。実IPや秘密情報を要件文書へ転記しない。

[基本設計](../basic_design.md)、[フロントエンド配置手順](../operations/runbooks/howto_release_frontend.md)、[バックエンド配置手順](../operations/runbooks/howto_release_backend.md)、[ステージング手順](../operations/runbooks/staging-deploy-notes.md)、[リリース手順](../operations/runbooks/release-script-notes.md)の関連箇所を現行化する。過去の公開記録は当時の事実として保持する。

## 0.9-C. システム設定に準拠したダークモード

### 切り替え規則

- OS・ブラウザの `prefers-color-scheme` に従い、ライト／ダークを適用する。ダーク指定がない環境はライトとする。
- 初回表示から適用し、起動中にシステム設定を変更した場合も再ログインや再読み込みなしで追従する。
- アプリ内の切り替えUI、ユーザー別設定、DB・localStorageへのテーマ保存は追加しない。
- 既存のTailwind・CSSと共通部品を利用し、テーマ切り替えのためだけの依存パッケージは追加しない。

### 対象画面・状態

| 対象 | 確認範囲 |
| --- | --- |
| 共通レイアウト | 背景、ヘッダー、フッター、選択中・無効のメニュー、罫線、セーフエリア |
| ログイン | 入力、パスワード表示切り替え、エラー、ホーム追加ガイド |
| タイムライン | 週・月・指定期間、曜日・今日・選択日、件数、絞り込み、ページング、カード、空表示、読込中 |
| アクティビティ登録・編集 | モーダル背景、全入力、日付・時刻、エラー、保存中、削除操作 |
| 設定 | 全カード、表示名、家族メンバー、カテゴリ、パスワード、成功・失敗表示、ログアウト、クレジット |
| 起動・異常時 | SPA読込中、Nuxtエラー画面、アプリ内メンテナンス表示、静的 `maintenance.html` |

### 表示要件・受入条件

- 背景、カード、本文、補助文字、罫線、フォーム、プレースホルダー、ボタン、アイコンを一貫した配色にする。背景だけ暗くして文字が読めなくなる状態を残さない。
- 通常文字のコントラスト比4.5:1以上を設計目標とし、代表的な本文・補助文字・エラー・ボタンラベルで確認する。
- フォーカス、選択、hover、disabled、通信中、成功、エラーを両テーマで判別できる。色だけに依存せず既存の文言・アイコン・ARIA情報を維持する。
- 日曜の赤・土曜の青、今日と選択日の区別、カテゴリー色の意味を維持する。保存済みのカテゴリ色自体は変更せず、背景や文字の組み合わせを調整する。
- 日付・時刻・select等のネイティブ入力も配色を確認し、入力値・選択肢を読めるようにする。
- SVGマスク、スピナー、QRコードなどを確認する。QRコードは読み取りに必要な背景・余白を維持し、一律反転しない。
- 初期HTML・SPA読込中の背景もシステム設定に合わせ、アプリ側で制御できる範囲の白い表示のちらつきを抑える。
- PWAでも起動後の画面と切り替えが正常に動く。ブラウザのテーマ色は対応範囲を確認して調整するが、OS管理の起動画面・アイコン・manifest色の動的切り替えは必須としない。
- ライトモードのレイアウト、情報量、入力挙動を維持し、0.9-Aの修正が両テーマで有効である。

## 0.9-D. 複数家族対応・リワードの実装準備

### 優先順位と今回の到達点

**課題7（複数家族の基盤）→ 課題9（新規家族・親登録）→ 課題6（家族単位のリワード）の順を採用する案とする。** 課題7・9は同一の後続版にまとめるか、段階導入するかを設計で決める。

現在、ユーザー・カテゴリ・活動履歴には家族境界がなく、親子ロールはユーザーに保存されている。リワードを先に実装すると、条件・対象者・獲得履歴へ後から家族分離を追加する必要があるため、先に所属とアクセス範囲を定義する。

v0.9.0では以下を設計資料として具体化する。migration、モデル、API、画面、ジョブの実装や、本番データの移行は行わない。後続版のバージョン番号・公開日は本書では確約しない。

### 進め方（2026-09-28追記）

1. 事前準備として、現行DBのスキーマ情報とER図を含むモデル仕様書を `docs/` 配下に作成する。既存の参考資料をそのまま現行仕様とせず、migration・モデル・実際の制約と照合する。
2. 仕様書にはテーブル・カラム・型・NULL可否・既定値・主キー・外部キー・一意制約・索引・削除時の動作、およびモデル間の関連を記載する。DBで保証する関係とアプリ側だけの関連を区別する。
3. 調査元・対象環境・確認日を明記する。実DBを確認していない項目はその旨を示し、リポジトリから読み取れる定義を商用DBの実測結果として扱わない。個人データや認証情報は掲載しない。
4. 現行モデル仕様書をユーザーへ提示し、それをもとにユーザーが複数家族・リワードのモデル素案を提案する。
5. 素案を受け取った後、以下の設計論点を対話で検討し、合意した内容を設計資料へ反映する。素案の提示前に新モデル・移行方式を独断で確定しない。

本書のモデル方針・推奨順序は対話の出発点とし、合意に応じて更新する。現行モデルの文書化と設計完了は区別し、素案待ちの間も0.9-A〜Cの作業は独立して進める。それ以外のタスクの具体的な進め方は担当エージェントに委ねる。

### 複数家族対応の初期スコープ

- 新規登録時に親アカウントと家族名を受け付け、一つの家族とその親を一体で作成する。
- 初期段階では一つのユーザーは一つの家族に所属する。親が新しく作成した子アカウントも同じ家族に所属する。
- 家族メンバー、カテゴリ、活動履歴、件数・集計、将来のリワードを家族内に閉じる。
- 親の管理権限は所属家族内に限る。活動履歴の編集・削除は本人のみという既存方針を維持する。
- 既存アカウントを別家族の子として紐づける機能、複数所属、家族切り替え、家族間交流は初期スコープから除外する。これらのためだけの所属中間テーブル等を先行実装しない。
- 「グループチャット的な利用」は閉じた家族単位の利用を指し、チャット・メッセージ機能の追加は含めない。

### リワードの要件整理

メモの内容を最新候補とし、[旧課題原案](backlog.md)の「月間固定」「トロフィー」「最大n個」を無条件に確定仕様として引き継がない。

- 親が家族に紐づくリワード条件を定義し、対象アカウントを同一家族内から指定する。
- 条件は期間内のアクティビティ登録回数と必要回数を持ち、同一日に複数回を数えるか設定できる。
- 条件達成時に報酬を獲得し、インベントリで獲得済み報酬と定義済みの条件を確認できる。
- 「お小遣い+n円」は報酬内容の例であり、送金・決済・残高管理は対象にしない。
- 将来のモデルは、家族に属する条件定義、対象ユーザー、獲得履歴を分けて検討する。獲得時点の条件・報酬内容の保存と重複付与防止を設計論点に含める。

次の論点は実装前に選択肢・推奨案・影響を整理する。今回、曖昧な値をコードやDBへ固定しない。

| 論点 | 決める事項 |
| --- | --- |
| 期間 | 開始・終了日指定かnか月の繰り返しか、月末・境界・タイムゾーンの扱い |
| 集計 | 実施日と登録日時のどちらを使うか、1日1回の定義、対象者ごとの達成か合算か |
| 履歴変更 | 過去日登録、編集、削除、条件変更、対象者変更時の再計算・獲得取消の扱い |
| 付与 | 即時判定か定期処理か、単発か繰り返しか、同時登録時の重複防止 |
| インベントリ | 本人・親・他の家族メンバーの閲覧範囲、進捗、失効・受渡し済み状態の要否 |
| 運用制限 | リワード定義数・対象人数の上限、親も対象にできるか、退会・削除後の記録保持 |

### 成果物・完了条件

- 現行DBのモデル仕様書（スキーマ情報・ER図・調査根拠）を先に作成し、ユーザーがモデル素案を検討できる状態にする。
