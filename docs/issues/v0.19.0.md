## 4. R01 — ログと追跡

### 4.1 記録形式・追跡ID

- アプリの運用・セキュリティイベントはJSON Linesとし、UTC時刻、環境、版または配置SHA、イベント名、重大度、結果、`request_id`を共通項目にする。日時を運用記録へ転記するときはJSTも明記する。
- HTTPリクエストごとにサーバーが新しい推測困難なIDを生成し、正常・401・403・404・422・429・500系の応答へ`X-Request-ID`を付ける。クライアント指定値はそのまま採用しない。
- 同じIDを処理中のログに付け、例外処理でも失わない。CLIは実行単位のIDを使う。アプリ到達前のApache等のエラーには付与できないため、Webサーバーログとの時刻照合を手順に記載する。
- 許可済みフロントからIDを読めるようCORSの公開ヘッダーへ追加する。既存JSON応答・日英メッセージは維持し、本文へのID追加や新しいエラー画面は必須としない。API文書に応答ヘッダーを記載する。
- 原則はイベント発生時だけ記録する。全APIの本文・全成功アクセスを新規に保存する方式は採用しない。

### 4.2 イベント一覧

| 分類 | 記録する事象 | レベル・補足 |
| --- | --- | --- |
| アプリ障害 | 未処理例外・5xx、メール失敗、画像削除失敗 | error／warning。例外クラスと固定エラーコードを基本とする |
| 認証 | ログイン失敗、ロック・レート制限発動、復旧・パスワード変更の成功／失敗、ログアウト | warning／info。存在しないアカウントも同じ失敗表現にする |
| 認可 | 認証済みの権限拒否、家族間アクセス拒否 | warning。外向け404を維持するものは応答を403へ変えない |
| 管理 | メンバー作成・編集・無効化・復元・パスワード再設定、家族設定・カテゴリ・リワード定義の変更、警告の確認済み操作 | info。操作・対象種別・結果のみ。変更前後の本文は保存しない |
| 運用 | チェック・定期処理・バックアップ・復元の開始／終了／失敗 | info／error。終了コード、所要時間、件数、実行ID |

認証済み処理の主体・家族・対象を結び付ける必要がある場合のみ内部IDを許可する。未認証入力からusername・メール・候補IDを作ってログへ転記しない。管理成功はDBコミット後に記録し、ロールバックした操作を成功扱いしない。対象別イベントとHTTP拒否イベントの重複を抑える。

### 4.3 保存しない情報・漏えい対策

- パスワード、Bearer・復旧・メール確認トークン、Authorization、Cookie、メールアドレス、username、表示名、活動本文・メモ、画像本体・メタデータ・実保存パスを運用ログへ記録しない。
- URLはルートテンプレートまたは固定分類名とし、クエリ・リクエスト／レスポンス本文・全ヘッダー・User-Agentを自動添付しない。生IPは新しいアプリ運用ログへ追加しない。
- 既存の認証警告用DBデータとサーバーのアクセスログは別系統として棚卸しし、既存機能を無断で削らない。IP等が残る場合は項目・目的・保持を明示する。
- Laravelの標準例外出力、SQL例外のバインド値、例外メッセージ、スタックの引数・パス、CLI標準エラーも点検する。許可項目から構成する方式を基本とし、単純なキー名置換だけで安全と判断しない。
- 改行・制御文字・任意長の入力によるログ汚染を防止する。管理イベントの動的contextは許可キーと長さを制限する。
- 本番`APP_DEBUG=false`を確認。生の例外情報をユーザー応答や通知メールへ含めない。

### 4.4 保存・閲覧・失敗時

初期案はアプリ運用ログ14日、監視結果・通知履歴30日、匿名化したCI計測結果30日、検査レポート14日。日次ローテーションと期限超過削除を行う。監視失敗中も削除が止まり容量を圧迫しないよう確認する。セキュリティ事案の保全は運用者が対象・期限を限定して非公開に複製する。

ログは公開docroot外、運用者のみ閲覧可能にし、配置時に上書き消失させない。ログ書き込み失敗によって通常の認証・更新を不要に失敗させず、機微情報を含まない代替エラーと容量／権限の独立チェックで検知する。監査記録の欠落は正常扱いしない。ログ先障害・ディスク不足を模擬して業務処理と検知を確認する。

## 5. R02 — 監視・通知・バックアップ

### 5.1 チェック項目と初期値

| 項目 | 初期頻度・条件 | 検査内容 |
| --- | --- | --- |
| アプリ内部 | サーバーcronで5分間隔、2回連続失敗 | Laravel起動・DBへの読み取り疎通・必要ディレクトリ書込可否。詳細はCLI出力を非公開保存 |
| 容量 | サーバーcronで1時間間隔、使用率80%警告・90%重大 | 契約容量・利用量、取得可能ならinode。OS全体の空き容量と契約上限を区別 |
| エラー・認証集中 | 5分ごとに直近5分集計 | 5xxが5件以上、認証失敗・制限・権限拒否が各20件以上で警告。単発4xxではメール送信しない |
| 定期バックアップ | 日次、直近成功から26時間超過で障害 | 終了コード・dump構造・サイズ・SHA256・画像バックアップとの対応 |
| 画像削除再試行 | 日次、失敗または24時間超の未処理を警告 | 既存`famie:retry-image-deletions`を利用。重複起動防止、実行時間上限、開始／終了時刻 |
| 定期処理の欠測 | 各予定間隔＋猶予2回分を超過 | 開始のみで終了なしも失敗として判定。バックアップは上記26時間を使う |

CPU・メモリ等は契約環境で取得可否を確認し、取得できない項目は代替確認と制約を記録する。存在しないキューやスケジューラーを稼働済みとして監視しない。cronの登録方式・タイムゾーン・CLI PHP・ロック・timeout・通知経路を一覧化する。

内部ヘルス詳細やDB情報を公開APIへ追加しない。既存`status`の契約は維持し、DB疎通はCLIで確認する。既存の配置後疎通確認は許可済みの接続元から行い、ステージングのIP制限を解除しない。商用への既存の疎通確認もGET等の非破壊検査に限定する。

### 5.2 内部監視の範囲と制約

今回追加する監視はサーバーcronによる内部チェックとイベント集計に限定する。予定時刻と実際の開始／終了時刻を記録し、実行中断や結果不明を成功扱いしない。動作中の内部チェックから他の定期処理の未実施・失敗を検知する。

サーバー全体やcron全体の停止は同じサーバー内の処理だけでは検知・通知できない。運用者が日次で最終実行結果を確認する運用とし、独立した監視元からの死活・欠測検知は後続タスクに委ねる。外形workflowの追加、Windows runnerによる定期巡回、稼働率算出は行わない。候補検証・配置後疎通確認に使う既存runnerの役割は維持する。

### 5.3 通知・対応

- 通知手段は運用者メール。宛先・SMTP等の秘密値は非公開設定へ登録する。アプリのアカウント通知宛先や家族の親へ運用通知を流用しない。
- 本文は環境、固定チェック名、重大度、発生／検知時刻、追跡ID、対応手順への参照だけとする。利用者情報・ログ全文・内部接続情報は含めない。
- 同一環境・チェックの未復旧障害は初回通知、継続中は60分に1回まで、正常2回連続で復旧を1回通知する。重大化は別途即時通知。メンテナンスは対象と期限を指定して抑止し、期間も履歴に残す。
- メール送信失敗は非公開記録と次回再試行で扱い、通知処理を再帰させない。SMTP障害も同じメールだけでは通知できない制約を明記する。
- 対応担当は運用者。通知受信 → 対象環境・候補確認 → ログと直近変更の確認 → 必要ならメンテナンス／既存切り戻し → 復旧確認 → 原因・影響・再発防止記録とする。自動ロールバック・自動DB復元は行わない。

### 5.4 バックアップと復元

- 既存の配置直前DBバックアップは維持する。リリース用は既存規約の最低3世代を保持し、候補・切り戻し・未完了セッションが参照するものは削除しない。
- 日次バックアップはDBと永続画像を対象とし、初期案は7日分。公開物・秘密設定とは分け、公開docroot外に保存する。容量と取得時の整合性を確認し、DBと画像の取得順・更新中画像の扱いを手順化する。
- バックアップを一覧表示できたことと復元成功を区別する。DBと画像を隔離した検証環境に復元し、家族数・活動・画像参照・ログイン・家族間分離を確認する。検証中の外部メール・定期処理は停止する。
- 商用データを開発PCやGitHub artifactへ複製しない。実データを使う復元先・閲覧者・検証後削除は実施前にユーザーへ提示する。まず専用テストデータで復元手順を検証する。
- 復元記録は日時・担当・対象環境・バックアップ識別子／SHA256・復元先・所要時間・検証結果・後片付けを残す。復元操作は対象DBとルートのガードを必須とする。
- 復旧目標は日次取得によるRPO 24時間。RTOは初回復元後のユーザー指定により、同じサーバーとバックアップを利用できる障害について、検知から復旧まで6時間以内を目標とする。商用データ量や基盤再構築を含む未測定の値を保証しない。同一サーバー保存だけではサーバー全損を救えないため、提供元バックアップの範囲・復元方法も確認する。別拠点保管の追加が必要なら費用・暗号化・保存先を相談する。

## 6. R03 — 継続セキュリティ検査

### 6.1 実行単位

| タイミング | 必須内容 |
| --- | --- |
| 通常PR | 秘密情報検査、pnpm／Composerの依存脆弱性検査、PHP・JS/TS・workflowの静的検査、関連する既存の認証・認可回帰 |
| 週次・手動 | 依存検査再実行、ステージングの限定的動的検査、入力・画像・権限の重点試験。runner停止時は未実施として追跡 |
| 各候補 | 固定SHAへの検査結果・指摘一覧、変更範囲の重点確認 |
| v0.21.0 | 最終機能への総合脆弱性検証。本版の基盤だけで全項目完了とは扱わない |

依存検査はlockfileを対象にし、開発依存も含めて分類する。秘密検査は現在のツリーとPR差分を対象とし、初回に履歴の検査も行う。テスト用の公開TLS鍵等はファイル・理由を限定して除外し、広いディレクトリ除外はしない。検出した秘密値を公開レポートへ転記せず、必要な失効・再発行を相談する。

静的検査はPHP・JS/TSの危険な入力／SQL／コマンド／HTML処理、Actionsの権限・未信頼入力を対象とする。候補はGitleaks、Semgrep、actionlint等。採用ツール・ルール・版・ライセンス・配布物検証・実行時間を実装時に確認し、固定して記録する。新規の有料サービス・外部へのソースアップロードを伴う方式は事前相談する。

### 6.2 動的検査と実行境界

- workflowは対象環境と完全SHAを入力し、配置済み候補と一致することを確認する。商用URL・任意URLは指定不可。ステージング固定ホスト・許可パスだけを対象にする。
- PRのコードを許可済みself-hosted runnerで自動実行しない。動的検査はレビュー済みの信頼できるworkflowから手動／定期で行い、実行資材・候補・権限を記録する。
- Windows runnerで利用できるツールと経路を先に検証する。Docker・WSL・Pythonの導入やIP制限緩和を前提にしない。ZAPは候補であり必須製品ではない。既存Playwright/APIテストと直接実行できる検査を基本とし、足りない検査は代替または追加基盤を相談する。
- ZAP等のpassive scanでもクロールによるアクセスは発生する。対象・到達先・GETで状態が変わる経路・ログアウト等の除外を確認し、最初は専用データで実施する。
- 認証あり検査は親・子・別家族の専用アカウントを使う。攻撃的入力・アップロード・連打はステージングのみ、件数・並列数・時間上限を設定する。実利用者のセッションや画像を使わない。
- 対象のXSS・SQLi・トラバーサル・なりすまし・セッション・辞書攻撃・CSRF・コマンド注入・家族間分離・画像認可・トークン失効・情報漏えい・CORS/CSP・PWA混在・競合・供給網を対応表にする。自動／手動／未対応・根拠・次回対応版を明記する。
- 初版は既存の認証・家族間分離・画像アクセスのテストを定期実行可能にし、ログへの秘密情報混入を新たに検証する。同意関連はv0.20.0実装後に追加する。ブラウザーから読めるトークンのXSS影響をレビューするが、認証方式の移行は別途合意する。

### 6.3 判定・例外管理

秘密情報検出、重大・高リスクの依存／静的検査指摘、新規の認証・認可回帰は必須検査を失敗させる。ただし第13節のユーザー承認済みnode-forge例外のみ、定めた条件と期限内で明示して通過させる。検査ツールの失敗やデータベース取得不能も成功扱いにしない。中以下は根拠・影響・対応期限・担当をIssueに記録する。誤検知除外は規則・対象・理由・期限を限定し、重大指摘を無言で除外しない。受容判断が必要な場合はユーザーに連携する。

レポートは公開可能な要約と非公開の詳細を分離する。GitHub artifactは非公開保管を保証する場所と見なさず、アップロード前にトークン・URL query・Cookie・個人情報・内部構成を除去する。

## 7. R04 — カバレッジ

- バックエンドは既存PHPUnitの`app/`を母集団として行カバレッジを計測し、生成コード・vendor・testsを含めない。PCOVまたはXdebugをCIの専用jobにだけ有効化する。SQLite全体とPostgreSQL重点検証は別レポートとし、単純平均しない。
- フロントは既存Node単体テストで実行するユーティリティ・検証スキーマ等を対象に行・分岐・関数を計測する。Node 24のcoverage機能とTypeScript／source mapの対応を小規模に検証し、未実行対象も母集団に入ることを確認する。成立しなければ別ツールの追加案を相談する。
- フロント単体の数字をVue画面・composable・E2E全体の数字として表示しない。画面カバレッジのためだけにテスト基盤を全面移行しない。
- レポートへ対象SHA、ツール版、実行条件、分子／分母、除外理由、日時を付ける。初回の実値は実装時に取得し、本書に仮の数値を書かない。
- 認証・復旧・失効、家族間分離、画像取得／更新／削除を優先し、重要分岐のテスト有無を表にする。未達は具体的な欠落分岐と追試を記載する。今回追加するログ秘匿・追跡・監視判定は正常／異常系を検証する。
- 初回は計測成功と重要領域の根拠ある検証を必須とする。以後の低下は差分と理由をレビューし、閾値・低下許容量は基準値取得後に提案する。計測失敗を0%や直前の成功値で隠さない。

## 8. R05 — CIの整理・バッジ

### 8.1 計測と分割方針

変更前後で同等のコード・runner・キャッシュ条件を可能な範囲でそろえ、各3回を基本にwall time・job／step時間・待機時間・runner使用時間・依存導入・ビルド重複を記録する。キャッシュ冷／温を分ける。既存runが比較可能なら再利用し、不必要なCI起動は避ける。高速化率を事前の合格値にせず、悪化した分割は採用しない。

候補構成はfrontend checks、backend SQLite、backend PostgreSQL、security、coverage、既存ブラウザー別E2E、最終verify。実測に基づき統合・分離を選ぶ。DBを共有して干渉する試験を同時実行せず、必要ならjobごとにDBを隔離する。辞書・API・日英・組み合わせ試験を重複に見えても根拠なく削らない。

- `verify`という最終判定を維持し、全必須jobの成功を明示確認する。failure／cancelled／予期しないskippedで成果物を生成しない。branch protectionの必須check変更が必要ならユーザーへ連携する。
- カバレッジ付き実行で通常テストを代替できる場合は重複を減らすが、DB条件や実行対象の差異を確認する。
- E2Eは既存のChromium／iPhone WebKitを維持する。共有ビルド・shardは状態分離と成果物同一性を証明できる場合に限り採用し、単純にworker数を増やさない。
- 依存cacheはlockfile・OS・runtimeをキーとし、秘密情報・DB・`.env`・利用者画像を含めない。Actions・検査ツールの追加は権限最小化・版固定・Node 24／runner互換を確認する。
- 最終候補は固定SHAから一度だけクリーンビルドし、静的資産検査・日英のrelease smoke後に保存する。同一成果物のステージング→商用昇格、SHA256・tree照合を維持する。

### 8.2 バッジ

既存の日英READMEのCIバッジは維持する。追加候補は対象を明記したbackend／frontend unit coverage。信頼できるブランチの成功runからだけ更新し、PRから公開先へ書き込ませない。値・対象SHA・時刻を保持し、失敗時は古い結果であることが分かる表示とする。外部サービスへの登録や公開用branchの新設が必要な場合は、具体案を別途確認する。

稼働率・Online等の監視バッジは今回追加しない。死活・外形監視とともに後続タスクで観測元・期間・欠測・公開範囲を設計する。管理サイトとの連携も本版の完了条件に含めない。
