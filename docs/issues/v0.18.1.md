## 4. R01 — 登録禁止アカウント名

### 4.1 対象と互換性

- 対象はログインIDの`username`。家族名・表示名・メールアドレスは対象外。
- 新規家族登録と、親による親／子メンバーの新規作成に同じルールを適用する。利用可否チェックも同じ定義を参照する。
- 既存アカウントが禁止名を使用していても、その理由で無効化・改名要求・ログイン拒否・セッション失効は行わない。パスワード変更／復旧、メール設定、表示名変更、メンバー無効化／復元にも禁止名検証を追加しない。
- 禁止名の比較時は入力値とリスト項目をASCII小文字化して完全一致で照合する。これは禁止判定用だけで、保存するusernameやログイン照合規則は変更しない。現行APIは小文字のみ許可するため、`Admin`等は引き続き形式エラーとなる。大文字を新規usernameとして許可する変更は今回含めない。
- 新規作成時だけ検証する。既存データの走査・修正やmigrationは行わない。Seeder／Factoryは新規作成APIの代替として検証せず、既存アカウント互換性のテストデータ作成に利用できる。

### 4.2 基本リストと独自追加（採用案）

基本候補は[shouldbee/reserved-usernames](https://github.com/shouldbee/reserved-usernames)。URLとリソースパスの衝突防止を目的とする予約語リストであり、システム・運営名だけでなく`about`・`blog`・`home`・`test`等も含む。不適切語やなりすましを網羅する辞書としては扱わない。ユーザーはシステム・運営名を選別する方針を選択した。一般予約語の全件採用は行わない。

2026-10-25確認時の固定候補：

- リポジトリcommit: `0302214e8c1363fc5877ce3343ef6262e8852e96`。
- [原本JSON](https://github.com/shouldbee/reserved-usernames/blob/0302214e8c1363fc5877ce3343ef6262e8852e96/reserved-usernames.json)：602件、小文字化後の重複なし。リストファイルの最終変更commitは`6ba3c80ec3f973de1e2676247a4b3cccf3c17d0b`（2019-02-17）。
- [MITライセンス](https://github.com/shouldbee/reserved-usernames/blob/0302214e8c1363fc5877ce3343ef6262e8852e96/LICENSE)を確認。取り込む際は原本の著作権表示・許諾文を保持し、同一成果物にも含める。
- 原本のうち16件は1〜2文字で、現行の3〜50文字のusername形式では入力できない。現行形式だけで絞れば586件となるが、これは調査値であって採用件数ではない。実際は以下の18件だけを明示選別する。元の語を部分削除して別名へ変換しない。

実装時の配置：

| `backend/resources/data/reserved-usernames.json` | 出典情報・固定commit・上流からの明示選別・Famie独自追加。下記ひな形 |

- `base_exact`の18件だけを固定原本から採用する。管理・権限・システム運用・連絡窓口を連想させる語を対象とし、選定語が原本に存在することを検証する。`about`・`blog`・`home`・`test`等は原本にあっても本案では禁止しない。
- 独自追加12件は上流にないFamie運営名・窓口名。上流選別18件と合わせた初期有効集合は30件。ハイフンとアンダースコアは別名なので、それぞれ明示する。
- 上流原本の存在確認済み選別語と独自追加をASCII小文字化し、集合として重複を除去して完全一致判定する。原本の602件をそのまま禁止集合へ投入しない。選別／追加は小文字の有効語で保存し、選定語の原本欠落・現行形式違反・同一リスト内の正規化後重複をCIで検出する。
- 上流の形式が文字列配列でない、JSONが欠落／不正、独自schema_versionが不明、未知キー・不正な独自語がある等の場合はCIを失敗させる。実行時も空リストへ黙ってフォールバックせず、対象の新規作成／利用可否チェックを既存形式の503で失敗させる。通常ログイン等へ影響しない読み込み範囲とする。
- 上流の更新は固定commitとの差分をレビューして手動取り込みする。登録時・アプリ起動時・通常CIで最新版を外部取得せず、外部障害や未レビューの上流更新で登録結果を変えない。
- 実装時に原本のSHA256・取得commit・取得日・ライセンスを記録し、原本／選別・独自追加／ライセンスが配置成果物に含まれることを検証する。管理画面・DBテーブル・追加パッケージは導入しない。
- 既存アカウントは基本リストにも独自追加にも遡及適用しない。禁止照合を共通化し、フロントへリストを複製しない。

### 4.3 API・表示・失敗時処理

| 入口 | 禁止名の場合 | 維持するもの |
| --- | --- | --- |
| 新規家族登録 | 422、`errors.username`に日英の利用不可メッセージ。家族／ユーザー／トークンを作成しない | 形式・重複・パスワード・レート制限 |
| 親によるメンバー追加 | 422、`errors.username`。ユーザー／所属を作成しない | 親限定認可・人数上限・既存トランザクション |
| 利用可否チェック | 形式が正しければ200、`{"available":false}` | 不正形式の422、既存レスポンス構造・レート制限 |
| 既存ログイン等 | 禁止名判定を適用しない | 従来の認証・停止・失効・復旧の規則 |

- 利用可否チェックに禁止理由や追加のDB利用状況は返さない。使用済み名も従来どおりfalse。
- 利用不可の画面文言は「このアカウント名は使用できません。別の名前を入力してください。」／“This username is unavailable. Choose another name.”を案とする。「登録済み」と断定しない文言を新規登録の事前確認・送信前ガードに使う。登録APIの既存重複エラーは維持可能。
- 事前確認は補助とし、確認APIを通さない直接POST、確認後の定義変更・競合でも作成APIが判定する。
- 通信失敗は利用可能／利用不可と断定せず、現行の確認失敗・再試行導線を維持する。古いusernameへの遅い応答で現在の入力状態を上書きしない。
- 入力・他項目のエラー・日英切替を維持する。禁止名一覧を利用者向け説明へ埋め込まない。

## 5. R02 — インベントリのトロフィー累計

### 5.1 集計範囲

- インベントリの選択メンバーについて、保持されている全期間・全ページの`RewardAward`を対象にする。家族全員の合算は追加しない。
- 1獲得レコードを1個と数える。`achieved_count`の合計、条件の必要回数、リワード定義数は数えない。
- 金・銀・銅は獲得時の`snapshot.color`で分類する。定義の編集・停止・削除後も、残っている獲得履歴は累計へ含める。既読／未読でも数は変えない。
- 履歴0件は3種とも0。表示中の10件、表示しているページのtotal、フロントに取得済みの履歴だけでは計算しない。
- 対象は現行どおり有効メンバー。親でも他家族／存在しない／無効メンバーは従来の404、一般メンバーによる同一家族の他者指定は従来の403を維持。累計だけを別権限で返さない。

### 5.2 API契約案

`GET /api/v1/groups/{group}/rewards/awards?member_id={membership_id}&page={page}`へ後方互換の情報を追加する。新しいquery・フィルター・エンドポイントは追加しない。既存の`data`・`current_page`・`last_page`・`total`等は維持する。

```json
{
  "data": [],
  "current_page": 1,
  "last_page": 1,
  "total": 0,
  "meta": {
    "trophy_totals": { "gold": 0, "silver": 0, "bronze": 0 }
  }
}
```

- `meta.trophy_totals`の3キーを常に返す。値は0以上の整数。`total`は引き続き選択メンバーの獲得履歴総数。
- 一覧と同じ家族・所属条件を集計クエリでも必ず適用する。全履歴をPHP／ブラウザへロードせずDB側で集計し、色ごとに一覧APIを3回呼ぶ方式や新しい保存済みカウンターは導入しない。
- SQLiteだけでなく商用相当のPostgreSQLでもsnapshot色の集計を確認する。現行索引と取得計画を確認し、新しいDB変更が必要なら理由・影響を別途連携する。
- フロントの一覧型は獲得一覧用の追加情報として扱い、条件・進捗／管理APIへ累計の必須項目を広げない。OpenAPIと型を合わせて更新する。

### 5.3 表示・更新

- インベントリのメンバー選択欄の下、獲得一覧の最上部へ非カードの1行で表示する。条件・進捗／管理タブ、獲得通知モーダルには追加しない。
- 表示順は金・銀・銅。既存`RewardTrophy`のSVG・色を再利用し、`金アイコン N | 銀アイコン N | 銅アイコン N`とする。色だけで種別を伝えず、読み上げ用に「金トロフィー N個」等の日英ラベルを付け、区切りは装飾として扱う。
- 数値は日英の既存数値フォーマットを使い、小数なし。320px幅・ライト／ダークを確認する。通常の桁数では1行を維持し、極端に長い数値は行内だけの横スクロールで対応し、ページ全体を横にはみ出させない。
- 初期選択は現行どおり本人。親のメンバー切替では選択先の累計へ更新し、一般メンバーにはメンバー選択や他者閲覧を追加しない。
- 同じメンバーのページ送りでは同じ全件累計を表示する。切替や再取得中は未確定の数を0と断定せず、読み込み表示（例：`—`）にする。失敗時も0ではなく既存エラー・再試行を表示する。
- メンバー変更時は前メンバーの累計を直ちに隠す。応答の一覧と累計をまとめて検証・反映し、遅い応答・画面離脱・ログアウトで別メンバーの情報が混ざらないよう既存のgeneration制御を拡張する。
- 新しい獲得がある場合は通常の再取得・画面再訪で反映。ポーリング・リアルタイム通知・新しい更新ボタンは追加しない。獲得通知の取得先や既読処理は変更しない。

## 6. 変更範囲と対象外

実装時の候補は`UsernameRules`、禁止名共通判定とJSON、登録／利用可否APIと新規登録UI、`RewardController::awards`、獲得一覧型・rewards画面・既存トロフィー部品、日英辞書・OpenAPI・関連テスト。配置や依存の構造変更は行わない。

対象外：1-17・1-19、ログインID変更、表示名の禁止辞書、既存ユーザーの移行、禁止名管理画面、家族全員合計、種別フィルター、獲得条件・通知・集中線変更、監視・ログ基盤・カバレッジ・CI再編、ポリシー・同意UI。
