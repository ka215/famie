## 2. 調査結果

- SSHで秘密値を出力せず設定確認：商用はfrom／SMTP usernameが `noreply@famie.ka2.org`。stagingは `anonymous@ka2.org`。両者ともSMTP `s140.coreserver.jp:587`、パスワード設定あり。stagingの宛先制限はtrue、商用はfalse。新メールアカウントの準備状況は確認中。

- `appShortName`はmanifestとApple用metaで共有されている。ホーム追加ガイドの表示とQRのURLはすでにfamie.co。

## 3. メール移管仕様

新アカウントの存在、SMTP認証方式・送信権限、SPF/DKIM/DMARC等の現状を確認する。送信元だけを書き換え、旧アカウントで新アドレスの送信が許可されるとは推測しない。新パスワードはCoreServerの非公開設定経由で扱い、チャット・Git・ログへ記録しない。

商用の目標は `MAIL_FROM_ADDRESS=noreply@famie.co`。SMTP username／passwordは新アカウントの実設定に合わせる。from name、暗号化、タイムアウト、APP_URL・FAMIE_FRONTEND_URL、DB・APP_KEYは維持する。ユーザーより新アカウント作成済みの報告を受領。新パスワードはGit管理外の非公開設定ファイルで受け渡す。

送信元・SMTP認証の切替順は承認済み：**stagingで一時的にnoreply@famie.coを使用して検証 → 商用へ同じ新アカウントを適用 → 商用公開と確認後にstagingをnoreply@famie.ka2.orgへ変更**。stagingの初期実設定はanonymous@ka2.orgなので、最後の工程は単純な初期設定の復元ではない。旧商用アカウントを検証後のstaging専用送信元として使う。全工程でstagingのIP・宛先制限は維持する。

環境設定の切替前に非公開バックアップを取り、切替後にconfig cacheを再生成する。許可した本人宛てにメール確認・再設定・変更通知等の既存フローで実配送を検証し、From・リンク先・配送認証結果を確認する。受信者・実トークン・パスワードを証跡へ記載しない。実配送はユーザーと宛先・操作を連携して行う。

失敗時はfrom・SMTP認証情報を組として旧設定へ戻し、config cacheを再生成する。DB復元・APP_KEY再生成・メール機能の認可変更は行わない。詳細手順は[メール送信元移管手順](../operations/runbooks/mail-domain-migration.md)で管理する。

## 5. PWA名

Nuxtの `appShortName = 'Famie'` に変更し、manifest `short_name` と `apple-mobile-web-app-title`を揃える。manifestのname、scope、start_url、アイコン、SW戦略、表示言語は変更しない。日本語UIのブランド表記を全置換する要求とは扱わない。

既存ホームアイコンの表示名がOSに即時反映されることは保証しない。新規追加時と既存PWAの更新時を区別し、必要な端末では再追加で確認する。新manifestとmetaは既存のホーム追加ガイドE2Eで検証する。
