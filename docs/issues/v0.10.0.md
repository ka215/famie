# v0.10.0 詳細要件 — 複数家族対応

## 目的

v0.9.0で合意した[グループモデル拡張設計](../development/group-model-extension-spec.md)と[移行・検証計画](../development/group-model-extension-plan.md)を実装し、家族ごとにメンバー・カテゴリ・活動記録を分離する。

v0.10.0の到達点は、既存利用者を一つの家族へ安全に移行し、新しい親が別の家族を登録でき、画面・API・DBのすべてで家族をまたぐ参照や更新ができない状態である。将来拡張用の機能を同時に完成させることは目標にしない。

## スコープ選定

### v0.10.0で実装する

1. `groups` / `group_members`を導入し、認証ユーザーと家族内の所属・役割を分離する。
2. 既存の全ユーザー・カテゴリ・活動記録を一つの初期家族へ移行する。
3. 初期段階は1ユーザー1家族に制限する。
4. メンバー・カテゴリ・活動記録のAPIを`/groups/{group}/...`配下へ移し、全操作を家族単位に認可する。
5. ログイン・本人情報・画面状態を新しい所属モデルへ対応させる。
6. 新しい親ユーザーと家族を作成する公開登録画面・APIを追加する。
7. 既存の親による同一家族内の新規メンバー作成を維持する。
8. 家族名の表示とadminによる名称変更を追加する。これにより移行時の仮名称を利用者が変更できるようにする。
9. 家族人数・カテゴリ数の上限と、公開登録APIの試行制限を実装する。
10. カテゴリに`sort_order`を持たせ、既存順序と初期カテゴリ順を確定する。ただし並び替え操作は提供しない。
11. 所属無効化後のログイン拒否・活動記録非表示・再有効化時の再表示を、将来の管理機能が利用できる基盤として実装・検証する。
12. 既存データ移行、配置、切り戻し判断、家族分離の自動検証を整備する。

### 後続版へ送る

| 項目 | 理由・v0.10.0での扱い |
| --- | --- |
| 複数所属・家族切り替え | 初期はDBの`UNIQUE(user_id)`でも禁止。選択UI、同意、資格情報の管理を後続設計とする |
| 既存ユーザーの招待・家族間移籍 | 本人確認・同意・重複アカウント統合が必要。v0.10.0は新規ユーザー作成だけ |
| メンバー編集・無効化・復元UI | 課題5として後続対応。v0.10.0では物理削除を廃止し、状態・認可・API基盤とテストまで |
| カテゴリ並び替えUI・API | `sort_order`の保存と読み出しだけ実装し、課題11-Bへ引き継ぐ |
| カテゴリ編集・削除UI | 課題11-Aへ引き継ぐ。既存APIは家族内に限定して維持 |
| リワード | 家族基盤の公開後に詳細設計・実装。v0.10.0ではリワード用テーブルを作らない |
| 画像・招待メール | 課題8・10として後続対応 |
| グループ削除・種別変更 | 初期は`family`だけ。削除・統合・organization等は提供しない |
| プロフィール追加列 | avatar、birth_date、phone_number、user_metaは利用機能と同時に追加する |
| メール追加・変更・認証、パスワード再発行 | 本人確認を伴う設定画面とともに後続対応。v0.10.0の新規ユーザー作成ではメールを受け付けない |
| CAPTCHA | 公開登録の最小範囲外。試行制限は実装する |

## データモデル

### groups

| 列 | 要件 |
| --- | --- |
| id | bigint PK |
| name | varchar(255) NOT NULL。APIは前後空白を除き1〜50文字 |
| type | varchar(50) NOT NULL、既定値`family`。v0.10.0では`family`だけ許可 |
| timestamps | 既存Laravel方針に合わせる |

家族名は一意にしない。adminだけが変更できる。グループ削除・type変更APIは作らない。

### group_members

| 列 | 要件 |
| --- | --- |
| id | bigint PK |
| group_id | groups.id、NOT NULL、ON DELETE RESTRICT |
| user_id | users.id、NOT NULL、ON DELETE RESTRICT |
| role | varchar(50)、`admin` / `member`のみ、既定値`member` |
| status | varchar(20)、`active` / `inactive`のみ、既定値`active` |
| timestamps | 既存Laravel方針に合わせる |

- `UNIQUE(group_id, user_id)`と`UNIQUE(user_id)`を設定する。
- `(group_id, user_id)`を活動記録の複合外部キー参照先にする。
- v0.10.0の画面はactive所属だけを通常メンバーとして扱う。
- active adminを最低1人維持する。自分自身と最後のadminは無効化・降格できない。
- role/status変更時はグループ行を先にロックし、グループ→所属ID昇順→対象行の順にロックする。

### users

- username・emailの全体一意性、既存ID、表示名、パスワードを維持する。既存メールアドレスとメールによるログインは維持する。
- v0.10.0で新規作成するユーザーのemailはNULLとし、公開登録・管理者によるメンバー作成の入力として受け付けない。メール追加・変更は、ログイン後の本人操作とメール認証を同時に実装する後続タスクとする。
- `users.role`を所属へ移し、移行検証後に削除する。
- `User::isParent()`のグローバル判定を廃止し、対象グループのactive所属がadminかを判定する。
- ユーザーの物理削除を通常APIから行わない。inactiveになってもユーザー名・メールを再利用可能にしない。

### categories

- `group_id bigint NOT NULL`を追加し、groups.idをON DELETE RESTRICTで参照する。
- `sort_order integer NOT NULL CHECK (sort_order >= 1)`を追加する。
- 全体の`UNIQUE(name)`を`UNIQUE(group_id, name)`へ変更する。
- 複合参照用に`UNIQUE(group_id, id)`を設定する。
- 一覧は`sort_order ASC, id ASC`で返す。v0.10.0ではクライアントからsort_orderを指定・変更できない。
- 新規カテゴリはグループ行をロックし、そのグループの末尾へ追加する。
- グループ作成時、既定7カテゴリを1〜7の順で同一トランザクション内にコピーする。
- 通常配置でCategorySeederを全グループへ再実行しない。改名・削除したカテゴリを復活させない。

### activity_logs

- `group_id bigint NOT NULL`を追加し、groups.idをON DELETE RESTRICTで参照する。
- `(group_id, user_id)`からgroup_members、`(group_id, category_id)`からcategoriesを参照する複合外部キーを設定する。
- 現行の`user_id → users.id ON DELETE CASCADE`を廃止する。
- group_idとuser_idは認証・URLコンテキストからサーバーが決め、作成・更新本文から受け付けない。
- `(group_id, activity_date, user_id)`を一覧・集計用索引とする。複合FK用索引も実装時にPostgreSQLの実行計画で確認する。
- inactiveメンバーの記録はDBに保持するが、通常の一覧・件数・詳細から除外する。再有効化すると同じIDの記録を再表示できる。

## 認証と所属コンテキスト

### ログイン

- usernameまたはemailとパスワードの確認後、active所属がちょうど1件あることを検証する。
- active所属0件はトークンを発行せず403。資格情報不一致は従来の認証失敗とし、所属状態を漏らさない。
- DB制約上想定外だが、active所属が複数ならトークンを発行せず409とする。
- tokenはuserだけを識別し、roleやgroup_idを保存しない。各リクエストで所属状態を確認する。
- 所属をinactiveにする処理は既存の全トークンを同じトランザクションで削除する。

### `/auth/me`

以下を返す。旧トップレベルのparent/childロールは返さない。

```json
{
  "user": {
    "id": 1,
    "username": "parent1",
    "display_name": "親",
    "email": null
  },
  "membership": {
    "id": 1,
    "role": "admin",
    "status": "active",
    "group": {
      "id": 1,
      "name": "既存の家族",
      "type": "family"
    }
  }
}
```

フロントはmembership.group.idを唯一の業務APIコンテキストとして保持する。任意のgroup_idをローカル保存して認可情報として使わない。

### 保護API共通処理

1. 認証ユーザーに指定グループのactive所属があることを確認する。
2. 指定グループ内でリソースを解決する。
3. roleと所有者による操作権限を確認する。

存在しないIDと別家族のIDは404として区別しない。別家族のuser_id/category_idをクエリや本文へ指定した場合は、存在を漏らさない422とする。一覧・件数・ページング・詳細・更新・削除のすべてへ同じ境界を適用する。

## API

公開APIの基準は`/api/v1`とする。

### 維持・追加する認証API

| Method / Path | 要件 |
| --- | --- |
| GET `/status` | 維持 |
| POST `/auth/login` | 所属検査を追加 |
| POST `/auth/register` | 親・家族・所属・初期カテゴリを原子的に作成し、成功時だけtokenを返す |
| POST `/auth/register/username-availability` | ログインIDの構文と全体一意性を公開登録前に確認する。IP単位で1分30回に制限 |
| POST `/auth/logout` | 維持 |
| GET `/auth/me` | userと単一membership/groupを返す |
| PATCH `/auth/me` | 本人のdisplay_nameだけ更新 |
| PUT `/auth/me/password` | 現在パスワードを確認して本人のパスワードを変更 |

### グループAPI

| Method / Path | v0.10.0の操作 |
| --- | --- |
| GET `/groups/{group}` | activeメンバーが家族名・type・上限情報を取得 |
| PATCH `/groups/{group}` | adminが家族名だけ変更 |
| GET `/groups/{group}/members` | activeメンバーだけを一覧 |
| POST `/groups/{group}/members` | adminが同一家族の新規user＋membershipを作成 |
| GET/POST `/groups/{group}/categories` | 同一家族の一覧／adminによる末尾追加 |
| PUT/DELETE `/groups/{group}/categories/{category}` | 既存機能を家族内・admin限定で維持 |
| GET/POST `/groups/{group}/logs` | 同一家族の一覧／本人の記録作成 |
| GET/PUT/DELETE `/groups/{group}/logs/{log}` | 同一家族で閲覧、本人だけ更新・削除 |

v0.10.0ではメンバーの編集・無効化・復元APIを一般公開しない。モデル・サービス層で状態遷移と認可を検証し、管理画面とAPIは課題5で同時に公開する。これにより、UIのない危険な管理操作だけを先行公開しない。

### 廃止する旧API

- `/users`、`/users/{user}`、`/users/{user}/password`
- `/categories`、`/categories/{category}`
- `/logs`、`/logs/{log}`

旧API互換期間は設けない。移行時に全tokenを失効し、利用者へ再ログインを求める。旧PWAが残った場合は一時的に404等となり得るため、ステージングで旧版からの更新とサイトデータ消去による復旧を確認する。現在の少人数運用では個別サポートを前提とする。

## 公開登録

### 入力

| 項目 | 要件 |
| --- | --- |
| group_name | 必須、前後空白除去、1〜50文字 |
| username | 必須、3〜50文字。半角小文字英字・数字・`.`・`-`・`_`のみ、先頭末尾は英数字、全体一意 |
| display_name | 必須、1〜50文字 |
| password / password_confirmation | 必須、現行と同じ最小6文字・一致 |

type=`family`、role=`admin`、status=`active`、email=`null`はサーバーが固定する。group_id・type・role・status・emailの持ち込みを拒否する。登録時にメールアドレスを受け付けないことで、未認証の利用者がメールの登録有無を推測できる経路を作らない。

同一トランザクションでuser、group、admin membership、既定7カテゴリを作成する。途中失敗時はすべて戻し、tokenはcommit後だけ発行する。成功後はログイン済みとしてタイムラインへ遷移する。

登録画面はusernameが構文上有効になってから500ms後、または入力欄からフォーカスが外れた時に利用可否を確認する。結果は入力欄の直下へ表示する。事前確認後の同時登録もあり得るため、登録APIでも同じ構文検証とDB一意制約を必ず適用する。

### 試行制限

- 送信元IP単位の固定窓方式。成功・入力エラーをともに数える。
- 初期値は10分間に5回。6回目は登録処理前に429と`Retry-After`を返す。
- 429後の待機時間は初期値10分。待機中の要求で解除時刻を延長しない。
- 計測期間、回数、待機時間はそれぞれ環境変数で正の整数として設定する。
- 信頼するproxy設定を確認し、任意の転送ヘッダーで送信元IPを偽装できないようにする。
- 同一IPの並行要求でも上限を超えない共有cache storeを使う。cache障害時の動作をテストし、制限を黙って無効化しない。

## 上限

| 設定名案 | 初期値 | 数え方・動作 |
| --- | --- | --- |
| `FAMIE_MAX_GROUP_MEMBERS` | 10 | active所属だけ。新規作成・将来の再有効化で検査 |
| `FAMIE_MAX_GROUP_CATEGORIES` | 10 | 既定7件、使用中、全sort_orderを含むグループ所有カテゴリ |
| `FAMIE_REGISTER_WINDOW_SECONDS` | 600 | 公開登録の回数計測期間 |
| `FAMIE_REGISTER_MAX_ATTEMPTS` | 5 | 期間内の許可回数 |
| `FAMIE_REGISTER_COOLDOWN_SECONDS` | 600 | 超過後の待機時間 |

不正値・0・負数では起動／配置検査を失敗させ、無制限へフォールバックしない。上限を引き下げても既存データを削除しない。既に上限以上なら新規追加だけを拒否する。人数・カテゴリの検査と作成はグループ行ロック下の同一トランザクションで行う。

## フロントエンド

### 認証・登録

- ログイン画面に「新しい家族を登録」を追加し、`/register`へ遷移する。
- 登録画面に公開登録の入力、バリデーション、送信中、422、429と再試行可能時間、一般エラーを表示する。
- ログイン／登録成功時にuserとmembershipを共通の認証状態へ保存する。
- 401、所属なし403、想定外の所属409を区別し、利用不可状態でタイムラインを描画しない。

### 既存画面

- タイムライン、登録モーダル、活動編集、設定の全リクエストを現在のgroup pathへ変更する。
- 設定に家族名を表示し、adminだけ編集できるようにする。
- parent/child表示はmembership.roleのadmin/memberを家族向け文言へ変換する。
- メンバー一覧とタイムライン絞り込みはactiveメンバーだけを表示する。
- カテゴリ一覧・入力候補はsort_order、idの順を保つ。
- URLやクライアント状態に別家族のIDが残ってもデータを表示しない。ログアウト・401・所属異常時にuser、membership、画面キャッシュを消去する。
- ライト／ダーク、PWA、モーダル、メンテナンス等の既存挙動を維持する。

## 既存データ移行

### 移行値

- 既存の全user、category、activity_logを一つの初期家族へ移す。
- 初期家族名は`既存の家族`とし、公開後にadminが設定画面から変更できる。
- users.roleのparentをadmin、childをmemberへ変換し、全所属をactiveにする。
- category.sort_orderは既存category.id昇順で1から採番する。
- 既存ID、ログイン情報、カテゴリ名・色、活動日・時刻・本文・メモ、作成更新日時を保持する。
- 既定カテゴリ名と一致してもコピーし直さず、既存カテゴリを初期家族の所有物とする。
- personal_access_tokensを全件削除し、全員再ログインとする。

### 適用順

1. 配置前に対象環境のDB・schema、件数、role許可値、孤立参照、カテゴリ名重複、active admin候補を読み取り検査する。
2. DB・アプリ・`.env`を既存リリース手順でバックアップし、二層のメンテナンスを有効にして書き込みを止める。
3. 新テーブルとNULL許容列を追加し、初期家族・所属・group_id・sort_orderをバックフィルする。
4. 件数・ID集合・NULL・参照・role変換を検査する。
5. NOT NULL、一意制約、CHECK、複合外部キー、索引を適用し、旧制約・users.roleを整理する。
6. 新API・フロントを配置し、設定cacheを生成する。CategorySeederによる再投入を停止する。
7. 環境・DB識別、migration状態、既存家族のログインとデータ、別家族登録と分離を確認してメンテナンスを解除する。

移行は適用記録と対象IDで再実行を判定し、家族名の`firstOrCreate`だけで識別しない。異常データを推測修復せず、検査で停止する。

### 切り戻し

新APIで書き込みを再開した後は、家族境界のないv0.9.0へ自動で戻さない。原則はロールフォワードで修正する。書き込み再開前に失敗した場合だけ、状態を確認して再実行または取得済みバックアップへ復元する。

DB復元は復元時点以降の更新を失うため、対象・損失範囲を確認して明示実行する。`database_rollback_compatible=false`としてリリース自動化へ反映する。

## 実装タスクと依存関係

| 順序 | タスク | 完了条件 |
| --- | --- | --- |
| 1 | 設定・migration・モデル | 新制約、既存データ移行、上限設定、token失効をPostgreSQLで検証 |
| 2 | 所属コンテキスト・認可 | 共通解決処理を導入し、直接ID・query・bodyを含む越境を拒否 |
| 3 | 認証API | login/me/logout/本人更新/パスワードを所属モデルへ移行 |
| 4 | グループ化した既存API | members/categories/logsとポリシーを新pathへ移行、旧APIを撤去 |
| 5 | 既存フロント移行 | 全画面がmembershipとgroup pathを使用し、既存機能が回帰しない |
| 6 | 公開登録・家族名編集 | 原子的登録、試行制限、上限、初期カテゴリ、登録画面を完成 |
| 7 | 移行・リリース検証 | ステージングで実データ相当移行、旧PWA復旧、2家族分離、切り戻し判断を確認 |

各段階は独立コミットを基本とするが、旧API撤去と対応フロントは同じ公開成果物に含める。途中状態を商用へ配置しない。

## 検証要件

### DB・migration

- 空DBとv0.9.0相当DBの両方からmigrationが成功する。
- 既存のuser/category/logの件数、ID、値が保持され、全行に正しいgroup_idが入る。
- parent/childがadmin/memberへ正しく変換され、users.roleが残らない。
- 別家族のuser/categoryを参照するlog、二重所属、不正role/status、非正数sort_orderをDBが拒否する。
- migration途中失敗、再実行、バックアップ復元をステージング相当手順で検証する。
- SQLiteだけで完了とせずPostgreSQLで複合FK・ロック・制約を確認する。

### 家族分離

最低2家族にadmin/memberを用意し、以下のすべてを確認する。

- メンバー、カテゴリ、活動一覧・件数・詳細・絞り込み・ページングに別家族が混ざらない。
- URL、query、bodyへ別家族のgroup/user/category/log IDを指定しても閲覧・作成・更新・削除できない。
- admin権限は所属家族だけに効き、同一家族のadminでも他者の活動記録を編集・削除できない。
- inactive・所属なしではログイン／保護APIを利用できず、既存tokenも使えない。
- inactive投稿者の記録は非表示、再有効化後は同じ記録が再表示される。
- 最後のactive adminを0人にする同時操作を拒否する。

### 上限・登録

- 10人目／11人目、10カテゴリ目／11カテゴリ目、inactiveを含む場合を検証する。
- 同時追加でも上限を超えず、失敗時に孤立user/group/categoryを残さない。
- 公開登録の成功、入力不正、重複username、email持ち込み拒否時の応答が登録有無によらず同一であること、初期カテゴリ、token発行を確認する。
- 同一IPの5回／6回、窓境界、待機解除、並行要求、別IP、設定変更、cache障害を確認する。

### 回帰・E2E

- 親／子のログイン、ログアウト、表示名・パスワード変更、メンバー作成、カテゴリ操作を確認する。
- 週・月・期間・日別のタイムライン、登録、編集、削除、件数、ページングを確認する。
- ライト／ダーク、iPhone相当画面、モーダル、PWA更新、メンテナンス、IP制限の環境差を確認する。
- 旧APIが公開されていないこと、新APIの未認証アクセスが401であることを確認する。
