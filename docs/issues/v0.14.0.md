# v0.14.0 詳細仕様 — 画像アップロード・ギャラリー

作成日：2026-10-10。作業ブランチ：`feature/v0.14.0`。

状態：ローカル確認完了、ステージング確認待ち。本文の「設計案」「暫定値」は全端末・全環境での検証済みを意味しない。

原案：`.tools/ka2_memo.md` の「v0.14.0 の対応候補」。本文だけで要件を参照できるよう転記・整理する。

## 1. 目的・範囲

家族のアクティビティに写真を添付し、タイムラインとギャラリーから閲覧できるようにする。公開環境のストレージ消費を運営側で制御し、まず特定家族で試験運用する。

| ID | 対象 | 内容 |
| --- | --- | --- |
| R1 | PWA名 | 初期HTMLに `apple-mobile-web-app-title` を追加 |
| R2 | 一覧の取得 | タイムラインの既存ページング維持、月カレンダーの日別件数取得改善 |
| R3 | 画像添付 | 家族別有効化・容量制限、変換、閲覧、差し替え、削除 |
| R4 | ギャラリー | 固定フッターの導線、投稿者・カテゴリー・期間での絞り込み |

対象外：S3への実移行、複数画像の操作UI、元画像の保管・ダウンロード、動画・Live Photosの動画部分の保存、画像編集・手動トリミング、運用者向けWeb管理画面、リワード実装。

## 2. 調査結果・前提

- [活動API](../../backend/app/Http/Controllers/Api/ActivityLogController.php)は50件単位のページングを実装済み。[一覧画面](../../frontend/app/pages/index.vue)にも「前へ／次へ」がある。件数超過で閲覧不能になる未実装状態ではない。
- 月カレンダーは対象月の全ページを取得して日別件数を集計している。
- 活動の編集・削除は本人のみ。所属無効化済み投稿者の活動は一覧・詳細から除外される。画像にも同じ公開範囲を適用する。
- 現行APIはBearer認証。[画像取得もこの認証方式](../../frontend/app/composables/useApi.ts)との整合が必要。
- [PWA設定](../../frontend/nuxt.config.ts)の `short_name` は「ファミー」。APIはService Workerの永続キャッシュ対象外。
- ユーザーによるCoreServer確認結果：PHP Imagick利用可能、WebP書き出し可能、HEIC読み込み不可。サーバー側HEIC対応の追加は困難。
- 上記サーバー確認はユーザー報告であり、エージェントが実環境で検証した結果ではない。

## 3. 合意済みの基本方針

| 項目 | 決定 |
| --- | --- |

| 初期運用 | 公開環境の `group_id = 1` のみ明示的に有効化 |
| 容量上限 | 家族単位で変更可能。変更できるのはサービス運用者のみ。既定1GB |
| OFF時 | 新規添付・差し替えは禁止。既存画像の閲覧・削除は継続 |
| 添付枚数 | 当面1活動1枚。上限を変更しやすい構造にする |
| 保存先 | 当面CoreServer。将来のクラウドストレージ移行を考慮 |
| 保存内容 | 最適化したWebPのみ。元画像・元の属性の維持は不要 |
| カード | 本文の下、メモがあればメモの下に表示。別サムネイルは作らない |
| 編集 | 画像の削除・差し替えが可能。削除対象はストレージから物理削除 |
| HEIC／HEIF | ブラウザー事前変換を採用。`libheif-js` WASM版を検証候補とする |
| HEIC確定条件 | 暫定値で実装し、実機検証後に対応画素数・処理時間等を調整する。向き・色の再現性も検証し、正式採用を判断する |
| ギャラリー | フッターのリワードと設定の間に追加。投稿者・カテゴリー・週間／月間／指定日期間で絞り込み |
| 一覧取得 | タイムラインは既存ページング維持。月カレンダーの件数取得改善は今回実施 |

一覧取得・ギャラリー表示・暫定値での実装後検証は2026-10-10にユーザー合意済み。HEICの画素数上限・タイムアウト秒数は実装時に暫定値を置いた。実機検証後に調整する。20MB・長辺1,600px・WebP品質80等も暫定値として使用する。

## 4. R1・R2：PWA名・一覧取得

### 4.1 PWA名

初期HTMLのheadへ `<meta name="apple-mobile-web-app-title" content="ファミー">` を出力する。manifestの `short_name` と同じ定義を参照し、名称変更時の不一致を防ぐ。既にインストールされたPWAの名前が自動変更されることは保証しない。対象iOSで新規追加時の名前を確認する。

### 4.2 一覧取得（実施範囲は合意済み）

- タイムラインは既存の50件単位・前後ページ切り替えを維持する。原案の無限スクロールは「ページングが未実装なら」という条件付きのため、必須変更にはしない。
- 画像は表示位置に近づいてから取得し、一覧APIには画像バイナリを含めない。
- 月カレンダーは日別件数を返す専用APIへ変更する。投稿者・カテゴリー・日付・有効所属の絞り込みは一覧と一致させ、全ページ取得を廃止する。
- 一覧の同順位を解消するためIDを最後のソートキーに加える。ページ取得中の追加・編集時の挙動も検証する。

## 5. R3：権限・家族設定・容量

### 5.1 運用設定（方式は設計案）

- 家族DBに画像有効フラグ・容量上限を保持する。既存家族・新規家族とも既定OFF。
- 運用専用Artisanコマンドで、対象家族・変更前後の値を確認して変更できるようにする。通常の家族APIには変更権限を提供せず、直接リクエストによる書き換えも拒否する。
- `group_id = 1` をアプリ内で特別扱いせず、公開時の明示的な運用操作で有効化する。migrationだけで自動有効化しない。ステージングのIDを本番と同一視しない。
- 家族設定画面では有効状態・使用量・上限を参照できる案とする。
- 有効な所属メンバーは画像を閲覧できる。追加・削除・差し替えは活動本人だけ。家族管理者による他人の画像変更は許可しない。
- OFFへの変更後はAPI側でも追加・差し替えを禁止する。画面を開いたままOFFになった場合も保存時に再確認する。

### 5.2 容量（計算方式は設計案）

- 1GBは1,000,000,000バイトと定義し、変換後WebPの実サイズで集計する。
- 所属無効化で非表示になった画像も容量に含める。所属復元時は再表示する。
- 上限超過時も本文編集・閲覧・画像削除は可能。上限引き下げによる既存画像の自動削除はしない。
- 差し替えは `現在使用量 - 旧画像サイズ + 新画像サイズ` で判定する。上限引き下げ後の超過状態では、使用量が減少する差し替えも許可する案とする。
- 家族単位で同時更新を制御し、並行投稿による上限超過を防ぐ。クライアント申告サイズは信用しない。
- 削除待ちの物理ファイル・一時ファイルが消費する実ディスク量も運用監視する。家族容量だけではサーバー全体の空き領域を保証できない。
- 差し替え中は旧・新ファイルが一時的に併存する。全体空き容量不足では保存を失敗させ、旧画像を維持する。

## 6. 画像変換・アップロード

### 6.1 対応形式・暫定値

| 項目 | 設計案／状態 |
| --- | --- |
| ユーザー選択形式 | JPEG・PNG・WebP・HEIC／HEIFの静止画 |
| API受付形式 | JPEG・PNG・WebP。HEIC原本は受付・保管しない |
| 選択ファイル上限 | 暫定20MB／枚。対応画素数と合わせて実機検証後に確定 |
| HEIC画素数上限・タイムアウト | 暫定値はWorker内Canvas利用時2,400万画素、非対応ブラウザーでは1,200万画素、どちらも90秒。実機検証後に調整 |
| APIのバイト・画素数上限 | 実装時の暫定値は30MiB・4,800万画素。中間PNGのサイズとCoreServerの制限を測定後に調整 |
| 保存寸法 | 暫定で長辺最大1,600px。縦横比維持、小画像は拡大しない |
| WebP品質 | 暫定80。実写真で画質・サイズ確認後に確定 |
| トリミング | 保存時は行わない |
| 元画像・メタデータ | 恒久保存しない。向き・色の補正に必要な情報は補正後に除去 |

原案の「最適化した画角」は、写真内容を失わない縦横比維持として具体化する案。アニメーション画像は今回の対象外として案内する。HEIFの全コーデック・全派生形式への対応は保証せず、検証したiPhone写真を中心に対応範囲を定める。

### 6.2 HEIC／HEIFのブラウザー事前変換（詳細は設計案）

1. ファイル内容・MIME・拡張子を照合して処理を選ぶ。拡張子だけで変換成否を判断しない。JPEG等として渡された写真はHEIC処理を省略する。
2. HEIC処理が必要なときだけ、アプリと同時配信するバージョン固定のWASM資産を読み込む。外部変換サービスへ写真を送らない。
3. Web Workerでデコードする。代表となる静止画1枚を選び、補助画像・深度画像・連写全体を添付しない。代表画像選択のAPI・実際の挙動は検証対象。Workerに`OffscreenCanvas`がない環境では画素データを画面へ転送し、画面側Canvasで縮小・PNG化する。
4. 向き・色を補正し、縦横比を維持して縮小する。HDR・深度・動画部分の保持は対象外。通常表示の色が不自然にならないことを確認する。
5. 縮小した画像を中間PNGとしてプレビュー・送信する案とする。中間JPEGによる追加の非可逆圧縮を避ける。
6. サーバーで再検証し、WebP生成・容量判定・保存を行う。

デコード前後のバイト数・画素数を制限する。縮小してもデコード時のメモリは削減できるとは限らない。48MPのRGBAデータだけでも約192MBであり、WASM・Canvas等の追加領域が必要になる。Worker化もメモリ消費自体の解決にはならない。

変換は1枚ずつ行い、選択変更・キャンセル・画面終了・タイムアウトではWorkerと一時URL等を解放し、古い変換結果を反映しない。「変換中」「送信中」を区別して表示する。変換時間の上限は実機検証で決め、根拠のない進捗率は表示しない。

### 6.3 サーバー処理

- 受信画像を実際にデコードして形式・サイズ・寸法を確認し、最終WebPを生成する。ブラウザー側の変換・制限を信用して省略しない。
- JPEG等の直接送信にも同じ出力仕様を適用する。
- 保存名はサーバーで生成し、元ファイル名や任意パスを保存先に使わない。
- 一時ファイルは非公開領域に置き、成功・失敗・中断後に清掃する。元画像を恒久保管しない。
- Web PHPのアップロード上限、リクエスト上限、メモリ、実行時間と仕様値を整合させる。変換後PNGが元HEICより大きくなる場合も検証する。

## 7. 投稿・編集・削除の整合性（設計案）

- 新規投稿・編集画面に画像選択・プレビュー・選択取消を設ける。画像なし投稿は既存仕様を維持する。
- 既存画像の削除・差し替えは保存で確定。編集をキャンセルしただけでは物理削除しない。
- 画像付き保存はユーザー視点で本文と一体の操作とする。変換・保存失敗時は本文だけ成功させず、入力を保持する。編集失敗時は既存内容を維持する。
- 新ファイル作成後にDB更新を確定し、旧ファイルは確定後に削除する。DBとファイルは単一トランザクションではないため、失敗時の補償処理を設ける。
- DB確定前に失敗した新ファイルは清掃対象。DB確定後に旧画像の物理削除だけ失敗した場合は削除待ちを永続記録して再試行する。物理削除未完了を完了として扱わない。
- 活動削除時も画像を削除する。DBの外部キー削除だけに依存してファイルを残さない。
- 同時編集・差し替え・削除の競合を検出し、他の保存結果を無条件で上書きしない。
- 連打・通信断後の再試行で活動や画像を重複作成しない仕組みを設ける。
- 家族容量の減算は一度だけ行う。削除済み・削除待ち・孤立ファイルとDBの差異を照合・修復可能にする。

## 8. 保存構造・API（設計案）

### 8.1 データ・ストレージ

- 活動とは別の画像レコードに、家族ID・活動ID・保存先disk・相対キー・バイト数・幅・高さ・MIME・表示順・作成日時を保持する。
- 活動と画像の家族一致を保証する。上限枚数はサーバー設定へ分離し、現時点では1枚を強制する。設定変更だけで複数枚UIまで完成するとは扱わない。
- CoreServerの非公開永続領域を使用し、通常リリースで削除・上書きしない。DBと画像を対応させてバックアップ・復旧する。
- ファイル操作をストレージ抽象化経由に集約する。公開URL・サーバー絶対パスを画像レコードの正本にしない。
- 将来の移行は、コピー・整合性検証・レコードの参照先切り替え・旧ファイル削除の順に実施可能とする。環境設定の変更だけで既存画像が移動したとは扱わない。

### 8.2 APIの責務

具体的なルート名・multipart更新方式・レスポンス型は既存規約に合わせ実装設計時に確定する。

| 操作 | 責務 |
| --- | --- |
| 家族情報取得 | 機能状態、使用量、上限、枚数・入力制限を返す |
| 活動一覧・詳細 | 画像ID・寸法等の表示用情報を追加。バイナリは別取得 |
| 活動作成・更新 | 本文と画像操作（維持／追加・差し替え／削除）を明確に区別 |
| 活動削除 | 画像削除処理も実施 |
| 画像取得 | 認証・家族所属・投稿者の有効所属を都度確認 |
| ギャラリー取得 | 画像付き活動を絞り込み、追加取得用情報を返す |
| 月別件数取得 | 日別件数だけを返す。今回の実施範囲に含む |

### 8.3 画像の公開範囲

- 認証付き取得からBlob URL等を生成する方式を候補とし、認証トークンを画像URLに埋め込まない。
- 未ログイン・別家族・無効化された閲覧者は取得不可。無効化された投稿者の画像も取得不可。
- 画像を公開ディレクトリや共有キャッシュへ置かない。HTTPはprivate/no-store相当、Service Workerの画像永続キャッシュは対象外。
- ログアウト・画面終了時にBlob URL等を解放する。既に端末へ表示・保存された画像の回収はできない。
- 差し替えでは画像IDまたは取得識別子を更新し、旧画像の表示を防ぐ。

## 9. R4：カード・ギャラリー（詳細は設計案）

- カードでは本文・メモの下に画像全体を表示する。画像寸法から表示領域を確保し、遅延読み込みによる大きなレイアウト変動を防ぐ。
- タップで拡大表示。既存カードの編集リンク・いいね操作と干渉させない。拡大表示の閉じる操作、フォーカス復帰、読み上げ用ラベルを設ける。
- フッターはタイムライン・リワード・ギャラリー・設定の順。アイコンは `.tools/ka2_svg-icon-list.md` の `aria-label="image-album"` を既存アイコン方式へ合わせる。
- ギャラリー初期値は今週・家族全員・全カテゴリー。スマートフォンで2列表示し、一覧内の画像タップで拡大する。これらは合意済み。活動への導線も提供する案とする。
- 絞り込みは投稿者・カテゴリー・週間／月間／指定日期間。期間の基準はアップロード日時ではなく活動実施日。開始日・終了日を含み、開始日が終了日より後なら取得しない。
- 週開始日などの日付処理は既存カレンダーユーティリティに合わせる。前後の週・月へ移動可能にする。
- 並び順は活動実施日・時刻の降順を基本とし、IDまで含め順序を一意にする。
- 既定30件単位のページングAPIを無限スクロールで追加取得する。取得件数は `FAMIE_GALLERY_PAGE_SIZE`（1～100）で変更可能。重複表示を防ぎ、編集等で順序が変わった場合は再取得する。
- フィルター変更時は一覧・ページ状態をリセットし、古いレスポンスを反映しない。追加取得失敗時は表示済み画像を残して再試行できる。
- 元の最適化WebPを使用し、別サムネイルは作らない。ギャラリーの一覧だけ画像中央を正方形にクロップして表示し、拡大時と活動カードでは画像全体を表示する。拡大表示から戻った際は可能な範囲でフィルターとスクロール位置を維持する。
- 機能OFFの家族ではフッターのギャラリーメニューを表示しない。既存画像の閲覧は継続できるため、URL直接アクセスではギャラリーを表示する。

## 10. 検証・受入条件

### 10.1 HEIC技術検証（暫定値で実装後、正式採用・リリース前）

| 対象 | 記録する結果 |
| --- | --- |
| 環境 | iPhone機種、iOS、Safari／PWA、ライブラリ・内包デコーダーのバージョン |
| 入力 | 通常・縦向き・ポートレート・HDR・高解像度、写真選択／ファイル選択、元バイト数・画素数 |
| 品質 | 正しい代表画像、向き、鏡像、色、縮小後の視認性 |
| 負荷 | 初回WASM読込時間、変換時間、中間PNGサイズ、メモリ不足・タブ終了の有無 |
| 異常系 | 破損画像、未対応形式、上限超過、キャンセル、タイムアウト、連続選択 |
| 配信 | Nuxt本番ビルドでのWorker／WASM読込、旧PWAからの更新、資産取得失敗 |

結果から対応画素数・入力上限・送信上限・タイムアウト・品質を決定する。ブラウザー自動テストだけをiPhone実機合格の代替にしない。正式採用時は同梱物のライセンス・配布条件も確認する。

### 10.2 機能受入

- 全家族既定OFF、公開時の指定家族のみON、一般APIから設定変更不可。
- OFF状態での追加・差し替え拒否と閲覧・削除継続。保存直前の設定変更も反映。
- 未ログイン・別家族・所属無効化・他人による編集を拒否。復元時の再表示。
- 容量境界・同時送信・差し替え差分・上限引き下げ・物理容量不足を検証。
- 画像保存失敗・DB失敗・削除失敗・通信断・再試行・同時編集で、既存画像の消失や重複を防止。
- ギャラリーの各フィルター、空結果、複数ページ、取得失敗、順序変更、拡大表示を確認。
- 画像のない既存活動・いいね・編集・月カレンダー・家族管理を維持。
- 非公開配信、ログアウト後の画面状態、PWAキャッシュ、画像を保持するリリース・復旧手順を確認。

## 11. 残る判断事項

基本方針の再確認は不要。次の項目は未合意・未検証として区別する。

| 項目 | 提案／決める時点 |
| --- | --- |
| 画像寸法・品質・20MB・30件 | 本文の暫定値で実装後、検証し調整。HEICはWorker内Canvas利用時2,400万画素、非対応時1,200万画素、90秒で暫定実装 |
| 中間PNG・Worker・画像選択 | `libheif-js` のAPI・Nuxt配信・実写真で成立することを確認後に確定 |
| UI詳細 | トリミングなし、カード側の拡大表示、OFF時導線は設計案。ギャラリーの2列・初期今週／全員／全カテゴリー・タップ拡大は合意済み |
| 運用方式 | DB保持＋専用コマンド、家族画面の参照表示を提案。運営者だけが変更する権限は確定済み |
| API・DB詳細 | ルート・制約・競合検出・再試行・削除待ち処理・容量照合方式を実装前に具体化 |

上記提案はユーザーが個別に承認したと記録しない。HEIC実機検証で成立しない場合も、無断で対応を落とさず、制限値・代替方式・リリース範囲を再検討する。
