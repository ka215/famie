## 環境と前提

- 対象: v0.4.0 / GitHub #10。`pnpm build` で生成した商用静的ファイルをHTTPSで配信する。
- 検証URL: `https://stg-famie.ka2.org/`。SSH: `ssh s140.coreserver.jp`。
- 専用アプリ: `~/famie-stg/backend`、公開先: `~/public_html/stg-famie.ka2.org/`。
- PostgreSQLのDB・ユーザー・スキーマは `ka2_famiestg`。`.env` の `DB_SCHEMA=ka2_famiestg` が必要。`public` スキーマには作成権限がない。
- `.env` は600、APP_KEYはステージング専用。許可IPは本番の既存リストを引き継ぐ。検証端末も許可されたネットワークで接続する。
- 検証用の親 `parent1` と子 `child1` を使用する。初期パスワード記録はGit管理移行後、`~/famie-stg-release-backups/initial-issue11/original-app/accounts.txt`（private退避領域）で管理する。結果記録・スクリーンショットへ含めない。
- #11対応後の共通 `deploy.sh` は `--env staging --ref <完全SHAまたは正式タグ>` を明示して使う。省略すると本番が対象になる。[ステージング運用手順](staging-deploy-notes.md)に従い、DB・公開先・シンボリックリンクがステージングを指すことを確認する。

## 通常利用での実機検証

各段階の結果を記録してから次へ進む。アイコン削除・サイトデータ削除・Service Worker解除は行わない。iOSバージョン、機種、日時、配置コミット、操作、実結果を残す。

| 段階 | 操作 | 期待結果 |
|---|---|---|
| 旧版の準備 | v0.3.0の生成物を配信。Safariで開きホーム画面に追加。アイコンから起動して親でログイン | 単独ウィンドウで画面が開く。ログインと旧設定画面を確認できる |
| 旧版から更新 | アプリを残したまま運用者が新版の生成物を配置。アプリへ戻り、閉じて再起動も試す | 通常利用の範囲で新版へ切り替わる。設定の表示名入力と開閉カードで版を識別。更新に要した操作・回数も記録 |
| 新版の通常操作 | 親・子の表示名を変更して再起動。カードを複数開き、入力途中で閉じて開く | 表示名が保持される。入力が失われず、権限別のカード表示を維持 |
| 開いている画面で停止 | 運用者が停止し、端末でAPIを使う画面遷移または保存を行う | 次のAPI通信で専用案内が出る。ログイン切れと誤認せず、保存は自動再送しない |
| 停止中の再起動 | 新版を利用済みのホーム画面アイコンから起動 | キャッシュから画面が起動してもAPIの503でメンテナンスを案内する |
| 新規アクセス | 停止中に未利用のブラウザコンテキストで開く | Apacheの専用HTMLが503で表示される。APIは識別可能なJSON503 |
| 停止中の再試行 | 「再試行」を押す | 停止継続を表示し、書き込みを再送しない |
| 案内中の通信断 | 機内モードにしてWi-Fiも切り、再試行 | 通信できない旨を表示。停止中と断定せず、案内は維持する |
| 解除 | ネットワークを戻し、運用者の解除後に再試行 | 通常画面へ戻る。認証保持、未保存操作の非再送、専用ページが残らないことを確認 |
| 通常時のオフライン | 新版をオンラインで起動後、機内モード・Wi-Fiオフで再起動とAPI操作 | キャッシュ済み画面の起動と通信失敗を記録。メンテナンスと誤認しない。オフラインでの保存・同期は対象外 |
| 通信復帰 | 通信を戻して画面を再読込 | 通常利用へ戻り、失敗した書き込みが勝手に送信されない |

旧版には新版のメンテナンス案内が組み込まれていないため、旧版を開いたままの通信に新版と同じ案内を要求しない。旧版SWのキャッシュ状況と新版への移行は分けて記録する。

## ステージングの停止・解除

最新の `maintenance.html`、`maintenance.json` と `.htaccess` の管理ブロックを配置済みであることを確認する。シェルでは失敗時に後続を実行しない。以下はステージング限定。

```sh
set -e
cd "$HOME/famie-stg/backend"
test "$(pwd -P)" = "$HOME/famie-stg/backend"
touch "$HOME/public_html/stg-famie.ka2.org/.maintenance"
chmod 604 "$HOME/public_html/stg-famie.ka2.org/.maintenance"
/usr/local/bin/php84cli artisan down --retry=60
```

停止中に `/` と `/api/v1/status` の503、`Cache-Control: no-store`、`Retry-After` を確認する。配置完了後、次の順で解除する。

```sh
set -e
cd "$HOME/famie-stg/backend"
test "$(pwd -P)" = "$HOME/famie-stg/backend"
/usr/local/bin/php84cli artisan up
rm -- "$HOME/public_html/stg-famie.ka2.org/.maintenance"
```

解除後は画面200、status API200、ログイン入力不正422を確認する。失敗時は同じ停止操作へ戻し、復旧してから実機検証を再開する。

### 実機で判明したアイコン指定の不足

SVGのfaviconとmanifestアイコンのみで、iOS向けのPNG指定がなかった。既存 `icon.svg` をChromiumで180×180に描画して `frontend/public/apple-touch-icon.png` を作成し、背景をSVGと同じ青で不透明にした。再生成時も同じSVGを原本とする。`nuxt.config.ts` の `app.head.link` に指定し、JavaScript実行前の生成HTMLにも含める。

AppleはPNGの `apple-touch-icon` を案内している。[Apple公式資料](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html)。文字アイコンは利用可能なアイコンがない場合のフォールバックと整合するが、背景色や「K」の選択理由まで実機情報から断定しない。[WebKit公式説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/#new-fallback-icon)。

2026-09-24: PNG追加後のLint・型チェック・商用ビルド通過。新版候補をステージングへ配置し、画面/status API200、ログイン入力不正422、PNGの200 / image/pngを確認。既存ホーム画面からの更新を先に検証し、アイコンの削除は行わない。Safariの追加プレビューで新版アイコンを確認してキャンセルする。既存アイコンが自動更新されるかは別途実結果を記録する。

既存ホーム画面アイコンは今回の確認では更新されなかった。アプリ本体の通常更新は成功している。アイコンの再追加確認は通常更新・停止解除・オフラインの検証を終えてから行い、既存アイコンの自動更新を保証しない。

失敗時は画面文言、再現操作、ネットワーク状態、再起動回数、スクリーンショットを記録する。認証情報は伏せる。2026-09-24、上記実機再確認をもって#10の受入条件を充足。ステージングは通常稼働に戻し、本番公開は未実施。
