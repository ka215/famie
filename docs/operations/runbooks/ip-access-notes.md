# 環境別IP制限の設定・解除・復旧

v0.9.0以降の運用手順。**この文書の作成時点では商用解除は未実施**。通常配置は[リリース手順](release-script-notes.md)で行い、本書の設定適用はステージング検証後の商用配置時に実行担当者が行う。

## 設定の対応

| 環境 | Laravel `.env` | Apacheの画面・API | 空許可リスト |
| --- | --- | --- | --- |
| 商用・解除後 | `IP_RESTRICTION_ENABLED=false` | 接続元IPによる制限を解除 | IP判定をスキップ。認証は必要 |
| ステージング | `IP_RESTRICTION_ENABLED=true`（未指定も有効） | 既存の許可IPだけ | 全拒否 |
| ローカル | 初期値true、既存のALLOWED_IPS | 既存設定 | 有効時は全拒否 |

`false`は引用符なしの環境値として設定する。`0`や空文字を解除用に使わない。Laravelの設定キャッシュへ反映されたboolのfalseだけが解除条件となる。`APP_ENV=production`だけでは解除しない。

`.env`とドキュメントルート`.htaccess`は配置・切り戻しとも保持される。Laravel設定はApacheへ自動同期されず、PHPの変更だけでは画面・API双方の公開範囲は変わらない。

## 商用配置時の手順

1. ステージングのモーダル・テーマ・API検証と実機確認を完了する。ステージングは制限を維持し、許可外IPの403も確認する。
2. 商用の対象ホスト、アプリ配置先、公開ルート、APIリンク先を既存手順で確認する。商用の`.env`、公開ルート`.htaccess`、API側・上位の有効なIP制限設定を確認する。秘密値や実IPを公開ログへ出さない。
3. 変更対象の設定ファイルを非公開のバックアップ領域へ退避する。バックアップは設定の部分復元に使い、以後のAPP_KEY・DB設定等を誤って巻き戻さない。
4. 通常手順で検証済みv0.9.0成果物を商用へ配置する。この時点は既存許可IPから確認する。IP制限は解除せず配置できる。
5. Apache・Laravelの既存メンテナンス機能を有効にして設定を変更する。商用`.env`へ`IP_RESTRICTION_ENABLED=false`を設定する。`ALLOWED_IPS`は復旧用に保持してよい。
6. 商用のApacheで、`Require ip`等の接続元IP制限部分だけを解除する。上位設定やAPI側の設定が有効なら、対象ホストの設定範囲で調整する。`.htaccess`をリポジトリの雛形で丸ごと上書きしない。メンテナンスブロック、API/SPAルーティング、HTTPS、秘密ファイルの拒否は維持する。
7. 商用backendで既存のPHP CLIを使い、`php artisan config:cache --no-interaction`を実行する。`php artisan config:show famie`で有効値を確認する。許可IPを含むため出力は非公開の作業記録で扱う。
8. メンテナンス中のHTML/APIが従来の503となることを確認し、既存手順でLaravelとApacheのメンテナンスを解除する。
9. 下表を確認し、通常リリースの商用確認を完了する。新規回線ではキャッシュを使わないHTTP取得で確認する。

Apache設定の継承・ホスティング側のアクセス制限はサーバー実態で異なる。残存設定を調べずに`Require all granted`を追記するだけでは完了としない。

## 確認表

| 接続条件 | 操作 | 期待 |
| --- | --- | --- |
| 商用・従来許可外IP | `/login/`、JS/CSS、manifest、Service Worker | 200、正しいMIME、表示可能 |
| 商用・従来許可外IP | `/api/v1/status` | 200、status: ok |
| 商用・未認証 | `/api/v1/auth/me`、`/api/v1/users`、`/api/v1/logs` | 401、データ非公開 |
| 商用・既存アカウント | ログイン、一覧、登録、ログアウト | 従来どおり利用可能 |
| 商用・権限不足 | 子によるカテゴリ追加、他者の履歴編集 | 403、更新されない |
| 商用・メンテナンス中 | HTML / API（GET・POST） | 503、既存のメンテナンス表示・JSON、no-store |
| ステージング・許可IP | 画面、ログイン、API | 従来どおり利用可能 |
| ステージング・許可外IP | 画面、静的資産、API | 403。メンテナンス中も先に拒否 |

再配置後もこの環境差分が維持されることを確認する。配置ガードはステージングの`.env`または有効設定が明示的なfalseなら停止するが、Apacheの継承状態や制限外回線の確認を代替しない。

## 失敗時・旧版へ切り戻す場合

1. 商用の既存メンテナンスを有効にし、退避したApacheのIP制限を復元する。
2. 商用の`IP_RESTRICTION_ENABLED=true`と有効な`ALLOWED_IPS`を復元し、設定キャッシュを再生成する。許可IPからアクセスできることを確認する。
3. 必要なら既存のrollback手順でアプリを切り戻す。v0.8.0以前は新しい解除設定を認識せず常にIP制限するため、許可リストを空にしてはいけない。
4. 許可外IPの画面/APIが403、許可IPのログイン・APIが正常であることを確認してメンテナンスを解除する。

IP制限設定だけを理由にDBを復元しない。`.htaccess`・`.env`はアプリの切り戻しで自動復元されないため、設定復元を別工程として記録する。

## 記録

対象環境、日時、実行者、成果物SHA256、変更設定名、Apacheの変更箇所、使用回線の種別、検証結果、復旧用バックアップ参照を `docs/operations/change-log/` に記録する。実IP・トークン・パスワードは記載しない。
