# ブランチ運用ルール

## 背景

公開環境用の変更と開発中の変更を分離し、PR による確認を経てリリースする。現在の開発規模に合わせ、バージョン単位の作業ブランチを基本とする。

## 決定

本ルールはワークスペース全体の開発・リリースに適用する。

### ブランチの役割

| ブランチ | 役割 | 分岐元・マージ先 |
| --- | --- | --- |
| `main` | 公開環境用。通常はリリース候補の `dev` からの PR のみを受け入れる | 通常の開発変更を直接 push しない |
| `dev` | 次回リリースの開発統合・最終検証用 | 作業ブランチから原則 PR で取り込む |
| `feature/vX.Y.Z` | バージョン単位の実装・検証用 | 最新の `dev` から分岐し、PR で `dev` へ戻す |
| `hotfix/<修正内容>` | 公開中の不具合の緊急修正用 | `main` から分岐し、PR で `main` へ戻す。修正は `dev` にも取り込む |

### 通常の開発・リリース

1. 開発開始前に現在のブランチと未コミット変更を確認し、既存の変更を保持する。
2. 最新の `dev` から `feature/vX.Y.Z` を作成し、実装と検証を行う。課題ごとにコミットを分ける。
3. 対象課題の実装・検証後、作業ブランチから `dev` への PR を作成してマージする。
4. `dev` の固定コミットをステージングへ配置し、リリース前の確認を行う。この期間は次バージョンの変更を取り込まない。追加修正も作業ブランチから PR で取り込む。
5. リリース候補の最新 `dev` から `main` への PR を作成し、確認後にマージする。
6. `main` のリリース対象コミットに `vX.Y.Z` タグを付与し、まず同タグをステージングへ配置して最終確認する。合格した同一タグ・コミット・生成物を再ビルドせず公開環境へ配置する。配置したコミットと結果を `docs/operations/change-log/` に記録する。
7. リリース後は `main` を `dev` にマージして同期する。共有ブランチの履歴を書き換えず、同期も原則 PR で行う。取り込み済みの作業ブランチは削除する。

リリース判定では、対象課題の完了、変更に必要な Lint・型チェック・テスト、該当する実機確認、リリース手順を確認する。タグの付与と本番配置は別工程であり、タグだけで配置完了とは扱わない。

ステージングの通常配置対象は `dev` とする。実装途中の実機確認に限り、push済みの `feature/*` / `hotfix/*` の完全SHAも認める。対象・期間・結果をIssueに記録し、検証中は別候補で上書きしない。[ステージング運用手順](../../operations/runbooks/staging-deploy-notes.md)に従い、検証データとPWAキャッシュを保持して更新する。

### 緊急修正

通常の `dev` 経由では間に合わない公開中の不具合は、`main` から `hotfix/<修正内容>` を作成する。修正・検証後に `main` への PR をマージし、新しいパッチバージョンのタグでリリースする。その後、`main` から `dev` への同期 PR を作成し、開発中の作業ブランチにも必要な修正を取り込む。

### バージョン管理

バージョンの正本と更新タイミングは [リリース手順のバージョン管理ルール](../../operations/runbooks/release-script-notes.md#0-バージョンの管理ルール) に従う。次の作業ブランチを作成した時点で `version.json` の `current` / `next` を更新し、package の更新は準備スクリプトに任せる。`main` のリリースタグは同コミット内の `next` に一致させる。

### v0.3.0 への適用

- 作業ブランチは `dev` から分岐する `feature/v0.3.0` とする。
- 課題 **1 → 13 → 4 → 12** の順で実装する。対象範囲は [課題一覧](../../issues/summary.md) を参照する。
- 今回は4課題を1本の作業ブランチで扱う。将来、並行開発や課題ごとのリリース延期が必要になった場合は、`dev` から課題単位で分岐する運用を検討する。

## 理由

`dev` をリリース候補として兼用することで、専用のリリースブランチを増やさず、公開前の確認場所を固定できる。バージョン単位の作業ブランチは、少人数で順次実装する現在の開発に適している。

## 影響

- 開発者・支援エージェントは、作業開始前および PR・リリース時に本ルールを参照する。
- 静的生成物を Git 管理する現行方針は維持する。生成物は作業ブランチで準備して PR に含め、`main` への直接 push で更新しない。
- 既存のリリース手順にある直接の `main` への push は本ルールで置き換える。ブランチ・PR の扱いが既存手順と異なる場合は、本ルールを優先する。
- 課題12の自動化では、PR に含める生成物の準備と、マージ後の公開作業を分け、タグが指すコミットを配置対象とする。
- 本文書は運用ルールを定めるものであり、GitHub のブランチ保護設定そのものを変更するものではない。
