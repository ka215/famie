# グループ基盤の名称・所属・初期カテゴリ

2026-09-28、ユーザーのモデル素案に対する対話で以下の3点を合意した。v0.9.0では設計までとし、実装時期は別途決める。

## 決定

1. `groups` / `group_members`を採用する。初期はfamily種別のみ。内部ロールはadmin/member、家族画面では親／子と表示する。
2. 所属中間テーブルを採用するが、初期提供は1ユーザー1グループに限定する。既存アカウントの追加所属・グループ切り替えは後続対応とする。
3. プリセットカテゴリはグループ作成時に各グループへコピーする。共通カテゴリを直接参照する方式は採用しない。

## 理由と影響

認証ユーザーと所属・役割を分離し、将来の家族以外の用途や複数所属へ拡張できる構造にする。一方、初期提供では複数所属の資格情報管理・招待・切り替えを含めず、単一所属の制約を設ける。

カテゴリをグループ所有とすることで、編集が他グループへ波及せず、活動履歴との所属一致を複合外部キーで保証できる。既存CategorySeederと配置時の呼び出しは、そのまま流用せず変更する。

## 2026-09-29の追加合意

- D6：業務APIは`/groups/{group_id}/...`で対象を明示し、毎回所属・権限を確認する。
- D7：既存データはすべて新設する一つのグループへ移行する。名称は実行前に指定する。

- D4：メンバー削除は所属無効化とし、ユーザー・所属・履歴を保持する。初期の単一所属では有効な所属がなければログインを拒否し、トークンを発行しない。無効化時に既存トークンを失効し、保護APIでも所属を確認する。
- D5：avatar・birth_date・phone_number・user_metaは先行追加せず、利用機能の実装時に型・用途・権限を確定して追加する。
- D8：カテゴリの並び順はsort_orderで保持する。グループ共通の順序を管理者が変更し、新規カテゴリは末尾に追加する。sort_order、idの順で安定表示し、並び替えは一括更新する。

グループ基盤のD1〜D8の基本方針は合意済み。今回の合意によってv0.9.0へDB・API実装を追加しない。

## 2026-10-01の追加回答

- 移行時に全トークンを失効し全員再ログイン。実利用者4名への直接サポートを前提に、旧API互換期間・専用更新画面を設けない方針とし、手動で新版へ復旧可能なことをリリース時に検証する。
- 同じグループの有効な管理者が既存所属を再有効化する。ID・活動記録を保持し、本人は再ログインする。
- 無効化済みメンバーを親・子のタイムライン絞り込み候補と通常の設定メンバーリストから除外する。過去の活動カード・件数・詳細も非表示とし、DBには保持して再有効化時に再表示する。
- ユーザーは原則無期限で保持し、自動削除しない。無効化によってユーザー名・メールの一意制約を解放しない。ログイン拒否は識別子ではなく所属状態で保証する。
- 家族人数・カテゴリ数はそれぞれ既定10、設定可能にする。人数はactiveのみを数える。復元は管理者専用の別入口で行う。

リワードの詳細、後続版の実装時期は引き続き別途決定する。
