## 1. 位置づけ・適用範囲

本書を、代表管理者の権限と保護、家族全体の退会、個別メンバーの削除、識別情報のマスク、問い合わせ用の30日退避に関する仕様の正本とする。v0.20.0の規約・同意機能に先行して対応し、その実際の挙動を規約・プライバシー・Cookie等の文書へ反映する。

版別の実装計画・APIの具体的な入出力・migration・テスト工程は[詳細要件書](../issues/v0.20.0.md)で管理する。本書の仕様と矛盾する従前の無効化／削除の説明は、本書の対象機能を実装する際に更新する。従前の商用仕様が本書の作成だけで変更されたとは扱わない。

[実装詳細素案](account-lifecycle-implementation-plan.md)で現行コードとの対応・DB・API・暗号化・消去・復元を検討する。素案にある判断待ちの変更は、本書の承認済み仕様を自動的に上書きしない。

承認の経緯は[決定記録](decisions/2026-11-03-account-lifecycle.md)を参照する。本仕様への承認は商用リリース承認とは別である。

### 用語

| 用語 | 定義 |
| --- | --- |
| 代表管理者 | 家族を登録した親。家族全体の退会・無効メンバーの削除を実行できる唯一の管理者 |
| 親 | 同一家族の有効なadmin所属を持つユーザー。代表管理者も親に含む |
| 一般メンバー | 代表管理者・親の権限を持たないメンバー。年齢や法的な親子関係の認定とは区別する |
| 無効化 | データと所属を保持して利用を停止する、親による再有効化が可能な操作 |
| メンバー削除 | 無効メンバーの所属を解除し、アカウントを論理削除する、復元不可の操作 |
| 家族の退会 | 家族全体の利用を終了する操作。有料プランの解約とは区別する |
| 問い合わせ用退避 | 削除前の限定情報を暗号化して30日間だけ問い合わせに利用する処理。期限後は稼働領域から消去し、提供元backupの残存コピーは世代更新で消滅する。アカウントの復元用backupではない |

将来のギャラリー有効化申請・ストレージ容量追加申請・課金連携で代表管理者の識別を利用できるようにするが、それらの機能自体は今回の範囲に含めない。

## 2. 承認済みの基本原則

1. 家族には代表管理者を1人固定し、代表権の移譲を認めない。
2. 他の親から代表管理者を無効化・削除・降格できず、パスワードの再設定による権限奪取も防ぐ。
3. 家族の退会は代表管理者だけが実行し、パスワード再確認と全員への影響の明示を必須とする。
4. 退会・削除は即時利用停止とDBの論理削除を基本とする。DB行の物理削除は当面実装しない。
5. 元の識別情報を問い合わせ用に30日退避した後、通常DBの該当値を消去・置換する。
6. 一般メンバーの自発的な退出は提供しない。無効化は従来どおり親が行い、無効メンバーの削除は代表管理者だけが行う。
7. 個別メンバー削除時には、対象メンバーの投稿・画像も必ず削除対象にする。記録を保持したい場合は削除せず無効化を利用する。
8. 退会・削除後の復元はアプリから提供しない。30日保持は取消・復元の猶予期間ではない。

## 3. 代表管理者

### 3.1 新規家族・既存家族

- 新規家族では家族登録を実行した親を代表管理者として、家族・所属の作成と同時に登録する。
- 既存家族は、移行時点で各家族に所属するユーザーのうち、`users.id`が最小のユーザーを代表管理者とする。これは商用DBを確認したユーザーの指定であり、作成日時や所属IDによる推測へ置き換えない。
- 移行では対象者の所属・親権限・有効状態を検証する。不整合があれば停止・報告し、別のユーザーへ自動的に差し替えない。
- 代表者IDを家族に明示的に保存する。利用時に最小IDを再計算しない。一般の更新APIから代表者IDを指定・変更できない。
- 有効な家族に代表者不在・複数代表が生じないよう、作成・移行・更新の整合性を保証する。

### 3.2 保護範囲

代表管理者は家族存続中、有効な親として維持する。他の親による次の操作をUIとAPIの双方で禁止する。

- 無効化、メンバー削除、親から一般メンバーへの降格。
- 代表者IDの変更、所属の付け替え・解除。
- 他者向けパスワード再設定機能による代表管理者のパスワード変更。

代表管理者自身による無効化・降格・個別削除も認めない。自身の利用を終える操作は家族全体の退会とする。本人による通常のパスワード変更・本人確認を伴うアカウント復旧は代表権の移譲と区別し、既存の安全な認証経路に従う。

## 4. 権限と状態

### 4.1 操作権限

| 操作 | 代表管理者 | 他の親 | 一般メンバー |
| --- | --- | --- | --- |
| 代表者以外の無効化 | 可。自分自身は不可 | 可。自分自身は不可 | 不可 |
| 無効メンバーの再有効化 | 可 | 可 | 不可 |
| 無効メンバーの削除 | 可 | 不可 | 不可 |
| 家族の退会 | 可 | 不可 | 不可 |
| 代表権の移譲 | 不可 | 不可 | 不可 |
| 代表者の無効化・降格・個別削除 | 不可 | 不可 | 不可 |
| 代表者に対する他者向けパスワード再設定 | 不可 | 不可 | 不可 |
| 自発的な個別退出 | 提供しない | 提供しない | 提供しない |

削除対象は一般メンバーに限らず、代表者以外の無効な親も含む。無効化・再有効化時の人数制限等は既存仕様を維持する。最大メンバー数は有効メンバーだけを数えるため、無効化した時点で枠が空き、削除で追加の枠が生じるわけではない。

### 4.2 状態遷移

| 状態 | ログイン・業務API | 所属 | 再有効化 |
| --- | --- | --- | --- |
| 有効 | 可 | 有効 | — |
| 無効 | 不可 | 履歴とともに保持 | 同一家族の有効な親が可能 |
| 削除済み | 不可 | 有効な家族所属から解除 | 不可 |
| 家族退会済み | 全員不可 | 家族全体を利用対象から除外 | 不可 |

有効→無効→有効の従来経路を維持し、無効→削除済みを追加する。有効メンバーを直接削除しない。削除後に以前の所属へ戻したり、再登録したアカウントへ履歴を自動的に付け替えたりしない。

## 5. 家族の退会

### 5.1 確認操作

- 代表管理者にだけ「家族の退会」を提供する。通常のログアウト・無効化・メンバー削除と区別する。
- 現在のパスワードをサーバーで再確認する。入力値をログ・退避情報へ保存しない。試行制限と送信中の二重操作抑止を設ける。
- 家族全員が直ちに利用できなくなり、全員の投稿・画像等が破棄対象になることを明示する。
- アプリから復元できないこと、識別情報の30日退避、画像は保持猶予なしで実ファイル削除すること、backupには一定期間残ることを説明する。「即時に全コピーを物理削除」と表示しない。
- 影響の説明と明示的な最終確認を経て実行する。画面を開いたことや無操作を承認とみなさない。

### 5.2 確定時の処理

1. 認証・有効所属・代表者・パスワードを検証し、家族と対象データを処理中の変更から保護する。
2. 削除前の限定情報を暗号化退避し、保存成功を確認する。
3. 家族・全所属・全ユーザーを退会／削除済みとして扱い、全員の通常DB上の識別情報をマスクする。
4. 全員の認証トークンと認証・メール変更・パスワード再設定用の情報を失効・消去する。
5. 投稿・画像・ギャラリー・リワード等の取得と更新を停止し、全投稿を論理削除、全アップロード資材を保持猶予なしの実ファイル削除対象にする。
6. 受付番号、操作日時、対象、処理結果、保持期限を記録し、完了を表示してログイン状態を破棄する。

家族の利用停止はDB上の確定と同時に有効になる。画像のファイル消去完了を待たない。以後の新規ログイン・既存トークン・直接URL・メールの旧リンクからも利用を再開できない。

## 6. 個別メンバーの削除

### 6.1 実行条件

- 実行者が同一家族の有効な代表管理者であること。
- 対象が同一家族の無効メンバーであり、代表管理者ではないこと。
- 削除済み対象を再有効化できず、対象メンバーの全投稿・画像も削除対象になることを明示して最終確認すること。

### 6.2 投稿・画像の必須削除

メンバー削除では対象メンバーの全投稿を即時非表示・論理削除し、画像の原本・サムネイル等を保持猶予なしで実ファイル削除する。投稿保持の選択UI・API項目は設けず、APIからも保持を指定して回避できないようにする。

記録を保持したい場合は無効状態のままにする。従来どおり無効メンバーの投稿は非表示で、親による再有効化で再表示する。削除済みメンバーの投稿を一覧へ再表示する経路、削除済みメンバー専用の記録管理画面、後日削除機能は設けない。

対象ユーザーの識別情報を退避・マスクし、有効な所属との紐づけを解除し、認証を禁止する。家族全体の名称や他メンバーの識別情報は変更しない。

投稿・いいね・獲得履歴の複合外部キーと内部参照を維持するため、所属レコードの元の家族IDは履歴参照専用として残す。`deleted_at`を付与し、通常の所属・認証・メンバー一覧／選択候補から除外することで論理的に所属解除する。家族IDの物理的NULL化や所属行の物理削除は行わない。非公開履歴の存在を有効な所属の根拠に使わない。

### 6.3 一覧・集計への適用

削除済みメンバーをインベントリ等の対象候補から除外し、その投稿・画像をタイムライン・ギャラリー・通常の投稿／獲得いいね累計へ含めない。保持済みの内部履歴を表示のために全件走査しない。DB行の論理削除だけでは保存量は減らないため、索引・対象絞り込み・実行計画の確認は引き続き必要とする。

削除メンバーが他の有効メンバーの投稿へ送ったいいねと、それによる他メンバーのリワード進捗への反映は維持する。送信者が削除済みという理由だけで、いいね・進捗・獲得済みトロフィーを取り消さない。削除対象本人の投稿に付いたいいねは、削除投稿を通常の表示・集計から除外する方針に従う。送信者名に元の表示名を残さず、通常のメンバー候補やプロフィールへ復帰させない。匿名表示・参照保持・既存の有効所属scopeとの調整は第12節で具体化する。

無効化中も、送信済みいいねは他の有効メンバーの投稿の件数・獲得いいね累計・リワード進捗へ引き続き計上する。無効化時に除外する従前仕様は本機能の適用時に変更し、既存の無効メンバーにも同じ条件を適用する。無効メンバー本人のログイン・操作を許可したり、無効メンバー本人の投稿を再表示したりする変更ではない。

## 7. 論理削除・通常DBのマスク

ユーザーと家族に削除／退会日時を記録し、通常の検索・認証・所属判定・一覧・更新対象から除外する。所属解除だけに依存してログインを禁止しない。

| 情報 | 確定時の処理 |
| --- | --- |
| メールアドレス | `null`。変更待ちメールや関連する認証情報も消去 |
| 表示名 | 「削除済みメンバー」相当の固定表示に置換。元の値を含めない |
| ログインID | 元の値を含まない一意の削除済みIDへ置換 |
| 家族名 | 家族全体の退会時のみ「退会済み家族」相当へ置換 |
| パスワード・認証 | ログイン不能とし、トークン等を失効。パスワード値は退避しない |
| 内部ID・関連履歴 | 整合性に必要な範囲で保持し、再利用・再付与しない |
| 投稿本文・画像 | 家族退会・個別削除とも対象者の全投稿・画像を削除対象にする |

元の識別情報を別の通常テーブル・監査ログ・ジョブpayloadへ複製しない。削除前のログインID・メールは、通常DB上のマスク確定後、新規登録で再利用できる。新規登録は別の内部ユーザーIDとし、過去の所属・活動・認証・問い合わせ権限を引き継がない。同じ文字列のログインID・メールを再利用したことを過去アカウントの本人確認とみなさず、古い認証リンク・処理待ちジョブが再登録者へ作用しないようにする。

マスクはリスク低減策であり、残る投稿・画像・ログを含めて識別不能になったとの保証ではない。個人情報の法的な分類を本機能の実装だけで変更しない。

活動履歴は論理削除とし、削除リクエスト内でDB行を物理削除しない。活動本文・補足メモは削除確定後、30日を待たず、小分けのバックグラウンド処理で速やかに消去・置換する。本文は空文字または元の内容を含まない固定の削除済み文言、補足メモは`null`等へ変更し、ID・関連参照の整合性に必要な行は残す。

活動本文・補足メモは問い合わせ用の暗号化退避へ含めず、別の通常テーブル・ジョブpayload・ログにも原文を複製しない。処理途中の失敗を記録し、件数を区切って再実行できるようにする。具体的な置換値・バッチ件数・実行経路・滞留検知は版別設計で確定する。30日後に活動履歴の行を物理削除する処理は設けない。

具体的な法的保全が必要な対象は、要請・命令の真正性・根拠・対象・期間を確認したうえで通常消去の例外として個別管理する。一般的な将来の問い合わせに備えて全活動本文の消去を延期しない。保全と外部提供の可否は別に判断し、例外の受付・解除手順は第12節で具体化する。

## 8. 問い合わせ用の暗号化退避

### 8.1 保存内容・期限

| 項目 | 仕様 |
| --- | --- |
| 目的 | 退会・削除に関する問い合わせの事実確認。復元・広告・分析に転用しない |
| 保存単位 | 操作の受付番号ごとに暗号化ファイル1件 |
| 対象情報 | 元のメール・表示名・ログインID、対象ユーザー／家族の内部ID、操作日時。家族全体の退会では元の家族名も含む |
| 保存しない情報 | パスワード、認証トークン、投稿本文・補足メモ、画像 |
| 期限 | 操作確定のUTC時刻から30日（30×24時間）。参照・問い合わせ受領・再試行で延長しない |
| 閲覧者 | 問い合わせ対応を行う運営者のみ。代表管理者・他の利用者には提供しない |

通常DBには受付番号・対象ID・操作日時・期限・処理状態と問い合わせ用確認コードの照合用ハッシュを記録する。元の識別情報と確認コードの原文は記録しない。ファイル名にもメール・表示名・家族名・元のログインIDを含めない。

### 8.2 保存先・暗号鍵

- Web公開領域、アプリの配置・切り戻し対象、画像保存先から分離した専用ディレクトリを使う。通常の公開StorageやダウンロードAPIを通じて配信しない。
- 認証付き暗号でデータを暗号化し、そのデータ用鍵を公開鍵で保護する方式を用いる。改ざん・別受付との取り違えを検出できるようにする。
- PHP標準のSodium拡張を前提に設計し、Composerに`ext-sodium`を必須宣言する。ローカル・CI・商用CLI／Webの利用可否確認と必要な有効化は実装工程で行う。利用できない環境では自動fallbackせず連携する。今回の承認を設定変更済み・商用利用可能確認済みとは扱わない。
- サーバーには暗号化用の公開鍵だけを配置する。復号用秘密鍵は運営者の管理端末等でパスフレーズ付きで保管し、サーバー・Git・CI成果物・通常backupへ含めない。
- 管理端末の保存領域を暗号化し、秘密鍵の予備は暗号化したオフライン媒体に1部保管する。パスフレーズは鍵・予備媒体と分けて管理する。退避ファイル自体のbackupを作らない方針とは区別する。
- `APP_KEY`を流用しない。鍵IDとファイル形式の版を管理し、鍵変更後も期限内の既存ファイルを扱えるようにする。
- ファイルの閲覧権限を最小化する。本番はディレクトリ0700・ファイル0600相当、WindowsではACLで同等の制限を行う。
- 暗号方式・ライブラリ・鍵形式・保管パスは第12節で具体化する。暗号処理を独自に設計せず、利用可能な標準実装を使用する。

### 8.3 問い合わせ対応・破棄

- 公開窓口は`support@famie.co`。2026-11-03にユーザーがメールアカウント作成済みと報告した。受信・返信・アクセス管理の実確認は別に行う。
- 退会・削除完了時に受付番号と推測困難な問い合わせ用確認コードを表示し、利用者が保存できるようにする。受付番号は案件検索用、確認コードは操作時の控えの所持確認用とする。一般のパスワード・ログイントークンを問い合わせで送らせない。
- 確認コードは操作確定から30日間有効とし、サーバーでは照合用ハッシュだけを保存する。コードの原文をログ・監査・受付番号・URLへ含めない。照合の試行制限を設け、期限切れで無効化し、不要になった照合用ハッシュも消去する。backup復元で有効期間を延長しない。
- コード紛失時は、削除前に認証済みだったメールの受信確認等により運営者が個別確認する。同じメールやログインIDによる再登録、表示名の一致、メールのFromだけで本人と認定しない。確認できない場合は個別情報を開示せず、一般的案内に限定する。
- 個別メンバー削除の控えは操作した代表管理者のものとし、コード所持を削除された本人の確認と読み替えない。回答できる内容を操作・対象・確認の程度に限定する。30日後も窓口での一般的相談は受け付けるが、期限切れの退避情報は参照しない。
- 運営者が本人確認と必要性を確認し、受付番号でファイルを特定してSSH経由で取得し、管理端末で復号する。メールだけで本人と断定しない。
- 平文をアプリログ・メール・汎用一時ファイルへ出力しない。管理端末上の取得物・復号結果も作業後に破棄し、端末の同期・backupへ残さない運用とする。
- アクセス監査には受付番号・担当者・日時・目的を記録し、復号内容を含めない。
- 期限到達後は問い合わせ用の取得・復号対象から除外する。毎時処理で期限を過ぎた暗号化ファイルを消去し、日次点検で未削除・失敗・cron欠測を検出する。
- 消去処理は再実行可能にし、ファイルが既にない場合も処理済みとして扱えるようにする。失敗を成功にせず、期限超過と再処理結果を記録する。
- 30日は参照可能期間であり、cron欠測下で30日ちょうどの物理消去は保証しない。ローテーション等で別ファイルへ移して期限を延ばさない。

問い合わせメールは対応終了から90日後に削除する。対象は受信・送信・添付・ごみ箱等の管理可能なコピーとし、退避情報の原文や確認コードを返信・転送へ複製しない。対応終了日時と削除予定を管理する。具体的な法的保全が必要な対象は第9.4節に従う。

CoreServer上のメールデータは提供元backupにも含まれるため、メールの実消去後も最大15世代分残り得る。端末に保存したメール・添付等も削除対象を棚卸しする。問い合わせメールの保存を理由に、退避ファイル・コードの30日期限を延長しない。

### 8.4 アプリ管理backupからの分離と提供元backupへの残存

退避領域はアプリが管理する通常DBのdump・画像archive・配置時backupから除外し、退避領域独自のbackupも当面作らない。ファイルを別の通常保存先へコピーして保持期間を延ばさない。

2026-11-03にユーザーが確認したCoreServer V1の仕様では、ホームディレクトリ以下のWeb・DB・メールを含む全体が1日1回自動backupされ、最大15世代を保持する。部分的な除外はできず、古い世代は自動的に上書き・削除される。退避フォルダーもこの対象となる。これはユーザー提供の確認結果であり、今回こちらから提供元へ照会・実測した結果ではない。

この制約下では、30日は問い合わせに利用できる期限と稼働領域の消去期限であり、全backupからの消滅期限ではない。稼働領域から実際に消去された後も、暗号化コピーが提供元backupに最大15世代分残り得る。日次更新が通常どおり行われ、期限消去が滞らない場合、操作確定から約45日まで残り得るが、厳密な45日以内の全コピー消去を保証しない。消去失敗・backup世代更新の遅延は別に記録する。

提供元backupに含まれるのは暗号化ファイルと公開鍵であり、復号用秘密鍵・その予備・パスフレーズを同じサーバーへ置かない。ただし、共通の秘密鍵を保持している限り、残存する暗号化コピーは技術的には復号可能である。30日到達が暗号学的な復号不能化を意味するとは説明しない。

提供元backupから復元する場合は、公開再開や問い合わせ用取得に先立ち、元の確定日時と保持期限で期限切れ退避ファイルを再消去する。backupを問い合わせの参照期間延長や、既に期限切れの退避情報の取り出しに使わない。期限内の退避情報が障害で失われた場合も復元を保証しない。

30日後に暗号化コピー自体を残さない要件や、技術的に復号不能にする要件を採用する場合は、提供元backup対象外の保存先、または期限単位の復号鍵破棄（管理端末・鍵の予備も含む）へ設計を変更する必要がある。これらの追加方式は現時点では未採用とする。

## 9. アップロード資材・backup・復元

### 9.1 資材の保持猶予なしの実ファイル削除

- 家族退会・個別メンバー削除のいずれも、確定時から対象画像へのアクセスを止める。
- 原本・サムネイル等はDB上の削除確定後に速やかに実ファイル削除を開始し、意図的な保持期間を設けない。削除予定・成功・失敗を管理し、再実行しても二重処理で壊れないようにする。
- 問い合わせ用の識別情報の30日退避とは別の仕組みである。画像を退避ファイルへコピーしない。
- DBのrollbackに先立って画像だけが失われないよう、DB確定後にファイル消去を行う。処理時間・障害による削除待ちは保持猶予と区別する。
- 削除失敗・再試行待ちの実ファイルは家族の容量使用量へ引き続き計上し、実ファイル消去の成功を確認してから容量枠を解放する。状態更新失敗時も再照合でき、消去前に再アップロードで容量が増幅しないようにする。
- 既存の通常投稿削除・画像差替え等との整合性を確認し、アップロードの頻度・削除待ち容量・backupの実使用量も監視する。

### 9.2 backupの扱い

- DB行の物理削除は当面行わず、マスク後の行が新しい通常backupに含まれることを許容する。
- マスク前の情報・活動本文・補足メモを含む既存世代は、現行の約7日保持を基本に世代全体を期限削除する。個別データのために既存archiveを編集しない。本文消去処理が未完了の間は新しいbackupにも原文が含まれ得るため、滞留を点検する。
- 削除前に作成された通常backupには画像が世代期限まで残り得る。実ファイル消去に失敗している間は新しいbackupにも含まれ得るため、失敗・再試行待ちを点検対象にする。
- 提供元backup・障害調査で別途取得したコピー等は棚卸しし、通常backupだけの期限で全コピー消滅を保証しない。
- アプリ管理backupもホームディレクトリ配下に置かれる場合、その約7日分の世代がさらに提供元の最大15世代のbackupへ収録され得る。したがって削除前の原文・画像は、通常更新下でも元データの消去後から概算で約22日残り得る。退避ファイルはアプリ管理backupから除外するため、この約7日の入れ子保持を追加しない。実際の消去・各世代の取得日時で判断し、固定日数だけで全コピー消滅と断定しない。

### 9.3 古いbackupからの復元

- 退会・削除の確定記録を、復元対象のDB／画像backupとは別に保全する。元の識別情報を含めず、対象ID・確定日時・削除範囲・処理状態等、停止と削除の再適用に必要な項目へ限定する。
- 問い合わせ用の暗号化退避とは別の記録とする。退避ファイルの30日削除によって、過去backupからの利用復活を防ぐ情報まで失わない。
- 復元は公開・利用を止めた状態で行い、退会・削除・識別情報のマスク・活動本文／補足メモの消去・資材削除を再適用してから再開する。必要な確定記録が取得できない場合は、そのまま公開しない。
- 復元を理由に退会・削除を取消したり、保持期限を再起算したりしない。

削除確定記録は、削除済みデータを復活させ得る全backupの期限経過からさらに30日間、かつ必要な削除処理の完了まで保持する。元データやアプリ管理backupの残存コピーが新しく提供元backupへ収録される場合も含め、最後に復活させ得る世代の期限を基準にする。操作日から固定52日等で機械的に消去せず、障害調査用コピー等の追加保管がある場合は管理対象とする。

削除確定記録は復元対象DBとは別に保管し、サーバー障害にも備えた別媒体の保護されたコピーを持つ。保持期限後はそのコピーも消去し、復元不能な世代を再び利用対象へ戻さない。問い合わせ用退避と異なり、消去の再適用に必要な内部ID・時刻・範囲・状態だけを保持する。

### 9.4 法的保全の例外運用

運営者が具体的な要請・命令等の真正性・法的根拠・対象・期間を確認し、必要なデータだけを個別指定して通常消去から除外する。受付日時・根拠・対象・担当者・期限・見直し予定・解除結果を記録し、公開・通常利用から分離して管理する。

保全の必要性は定期的に見直し、不要になったら解除する。解除後、通常の保持期限が過ぎている情報は速やかに消去する。保全対象を通常消去が誤って処理しないよう競合を防止する。法的保全は外部提供の許可を意味せず、提供の可否・範囲は別に判断する。一般的な将来の照会に備えた全件の保持延長はしない。

## 10. 原子性・競合・障害対応

- 権限・状態を確定直前にも検証する。他の親による再有効化、投稿、画像更新、同時退会・削除と競合しても、退会後に処理が成立しないようにする。
- 家族・所属・ユーザーの状態変更、マスク、認証失効、削除予定、確定記録はDBトランザクションで整合性を保証する。
- 暗号化ファイルとDBは同一トランザクションにできないため、受付番号・準備／確定状態・再照合を使って管理する。平文をDBへ一時保存して解決しない。
- 退避保存失敗では退会／削除を完了扱いにしない。DB失敗では変更をrollbackし、準備済みファイルを回収する。途中停止時も後から未確定ファイルを検出・回収できるようにする。
- 完了後に応答が失われても、再送で別の退避ファイルや新しい保持期限を作らない。再試行と結果照会の具体的な契約は版別設計で定める。
- 期限消去・backup整理・復元時の再適用は、対象と期間を限定して実行する。別家族・別用途ファイルを巻き込まない。
- アプリの切り戻しで削除済み利用者を再有効化しない。旧版が新しい状態を解釈できない場合は利用制限／メンテナンスを維持する。

## 11. 画面・監査・受入基準

画面の文言・警告・エラーは日英対応する。代表管理者の識別、権限に応じた操作、キーボード・読み上げ、320px、ライト／ダーク、iPhone Safari／既存PWAで確認する。APIは画面の表示有無に依存せず権限を検証する。

| ID | 受入基準 |
| --- | --- |
| A01 | 既存家族の最小users.idと新規家族作成者が代表者に固定され、移譲・自動交代がない |
| A02 | 他の親から代表者の無効化・削除・降格・パスワード再設定をAPI直呼びでも実行できない |
| A03 | 親による無効化・再有効化を維持し、無効対象の削除だけを代表者に許可する |
| A04 | 家族退会は代表者・パスワード再確認・影響説明・最終確認を満たした場合だけ確定する |
| A05 | 個別削除で全投稿・画像が必ず削除対象となり、保持を指定できず、一覧・対象候補・投稿／獲得いいね累計から除外される |
| A06 | 通常DBの識別情報が仕様どおりマスクされ、所属・認証・旧トークン・メールリンクから復帰できない |
| A07 | 退避ファイルを公開URLや利用者権限で取得できず、サーバーの公開鍵だけでは復号できない |
| A08 | 識別情報の退避は30日で期限処理される。画像は保持猶予なしで実ファイル削除し、失敗時は再試行して消去成功まで容量枠を解放しない |
| A09 | アプリ管理backup・成果物に退避ファイル・秘密鍵・マスク前の値の別コピーを混入させない。提供元backupへの暗号化コピーの含有・15世代保持・復元時の期限再適用を区別して確認する |
| A10 | ファイル保存失敗・DB失敗・応答消失・並行操作・期限消去失敗から整合性を保って再処理できる |
| A11 | 古いbackupへ退会・削除記録を再適用し、公開前に利用停止・マスク・画像削除を確認できる |
| A12 | 家族間分離・既存の親／一般権限・活動・画像・いいね・リワードに意図しない退行がない |
| A13 | 日英・実機／既存PWA・運用点検に合格し、保持とbackupの説明が実態に一致する |
| A14 | 活動本文・補足メモを30日待たず小分けに消去・置換し、再試行・復元後も原文が再表示されず、DB行と関連参照の整合性を保つ |
| A15 | 問い合わせコードのハッシュ照合・30日期限・紛失時対応・操作主体の区別が機能し、メール再利用等で過去情報を開示しない |
| A16 | 監査90日・問い合わせ終了後のメール90日・削除確定記録の保持基準を適用し、backup復元やコピーにも期限を再適用する |

監査には操作種別・受付番号・actor／対象の内部ID・時刻・削除範囲・成否を残す。パスワード、元のメール・表示名・家族名・ログインID、投稿内容は記録しない。既存のアプリログ14日・監視履歴30日の方針を、問い合わせ用退避の期限へ混同しない。

本機能の操作・退避情報の閲覧等の監査記録は、イベント発生から90日保持する。既存のアプリログとは保存先・期限を区別し、閲覧者を運営者へ限定する。確認コード原文・照合用ハッシュ・復号内容を監査記録へ入れない。期限後は稼働領域と管理可能なコピーから消去し、提供元backupへの残存と復元時の期限再適用は他の管理情報と同様に扱う。具体的な法的保全が必要な対象は第9.4節に従う。

## 12. 実装前に具体化する事項

承認済みの機能・識別情報退避の30日期限・画像の保持猶予なし削除・権限は本書で固定する。以下は実装設計や運用実測が必要な詳細であり、実装済み・確認済みとは扱わない。

- 代表者ID・削除状態・所属解除・非公開履歴のDB配置と外部キー、論理削除scopeの適用範囲。
- 削除対象投稿のいいね・獲得履歴・進捗の整合性、削除済みデータを除外する索引・集計条件・実行計画、削除待ち画像の容量計上と実ファイル消去結果の再照合。
- 活動本文・補足メモの具体的な置換値、小分け消去のバッチ件数・実行経路・滞留検知・再試行。速やかな原文消去を前提とし、DB行の物理削除や30日退避へ変更しない。
- APIのパス・入力・応答・冪等性、パスワード再確認の検証・試行制限、結果照会方法。
- 実環境で利用可能な暗号実装、ファイル形式・鍵形式、承認済みの端末暗号化・オフライン予備を前提にした鍵の初期配置・更新・紛失時の具体的手順。
- 退避領域・秘密鍵の実パス、SSH取得・管理端末での復号と作業後破棄の具体的手順。
- 提供元の日次・最大15世代・除外不可を前提とした実際の配置と入れ子backupの棚卸し、削除確定記録の別保全の実装、確定した保持基準の期限算定と復元時の再適用手順。
- cron欠測下での毎時処理・日次点検・期限超過通知と手動再処理、処理量・時間制限との整合性。
- 作成済みの`support@famie.co`の受信・返信・アクセス管理の実確認。承認済みの受付番号・秘密確認コードの具体的な生成／表示／安全な照合方法、紛失時の個別確認手順、問い合わせ終了日の記録とメール消去の実施手順。
- 第9.4節の法的保全の運用に沿った記録形式・見直しの実施間隔・指定／解除の操作と、通常消去との競合防止の実装。

実装順は「代表管理者の固定・保護→無効メンバー削除・退会・保持／消去・復元確認→規約・同意」とする。詳細要件・ロードマップへの反映と受入工程は、これらの仕様を前提に整備する。
