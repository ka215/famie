# グループモデル拡張の移行・検証計画

2026-09-28。[モデル拡張設計案](group-model-extension-spec.md)に対応する後続版向けの計画。v0.9.0では文書化までとし、本書の手順はまだ実行しない。設計案の未合意事項を解消してからmigration・APIを実装する。

## 1. 移行前の確認

- 既存データには家族の所属情報がない。親ごとの自動分割はせず、全ユーザー・カテゴリ・履歴を一つの初期グループへ移す案とする。グループ名は実行前に指定する。
- 対象環境のPostgreSQLバージョン・制約・索引を確認する。現行仕様書の実測対象はローカルであり、商用・ステージングの実測を代用しない。
- ユーザー・カテゴリ・履歴の件数、ID集合、参照先、既存列の値を検証用に記録する。個人データを含むバックアップ・検査結果は非公開の運用領域に置き、docsへ保存しない。
- parent/child以外のrole、孤立した履歴、カテゴリ名重複、親が0人などの異常を検出したら停止する。移行処理が管理者を推測して昇格させない。
- DBバックアップと復元手順を確認し、ステージングで移行・失敗時復旧を試す。コードだけ戻せば復旧できるとは扱わない。

## 2. 段階移行

初期案は書き込み停止を伴う切り替えとする。無停止・旧新APIの並行書き込みは対象外。スキーマ拡張を先行配置する場合も、旧アプリからの追加データを含めて最後に全件検査する。

| 段階 | 処理 | 次へ進む条件 |
| --- | --- | --- |
| 1. 拡張 | groups / group_membersを作成。categories / activity_logsへNULL許容のgroup_idを追加。users.roleは保持 | 旧データ・既存機能が保持される |
| 2. 書き込み停止 | メンテナンスで更新API・登録・対象ジョブを止める。最終バックアップ・件数を記録 | 更新中リクエストの終了と停止状態を確認 |
| 3. 所属作成 | 初期グループを1件作成し、全ユーザーに所属を作る。parent→admin、child→member、status=active | ユーザー数と所属数が一致し、active adminが存在 |
| 4. 帰属設定 | 全カテゴリ・履歴へ初期group_idを設定。既存ID・本文・日時・色等は変更しない | NULL・孤立参照・グループ不一致が0件 |
| 5. 制約切り替え | グループ単位の一意制約・複合FK・索引を設定。旧カテゴリ名一意制約と旧ログのuser CASCADE等を整理。group_idをNOT NULL化 | 新しい制約が全既存行に適用済み |
| 6. アプリ切り替え | 所属権限・グループ限定API・対応フロントを配置。旧グローバルrole判定を使わない | 認証、一覧、集計、更新の越境検査が通過 |
| 7. 再開 | 既存グループの回帰確認後に利用再開。新規グループ登録の公開は分離検証後 | 監視・復旧判断担当と公開条件を確認 |
| 8. 旧列撤去 | 新アプリへの切替検証後、users.roleと不要索引を撤去（旧API互換期間は設けない） | 旧コードへの依存がないことと復旧可能範囲を確認 |

移行処理は適用記録・固定した初期グループIDで再実行を判定する。名前だけのfirstOrCreateで移行先を識別しない。途中失敗時はトランザクション境界を記録し、検証した再開点から進める。データ量・ロック時間を確認して、DDLとバックフィルのトランザクション範囲を実装時に決める。

既存カテゴリは名称がプリセットと一致していてもすべて初期グループの所有物として保持する。移行時に既存カテゴリを再コピーしない。新規グループだけへ7件のプリセットを一度コピーし、改名・削除済みのカテゴリを配置のたびに復活させない。

## 3. 認証・旧フロントとの切り替え（2026-10-01更新）

- 移行時は全トークンを失効し、全員再ログインする。無効化ユーザーに対する継続的なトークン失効とは別の切替操作として記録する。
- 実利用者は家族4名で直接サポートできるため、旧API互換期間・専用のPWA更新画面は設けない方針。端末から新版へ復旧できることを公開条件とする。
- 現行nuxt.config.tsはautoUpdate、HTML/JS/CSSのプリキャッシュ、API GETはNetworkOnly。古い画面が旧APIを呼び、一時的な404・表示失敗や認証レスポンス形式の不一致が起き得る。自動更新設定だけで全端末の即時更新を保証しない。[Vite PWA公式](https://vite-pwa-org.netlify.app/guide/auto-update)参照。
- 旧版をキャッシュした実機で、オンラインでの全タブ・PWA終了→再起動・再読込→再ログインを確認する。解消しない場合は対象サイトのデータ・Service Workerの消去と再アクセス、必要に応じてホーム画面への再追加を手動サポートする。アイコン削除だけで全キャッシュが消えるとは扱わない。
- サイトデータ消去は端末のログイン状態・未保存入力等を失うが、サーバーへ保存済みの活動記録は削除しない。端末別の具体的な復旧操作はリリース時に検証して記録する。
- 復旧は業務APIの成功やログイン済み状態に依存させない。新しいHTML・JS・sw.jsが正常に取得できること、新版で再ログイン・閲覧・保存できることを検証する。手動復旧不能ならその原因を修正してから公開し、復旧可能性を未検証のまま断定しない。

## 4. 配置と切り戻し

既存の配置スクリプトはmigrationとCategorySeederを呼ぶため、スキーマ変更だけでなくこの呼び出しも変更対象に含める。通常配置で既存グループへプリセットを再投入しない。

リリースの`database_rollback_compatible`は実際の互換性に合わせる。users.roleを残していても、複数グループ作成後に旧アプリへ戻すとグループ境界が失われるため、旧アプリへの自動切り戻しは許可しない。

| 状態 | 復旧方針 |
| --- | --- |
| 新アプリでの書き込み再開前 | メンテナンスを維持し、記録したスキーマ・データ状態に応じて修正再実行またはバックアップ復元。旧コード再開前に旧制約との互換性を確認 |
| 新アプリでの書き込み再開後 | 原則はグループ境界を維持した修正版へ進む。単純なdown migrationや旧コードへの復帰をしない |
| DB復元が必要 | 復元時点以降の更新を失う範囲を確認・合意し、書き込み停止・データ保全・復元・検査を行う |

新グループのデータを一つへ統合する自動逆移行は作らない。カテゴリ同名やユーザーの所属を失うため、元の状態に可逆ではない。

## 6. 検証仕様

少なくともA/Bの2グループにadmin/memberを用意し、inactive所属・所属なし・最後のadminも作る。正常系に加え、URL・本文・クエリへの他グループIDの混入を検査する。

| 対象 | 検証内容 |
| --- | --- |
| 閲覧・集計 | メンバー・カテゴリ・履歴・件数・ページング・期間・絞り込みへ他グループが混ざらない |
| 更新・削除 | 他グループのID指定を拒否。同グループのadminでも他者の履歴編集は不可。group_id/user_idの更新拒否 |
| 権限 | memberの管理操作、inactive・所属なしの操作、偽装role・group_idを拒否。role変更を既存トークンにも即時反映 |
| 管理者の維持 | 最後のadminの降格・無効化を拒否。2人のadminの同時変更でも0人にしない |
| パスワード | 他グループへの変更不可。本人は現在パスワードを要求。グループ管理と本人変更の経路を分離 |
| DB制約 | SQLで直接、不一致のログ投稿者・カテゴリ・重複所属・重複カテゴリを挿入して拒否を確認。別グループの同名カテゴリは許可 |
| 登録 | 重複ユーザー名・メール、途中失敗、同時登録で孤立データを残さない。プリセットは1グループに一組だけ |
| 移行 | 元のID・値・参照先・件数を保持。parent/child変換、NULL解消、異常時停止、再実行、バックアップ復元を確認 |
| 配置・互換 | 配置で削除済みカテゴリが復活しない。旧PWA・旧トークンの扱いが設計どおり。旧アプリへ危険な切り戻しをしない |

SQLiteのテストだけでPostgreSQLの制約・ロックを検証済みとしない。実装時はプロジェクトの既存テスト基盤を利用し、PostgreSQLで複合外部キー、NULL、同時更新、migrationを検証する。索引は実クエリの実行計画とデータ量で確認する。

リワードは詳細設計後、期間境界・過去日登録・編集削除・対象者変更・二重付与・所属無効化を追加検証する。この段階で未確定の付与仕様をテストへ固定しない。

## 7. 実装前に残る判断

D1〜D8の基本方針は合意済み。D4は所属無効化・履歴保持・ログイン拒否・既存トークン失効、D5は利用機能と同時の列追加、D8はsort_orderによるグループ共通順序を採用する。2026-10-01に全トークン失効、手動サポートを前提とした互換期間なし、同じ家族の管理者による再有効化、原則無期限保持・自動削除なし、人数・カテゴリ既定上限10を確認した。追加回答により、活動記録はDB保持のまま非表示・復元時に再表示、管理者専用の復元入口、activeのみ人数計算、公開登録は同一IPで10分5回・回線共有枠・各パラメータ設定可能と確定した。超過後の待機時間は600秒を暫定初期値とし、初期値そのものは未指定。リワードの付与条件は別の対話で確定する。未決事項がある間も資料の精査は進めるが、対応するDB・API実装には進まない。

## 8. 2026-09-29追加の検証・タスク

- D4：inactive・所属なしでは正しいパスワードでもトークンを発行しない。ログインと無効化の競合、既存トークン、本人プロフィール更新を含めて拒否を検証する。
- 課題11-B：sort_orderの追加・初期化、一覧の明示順、管理API、並び替えUIを後続タスクとする。既存APIは明示的な並び順を指定していないため、既存行はid昇順で初期化する案。
- 並び替えは別グループ・memberからの拒否、重複・欠落ID、作成削除との競合、同順位の安定順、失敗時の全体ロールバック、全選択UIへの順序反映を検証する。
- 列の導入はNULL許容追加→グループ単位に採番→NOT NULL・正数制約の順とし、新規作成処理も同時に更新する。実装版は別途決定し、v0.9.0のDB変更には含めない。

## 9. 追加合意に対応する受入条件（2026-10-01）

- 親・子双方で、無効化済みメンバーとその記録が通常一覧・絞り込み・タイムライン・件数から消える。詳細URL・ユーザーIDの直接指定でも取得できない。
- 管理者専用の復元入口から同グループ所属を復元でき、同じIDの活動記録・件数が再表示される。古いトークンは復活せず再ログインする。子・別グループ管理者による復元は拒否する。
- 人数はactiveのみ。上限10人のとき追加・復元を拒否し、無効化で空きができた後に許可する。同時追加・復元でも上限を超えない。
- 公開登録は同じIPから10分間5回まで。成功・入力エラーを数え、6回目は登録処理前に429となる。回線共有、別IP、窓境界、待機期間、並行要求、設定変更を検証する。
- 待機中の連打で解除時刻を延長せず、Retry-Afterが実際の解除時刻と一致する。計測期間と待機時間が異なる設定も検証する。
