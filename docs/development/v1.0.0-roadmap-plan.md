### v0.18.0：日常操作と表示の改善

#### 未確認ログイン警告

既存の未確認警告取得・確認済みAPIを再利用し、通知モーダルと設定画面の状態を共有する。親向けメンバーリストの該当者横に、元メモ指定の`key-alert-outline`を警告色で表示し、押下で警告を再表示する。

「閉じる」では未確認状態とアイコンを残し、「確認済みにする」の成功後に消す。親以外への非表示、失敗時の再試行、アカウント切り替え時の状態破棄を確認する。

#### ギャラリーからの詳細・いいね

一覧と同じ情報・操作を持つ詳細カードを1件表示する。画像・本文・メモ・いいねを表示し、自分の投稿だけ編集ボタンから別の編集操作へ進める。他者の投稿は編集不能なフォームとして表示しない。

既存の`ActivityLikeButton`・`useActivityLikes`を再利用し、二重操作・通信失敗・再試行の扱いをそろえる。ギャラリーへ戻ったときの期間・絞り込み・スクロール位置を維持する。サムネイル上で直接いいねする操作は初回範囲に含めず、必要なら別途計画する。

#### リワード演出・README

- 集中線は色を付けず、透過度の異なる白い線とする。dialogと背景の重なりを試作で確認し、操作を遮らないこと、動きを減らす設定、iPhoneでの負荷を検証する。
- `README-ja.md`と日本語UIのスクリーンショットを用意し、英語READMEと相互リンクする。冒頭の「English｜日本語」を基本とし、バッジを使う場合は「README: 日本語」等、技術言語と誤認しにくい表現にする。
- 最新CI結果のバッジを追加する。未公開機能を実装済みとして紹介しない。

### v0.19.0：監視・検証の基盤

2026-10-26のユーザー決定により、死活監視・外形監視の新規実装（Windows runnerの定期巡回、Web/API・TLS期限の継続監視、稼働率バッジを含む）は後続タスクへ延期し、対応版は未定とする。既存の配置後疎通確認・候補検証は維持する。`manage.famie.co`は別リポジトリの別プロジェクトとして、インフラを含め別途検討する。[v0.19.0詳細仕様](../issues/v0.19.0.md)はこの範囲変更を反映し、同日仕様全体を承認済み。

| 区分 | 最低限の対象 |
| --- | --- |
| アプリ | エラー、認証失敗・制限、権限拒否、管理操作、リクエスト追跡ID |
| サーバー内部 | 容量、バックアップ成否、実際に使用する定期処理。Web/API死活・外形監視とTLS期限の継続監視は後続タスク |
| 運用 | 通知先・条件、保存期間、閲覧権限、障害対応、バックアップからの復元確認 |

パスワード・トークン・活動本文・画像等をログへ不用意に残さない。監視で侵害不存在を保証するのではなく、検知対象と対応手順を明文化する。

カバレッジは現状値を取り、認証・家族間分離・画像アクセスを優先する。同意記録の実装後は同領域も対象に加える。全体の高い数値だけを初期の合格条件にしない。

CIは既存のchecksとブラウザ別E2Eの並列化を前提に、工程別所要時間と重複処理を計測する。辞書検査・単体・API・日英の画面操作を役割で整理し、効果のある分割を採用する。日英切り替え等の組み合わせ試験と、成果物生成前の必須合格条件を維持する。

カバレッジバッジは実測と安全な公開方式に基づき追加する。監視・稼働率バッジは死活・外形監視とともに後続タスクへ延期する。再開時には瞬間的なOnline表示と観測期間付きuptimeを区別し、公開情報から内部構成を漏らさない。

node-forgeの修正版は初期調査時点で未公開だったが、同日1.4.1の公開を受け更新・脆弱性例外撤去をローカル検証中。観測候補55adfbc6は上書きせず、更新後の候補を別途検証する。解消不能なら未達を明示し、例外期限を自動延長しない。cronの観測期間と修正後の受入を合意し、直近正常だけで過去欠測の原因解消としない。

## 5. セキュリティ検証の恒常化とv0.21.0

### 実行頻度と対象環境

| タイミング | 実施内容 |
| --- | --- |
| 通常PR | 関連する認証・権限回帰、秘密情報・依存関係・静的検査 |
| 定期・手動 | ステージングで動的検査、広い入力・アップロード検証 |
| 各リリース候補 | 変更範囲の重点検証。認証等の変更では範囲を拡大 |
| v1.0.0直前 | 全項目の総合検証、修正、再検証 |

検証コードを専用ブランチへ隔離せず、通常の開発と共有し、手動workflowで候補SHAを指定できる構成を基本とする。既存のIP制限と許可済みself-hosted runnerを利用し、検査ツールの通信・認証経路を確認する。IP制限を維持したステージングでの全項目実施を目指すが、実行可能性は検証基盤の設計時に確認する。

侵入的検査は専用テスト家族・データを使ってステージングで行う。商用は非破壊の疎通・設定確認を中心とし、総合スキャンの標準対象にしない。

### 検証項目

元メモのXSS、SQLインジェクション、ディレクトリトラバーサル、なりすまし・セッションハイジャック、辞書攻撃、CSRF、OSコマンドインジェクションを検証対象とする。入力欄だけでなくAPI・URL・ヘッダー・ファイル等の入口も整理する。

追加対象は次のとおり。

- 家族間・ロール間の権限逸脱：ID変更による他家族の活動・画像・警告へのアクセス。
- トークン・復旧経路：失効、ログアウト、メンバー無効化、再設定トークンの期限・再利用。
- 画像処理：形式偽装、巨大画像、容量制限、メタデータ、画像URLの認可。
- 情報漏えい：メール等の列挙、詳細エラー、ログ、バックアップ・設定ファイルの公開。
- ブラウザ側の保護：CORS、CSP、クリックジャッキング、PWAキャッシュのアカウント間混在。
- 競合・濫用：連打、二重送信、レート制限回避、リワード・いいねの整合性。
- 供給網：依存パッケージ、Actions、秘密情報、成果物の完全性。
- ポリシー・同意：同意前の非必須処理、同意記録の改ざん・検証漏れ。

承認時点では、認証トークンはJavaScriptから読めるCookieに保存し、APIへBearerで送信している。脆弱性が確認されたという意味ではないが、XSS時の影響と認証方式を重点レビューする。CSRFは各エンドポイントの認証経路に沿って確認する。

「バックドアがないこと」は単一試験で証明できないため、コード・依存関係・配置資材・管理経路のレビューへ分解する。OWASP ASVSを項目整理の基準に用い、自動検査で保証できる範囲と手動確認を記録する。

## 6. v1.0.0公開条件

- v1.0.0前に割り当てた要件の実装・受入を完了している。
- 日英のポリシー、必要な同意制御・記録、既存利用者の扱いが整備されている。
- 監視通知、障害対応、バックアップからの復元を確認している。
- 総合セキュリティ検証で判明した重大・高リスク問題が解消され、修正後の再検証に合格している。残る指摘の評価・扱いも記録する。
- 日英、iPhone Safari／PWAの主要導線と最終回帰確認に合格している。
- 固定候補のステージング確認、ユーザーによる商用リリース承認、同一成果物の昇格を既存手順どおり実施する。

| 目安 | 対応範囲 | 着手時に決める事項 |
