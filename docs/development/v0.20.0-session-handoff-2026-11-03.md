## 3. 重大事故の確定事実

### 3.1 事故を起こしたコマンド

Codexが2026-11-03 17:26頃に以下を実行した。

```text
php artisan migrate:fresh --env=testing --force
```

`.env.testing`が存在しなかったため、`--env=testing`はAPP_ENVだけを変更し、DB接続値は`.env`のローカルPostgreSQLを継承した。`phpunit.xml`のSQLite `:memory:`指定はPHPUnit起動時だけに適用され、Artisan単体実行には適用されない。その結果、接続先`famie_db`のpublic schemaが`migrate:fresh`で全再作成された。

### 3.2 原因を裏付ける証拠

- PostgreSQL物理テーブルファイルの作成日時：2026-11-03 17:29:09 JST。
- 事故直後は全19 migrationが同一の`batch=1`で、users/groups/group_membersは0件・物理ファイル0 bytesだった。
- Codex sessionログに17:26頃の上記コマンドが残っている。
- 事故直後の論理削除ユーザー、削除所属、退会家族、ライフサイクル操作は全て0件だった。F02の退会／メンバー削除機能が誤実行されたのではない。
- PostgreSQLは`archive_mode=off`、`archive_command=(disabled)`。アプリの日次バックアップ保存先にも利用可能な直近世代はなかった。

### 3.3 根本原因

直接原因は、破壊的コマンドの実行前に実接続先を検証せず、`--env=testing`をDB分離と誤認したこと。工程上の原因は、ローカル利用DBに対する破壊的Artisanコマンドをアプリ側で拒否する仕組みと、実行前スナップショットがなかったこと。これはCodex側の重大な操作ミスである。

## 5. 追加した再発防止策（未コミット・要独立監査）

以下を未コミット差分として追加した。

- `backend/app/Support/DestructiveDatabaseCommandGuard.php`
- `backend/tests/Unit/DestructiveDatabaseCommandGuardTest.php`
- `backend/app/Providers/AppServiceProvider.php`からのLaravel標準`prohibit()`設定

対象コマンド：

- `migrate:fresh`
- `migrate:refresh`
- `migrate:reset`
- `db:wipe`

現在の方針は、APP_ENVが`testing`で、既定接続のDBが`:memory:`または名前が`*_test`の場合だけ許可し、それ以外は終了コード1で拒否するもの。事故時と同条件の`APP_ENV=testing`＋`famie_db`では拒否されることを確認した。

注意事項：

- 最初に試した`CommandStarting`イベント方式は、外側のArtisanコマンド開始後にサービスプロバイダがbootするためガードにならず、不採用とした。
- `.env.testing`追加案は既存PHPUnitのAPP_KEY等を遮蔽して多数のテストを壊したため撤回済み。現時点で`.env.testing`は追加していない。
- Laravel標準`prohibit()`は既定接続を基準にした静的判定である。`--database`による別接続指定など、全ての経路を十分に防げるかは次セッションで独立して脅威分析すること。
- ガードを安全と断定せず、破壊的コマンドを実データDBへ向けて再試験しないこと。専用の使い捨てDB／SQLiteファイルで試験すること。
