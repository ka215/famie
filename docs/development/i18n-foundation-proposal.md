# 多言語化の基盤設計素案 — v1.0.0に向けて

作成：2026-10-17。v0.16.1の成果物は本素案。**翻訳・DB・API・画面の実装は今回行わない**。[v0.16.1の対応範囲](../issues/v0.16.1.md)に基づく。以下の技術選定・API案・項目名は採用前の案である。

## 1. 要求と現状

v1.0.0は日本語・英語の2言語対応で公開する。初期表示は利用者のロケールから決め、日本語以外は英語とする。表示設定から各ユーザーが変更でき、家族全員の設定にはしない。フロント／バックの利用者向け文言は翻訳ファイル経由にする。

現行フロントはNuxt 4の静的SPAで、常駐Nodeサーバーは使わない。`useApi` はBearer認証とJSONを利用。画面・Zodエラー・ARIA文言は日本語を直接記載している。カレンダーユーティリティにはja系／その他をja-JP／en-USに分ける既存処理があるが、週開始日は元の端末ロケールを参照する。`useTheme`の端末保存を、そのままユーザーの言語設定の正本にはしない。

バックエンドはLaravel 13。`config/app.php`のlocale設定はあるが、Controller・FormRequest等の応答、アカウントメール、共通エラーに日本語の直接記載がある。認証ユーザーと家族所属は別オブジェクトとして扱われ、将来の言語保存先は所属・家族ではなくユーザー本人とする。

## 2. 言語判定・保存案

ユーザー承認済みの方針は、本人のDB設定を端末間で共有し、「自動／日本語／English」の3択にすること。具体的な項目案は `users.ui_locale = null | ja | en`。nullは「自動」、固定値は本人が選択した言語。子を含む全ユーザーが自分だけを変更する。既存ユーザーにはnullを初期値とする。家族管理APIから他人の言語を変更させない。

| 状態 | 表示言語の決め方 |
| --- | --- |
| ログイン後・固定言語あり | DBの本人設定を最優先。別端末にも適用 |
| ログイン後・自動 | ブラウザが最優先とする言語がja系ならja、それ以外はen |
| 未ログイン | その端末のゲスト選択があれば適用し、なければ同じ自動判定 |
| 判定不能・不正値 | enへフォールバック。IPによる国推測は使わない |
| アカウント変更・ログアウト | 前ユーザーの言語キャッシュを解除し、本人設定／ゲスト設定を再判定 |

`ja`／`ja-JP`は日本語、`en-JP`／`fr-FR`は英語とする案。「端末に日本語が候補として含まれるだけ」で最優先の他言語を上書きしない。手動設定をOS変更で上書きしない。「自動」の場合だけ端末変更に追従する。言語判定とタイムゾーン・週開始日・リワードの期間計算は分離し、言語変更で既存データの意味や対象日を変えない。

2026-10-17にja系による初期判定と本人DBでの保存方針を承認いただいた。端末キャッシュは補助とし、ログインユーザー別のキーで家族共有端末の混同を防ぐ。DBのカラム名・型等の具体的な実装は後続版で確定する。

## 3. フロントエンド案

候補はNuxt I18n（内部のVue I18nを利用）。既存URL・旧メールリンク・PWA scopeを維持するため、言語別のURL prefixは追加しない `no_prefix` を基本とする。公式の[ルーティング戦略](https://i18n.nuxtjs.org/docs/guide)を確認した。独自の文字列置換器より、名前付きパラメータ・複数形・型検査・フォールバックを持つ既存機構を優先する。

`frontend/i18n/locales/ja.json`・`en.json`などの辞書を機能別の意味キーで管理する案。`common.save`、`activity.create.title`、`account.passwordReset.invalidLink`などを用い、日本語本文を識別子にしない。単語断片の連結ではなく文単位で翻訳し、パラメータを名前付きで渡す。ユーザー入力を翻訳キーにせず、HTMLを含む翻訳は原則避ける。

静的生成で動く構成を必須とし、実行時のNitro翻訳APIに依存しない。まず2言語の静的バンドルを候補として検証し、遅延読込は全辞書が成果物・PWAに含まれることを確認してから採用する。[公式の翻訳ファイル読込](https://i18n.nuxtjs.org/docs/guide/lazy-load-translations)と、実装時の採用版のNuxt 4互換性・設定を再確認する。v0.16.1ではパッケージを導入しない。

起動時はゲスト／本人キャッシュで仮表示し、本人取得後にDBの設定へ合わせる。設定更新は成功応答で確定し、失敗時は保存済み言語を保持する。`html[lang]`、画面タイトル、ARIA、Zodエラー、確認ダイアログ、トーストを同じ言語にする。日付・件数の表示はIntlを使うが、APIのISO日付・数値形式は変更しない。

## 4. API・バックエンド案

本人の既存 `PATCH /auth/me` へ `ui_locale` を追加し、ログイン・本人取得応答にも返す案。既存の表示名等と部分更新を両立し、許可値はnull／ja／enのみ。migration・OpenAPI・フロント型・Featureテストを同じ実装版で更新する。新しい家族設定APIは作らない。

フロントは実効言語を `Accept-Language: ja` または `en` で送る。バックは認証後の本人固定設定を優先し、自動・ゲストは許可言語へ正規化したヘッダーから決める。不正な値で任意ファイルを読まない。Laravelの[公式ローカライズ機構](https://laravel.com/framework/docs/13.x/localization)には辞書・リクエスト単位のlocale・fallbackがあり、これを使う案とする。

`backend/lang/ja/`・`en/`配下で、入力検証・認証・アカウント・活動・リワード・メール等の文言を管理する。リクエストごとに言語を決め、別ユーザーの処理へ状態を残さない。認可判定・HTTPコード・数値・JSONのキーは変えない。既存の日本語本文に依存するフロント判定がないか確認し、必要なエラーは言語に依存しない安定したcodeで分岐する。code追加は実装版で互換性を審査する。

応答の言語を明示する場合は `Content-Language`、キャッシュされる応答は `Vary: Accept-Language`等の分離を検討する。認証データの共有キャッシュは導入しない。

## 5. メール・例外経路

メールの件名・本文・ボタン・有効期限表現も対象。固定言語のある受信者には本人設定で送る。自動の場合は申請時の実効言語を処理コンテキストへ渡す案とし、遅延処理でも再現する。旧アドレスへの変更通知など、操作した人と受信者が異なる場合は受信者の設定を基準にする。ユーザー未特定の応答はヘッダーから決め、登録の有無を言語差や応答差で漏らさない。

認証切れ・アクセス制限・メンテナンス・通信失敗・404・起動中表示・SW更新・ホーム追加ガイドまで棚卸しする。Apacheの静的メンテナンス画面・旧URLの案内JSONはアプリの辞書を実行できないため、ビルド時の静的生成または日英併記を別途設計する。OS固有のインストールUI文言はアプリの翻訳で制御できない範囲として区別する。

活動本文・家族名・人名・編集可能なカテゴリ名・リワード名等の保存済み利用者データは自動翻訳しない。初期カテゴリの扱いは保存名をそのまま表示することを基本に、翻訳対象との境界を実装時に確認する。言語変更で既存レコードを書き換えない。

## 6. 翻訳データの一元管理

最初はフロント／バックで別の辞書を持ち、共通の意味キー・用語集・レビュー基準を揃える案を推奨する。両者でパラメータ構文、複数形、ネスト／キー解決が異なるため、同じJSONを無変換で読めるとは扱わない。フロントがバックのソースを実行時に読んだり、翻訳用APIに毎回依存したりする構成は避ける。

将来の一元管理案は、ルートの共通カタログを正本にし、ビルド時にVue用辞書とLaravel用辞書へ生成する方式。共通化するのは共通UI・エラー・メールの意味キー等に絞り、各基盤固有の複数形・書式はadapterで変換する。キー一致・パラメータ集合・重複・空文言・生成後差分をCI検査する。生成物の再現性と翻訳の所有範囲を確定してから採用する。

一元管理は後続タスクとして分離できる。v1.0.0の必須条件は利用者向け文言が日英の翻訳ファイルから出力され、個人単位で言語を変更できることであり、カタログ物理統合そのものとは分ける。

## 7. 実装分割・受入計画

1. 言語判定・保存方針、用語、翻訳対象を確定。辞書・型・静的生成の最小構成を検証。
2. 本人設定のDB・API・表示設定・認証前後の言語適用を実装。
3. 共通UI→認証／設定→活動／画像／リワードの順に画面文言を移行し、API検証・例外・メールを移行。
4. 静的例外経路とPWA・アクセシビリティを確認し、v1.0.0の受入を実施。
5. 必要なら共通カタログ生成を独立して実装。

ja-JP／ja／en-US／en-JP／その他／取得不能、自動・固定・保存失敗・端末変更・ユーザー切替、家族内で異なる言語、認証切れ、メールリンク、日英の長文・複数形・ARIA、PWA更新をテストする。キー・パラメータ差分をCIで検知し、fallbackがあるだけで未翻訳を合格としない。APIの権限・レート制限・日付境界・リワード獲得が言語で変わらないことも回帰確認する。

## 8. 判断状況

- 確定：対象は日英、利用者ごとの切替、フロント／バックとも翻訳ファイル経由、v0.16.1は基盤設計素案のみ。
- 承認済み：ja系による初期判定、DB本人設定の自動／日本語／English、端末間での共有。
- 後続設計で確定：採用ライブラリの版、辞書の具体的配置、API項目・エラーcode・自動メールの言語保持、静的例外経路、カタログ統合の実施版。
