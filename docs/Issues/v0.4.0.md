## 12-C：ステージング運用・環境切り替え（追加承認）

ステージングを常設のリリース前検証環境とし、独立した実装を作らず `deploy.sh --env production|staging` で切り替える。既定はproduction、事前確認のみ。実配置には `--apply` と専用DBのバックアップ参照を必須とする。

受入条件：

- 本番はorigin/mainと一致する正式タグのみ、任意refを拒否する。ステージングはdev、実機確認用feature/hotfixの完全SHA、または本番候補の正式タグを明示する。
- 環境ごとのパス・URL・DB・スキーマ・バックアップ・ロックを固定し、.envと有効な設定・実接続の取り違えを更新前に拒否する。
- 停止と復旧、705/604、IP制限・.htaccess・APIリンク、バックアップを両環境で維持する。
- .env・DB・検証データを保持してアーカイブ配置からGit管理へ移行し、通常配置ではDB初期化やUserSeederを行わない。
- dev確認→mainへPR→正式タグのステージング確認→同じ生成物で本番配置をルール化する。
- 旧本番入口の刷新はv0.4.0公開直前に固定コミットから行い、旧cli名は互換入口とする。
- 異常入力・環境不一致・本番制約・失敗復旧のテストと実ステージングの配置を確認する。

手順・検証結果は[ステージング運用手順](../operations/runbooks/staging-deploy-notes.md)、進捗の正本は#11。本番アプリの公開と旧入口の実切り替えは今回の作業対象外。

## 12-A：デプロイ運用の一本化

PHP CLI と Composer の実行パスを指定できる標準スクリプトへ統合する。独立した deploy.sh / deploy-cli.sh の二重保守を継続しない。既存名からの移行方法を明示する。CGI版PHPでの実行は対象外。

受入条件：

- PHP CLI・Composer の実行確認を更新前に行い、不正な指定では更新を開始しない。
- 全 Artisan・Composer・異常終了処理で選択した CLI を使用する。
- 公開資材はディレクトリ705・ファイル604とし、バックアップ保護用 umask 077 を維持する。backend全体の権限は一括変更しない。
- 本番 .htaccess、APIリンク、IP制限を保持する。
- バージョン・タグ検証、DBバックアップ参照、二重実行防止の既存動作を維持する。
- 失敗段階・バックアップ・復旧操作が分かるログと、サーバー上の旧スクリプトの移行手順を用意する。
- 構文・入力拒否・CLI/Composer異常・公開権限・保護対象の保持を影響に応じて検証する。POSIX権限は対応環境で確認し、Windows上の構文確認だけで完了としない。

## 12-B：メンテナンス表示と運用連動

静的フロントとLaravel APIの両方を対象とする。今回の403は権限エラーであり、メンテナンスには503を使用する。

受入条件：

- 許可された利用者の画面アクセスには専用ページとHTTP 503を返す。IP制限は緩和しない。
- APIにはメンテナンスと識別できる503応答を返す。通常の通信障害・オフラインと区別する。
- 開いている画面・PWAは次のAPI要求で検知し、専用の案内を出す。認証切れによるログアウトとして扱わない。
- メンテナンス中の案内が、通常のエラー表示や認証ミドルウェアで上書きされない。
- デプロイ開始時に有効化し、変更開始後の失敗では維持する。更新前の検証失敗で稼働中サービスを停止しない。
- 更新完了後は合意した確認順序で解除する。解除後のチェックに失敗した場合もメンテナンスに戻して復旧方法を示す。
- 再試行ボタンで復旧を確認できる。書き込み要求は自動再送しない。
- 専用ページ自体をキャッシュし続けて復旧後も表示される問題を防ぐ。既存PWAキャッシュから起動する場合も検証する。
- 新規アクセス・開いている画面・失敗時維持・復旧・通信障害との区別を確認する。Apacheの503とAPIの503はそれぞれ検証する。

対象外：常時監視・操作していない端末への即時通知、復旧予定時刻の管理画面、書き込み自動再送、オフライン記録・同期。

### 確定事項：方式Aでメンテナンス解除とHTTPチェックを行う

採用する方式Aは「メンテナンス中に配置・設定などの確認 → 解除 → 公開URLのHTTPチェック → 失敗時は再度メンテナンス」。既存の手順を活かして規模を抑えるが、解除からチェック完了まで一般利用者がアクセスできる短い期間がある。

ユーザー承認済み。解除前の検証専用アクセス経路は今回設けない。

## 3：自分の表示名変更

親・子とも、ログイン情報カードから自分の display_name のみ編集する。親による子の編集は課題5に残す。

表示名変更を最初の適用先として Zod を小規模に導入する。スキーマは `frontend/shared/utils/` に置き、Vue の状態や画面表示に依存させない。フォームの型はスキーマから導出し、二重定義を避ける。

受入条件：

- 空欄不可・最大50文字の既存制約に合わせ、失敗理由を表示する。
- 保存後に画面内の自分の表示名へ反映され、再読込後も保持される。
- 他人の情報、ユーザー名、メール、ロールをこの操作で変更できない。
- 既存の親向け更新APIを子へそのまま開放しない。自己更新の許可項目・対象者をサーバー側で制限する。
- 親と子の正常保存、入力不正、他人・権限項目への更新拒否を検証する。
- 保存時に Zod の safeParse で検証し、不正な入力は送信せず、日本語で理由を表示する。
- 空欄・空白のみ・正常値・50文字の境界と超過を確認する。絵文字等の文字数と空白の扱いを Laravel 側と整合させる。
- Laravel 側の検証と権限制御を維持し、API の422エラーも画面に表示する。クライアントの検証だけに依存しない。

対象外：他の既存フィールドの一括移行、汎用フォーム基盤、追加のフォームライブラリ。フロントとバックのスキーマ連携（OpenAPI Schema による契約連携・型や検証コードの生成など）は後続対応とし、構造を別途検討する。今回は共有契約の自動化を行わず、双方の検証結果の整合を確認する。

### #8 検証結果

- 本人専用 `PATCH /v1/auth/me` は表示名のみを受け付け、対象ID・他の属性の混入は422で拒否。既存の親向け更新APIの権限は維持。
- Laravel：17テスト／72アサーション通過。親・子の保存、他人・権限項目の保護、認証必須、空欄・不可視空白・50/51文字・絵文字を検証。
- Zod：Laravelの前後空白除去・Unicodeコードポイント数に合わせたスキーマの単体テスト通過。型はスキーマから導出。
- Chromium / iPhone相当WebKit：親・子各2ブラウザの4テスト通過。不正入力の未送信、ヘッダー・家族一覧への反映、再読み込みでの保持、API422表示を確認。
- 関連Lint・型チェック・Pint通過。生成物の更新と公開はリリース準備で行う。

## 14：設定カード開閉

- 複数カードを同時に開ける。ロール別の表示権限は維持する。

- 初期状態、独立した開閉、入力保持、キーボード操作を検証する。
